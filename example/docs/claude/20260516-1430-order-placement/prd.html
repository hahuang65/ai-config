PRD — Order Placement

Customer-facing order placement endpoint with idempotency keys, persistent order history, cancellation, and at-least-once event emission for downstream consumers (Fulfillment, Billing).

01Problem & Solution

Problem

Customers can browse the catalog and add Items to a Cart, but there is no way to convert a Cart into a persisted Order. Without persisted Orders, downstream systems (Fulfillment, Billing) have nothing to consume, Customers have no order history, and naïve retries risk creating duplicate purchases on flaky mobile connections.

Solution

Add a customer-facing order placement endpoint that:

  1. Accepts a Cart and produces a persisted Order with pending status
  2. Deduplicates retries via Idempotency-Key (24h, per Customer)
  3. Emits OrderPlaced for downstream consumers
  4. Exposes order history per Customer
  5. Allows Customers to cancel pending Orders

03Implementation Decisions — Modules

OrderService

Owns Order persistence, state transitions, and event emission. Small public surface: place_order, cancel_order, list_orders. Internal complexity (transactional outbox, state machine validation) is fully encapsulated.

Deep module

IdempotencyStore

Redis-backed lookup keyed on (customer_id, idempotency_key). Public surface: get, put. Internals handle TTL, key encoding, and degrade-on-outage semantics.

Deep module

EventPublisher

Generic at-least-once publisher with transactional-outbox semantics. Used here for OrderPlaced and OrderCanceled. Shared with other contexts.

Existing shared module

HTTP layer

Thin handlers that validate inputs, call OrderService, map errors to status codes. Authorization checks Customer ownership.

Shallow by design
04Implementation Decisions — Choices
  • Lifecycle: linear pending → confirmed or pending → canceled. No back-transitions. ADR-0002
  • Idempotency: client-supplied Idempotency-Key header (required); Redis 24h TTL; per-Customer scoping. ADR-0001
  • Events: at-least-once delivery; consumers required to dedupe on event_id. ADR-0003
  • Ordering: emit OrderPlaced AFTER the Order row commits, never before. Use transactional outbox for the publish.
  • Authorization: order history and cancel endpoints verify the requesting Customer owns the Order. 403 on mismatch.
  • Cancel from confirmed: rejected with 409 and error code ORDER_NOT_CANCELLABLE. UI maps to "contact support" — refunds live in Billing.
05Testing Decisions
Good tests here exercise the OrderService through its public interface only — never reach into Redis or the DB directly. A test reads like a specification: "places an Order with pending status and emits OrderPlaced," not "calls _persist_order then _publish_event."

06Out of Scope

Deliberately excluded

  • Refunds (Billing's concern; see ADR-0002)
  • Partial cancellation of individual OrderLines — Order is the unit of cancellation
  • Order modification after placement — Customers create a new Order to change Items
  • Guest checkout — Customer identity is required
  • Multi-currency totals — single-currency for now; revisit when the requirement is real
  • Inventory checks at order placement — Fulfillment handles backorders
07Further Notes
  • Price snapshotting: Catalog is source of truth for Item prices. We snapshot the price into each OrderLine at order time so a future price change doesn't retroactively alter an existing Order.
  • Telemetry: every endpoint emits a structured log with customer_id, order_id, idempotency_hit, latency. Grafana dashboard surfaces idempotency hit rate as a healthcheck metric.
