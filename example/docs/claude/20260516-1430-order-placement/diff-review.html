01Executive Summary

What landed

A customer-facing order placement endpoint with idempotency-keyed retry deduplication (Redis, 24h TTL), persistent order history with cursor pagination, customer-initiated cancellation of pending Orders, and at-least-once event emission (OrderPlaced, OrderCanceled) consumed by Fulfillment and Billing.

The Commerce context's domain language was crystallized in CONTEXT.md: Customer, Cart, Order, OrderLine, IdempotencyKey, OrderStatus, OrderPlaced, OrderCanceled. Three ADRs ratify the load-bearing decisions: idempotency-key storage (Redis vs Postgres), the linear order state machine (no refunds in Commerce), and at-least-once event delivery.

Verification clean: tsc, lint, full test suite, build all green. code-reviewer found 2 HIGH issues — both fixed before merge. doc-updater refreshed the events catalog. fact-check confirmed PRD and tasks align with the implementation.

05Code Review Findings

The Good

  • OrderService.place_order reads like a specification — interface mirrors the user story
  • Transactional outbox correctly emits the event AFTER row commit (verified with fault-injection test)
  • IdempotencyStore degrades gracefully on Redis outage — endpoint stays available
  • State-machine invariants enforced in one place (OrderService) — HTTP layer is genuinely thin
  • Test names use CONTEXT.md vocabulary throughout (Customer, Order, OrderLine, IdempotencyKey)

Fixed Before Merge

  • HIGH: initial code-reviewer pass flagged a missing authorization check on cancel — was relying on the order-history check rather than re-verifying. Fixed: added explicit check in OrderService.cancel_order
  • HIGH: log redactor wasn't scrubbing the IdempotencyKey itself — could leak a client-chosen secret. Fixed: added IdempotencyKey to the redactor's allowlist
  • MEDIUM: originally used SELECT FOR UPDATE in idempotency check before discovering Redis was a better fit. Reverted before merge per ADR-0001

Tracked Follow-ups

  • Cursor-pagination encoding uses base64(json) — works but should be HMAC-signed before public API exposure. Tracked in INGEST-4471
  • Grafana alert threshold (50% hit rate for 10min) is a placeholder — real threshold needs a week of production data to tune
  • Fulfillment's plan for handling OrderCanceled arriving before OrderPlaced is documented but not yet tested end-to-end across services
06Decision Log
  • Redis over Postgres for idempotency-key storage. Native TTL, ~1ms hits, no cleanup job needed. Outage degrades gracefully. (ADR-0001)
  • Linear state machine with no back-transitions. Commerce knows nothing about Refunds — that's a Billing concern. Explicit boundary decision to keep our invariants tractable. (ADR-0002)
  • At-least-once delivery with idempotent consumers. Exactly-once across process boundaries is a distributed-systems fairytale; rejected 2PC and at-most-once. (ADR-0003)
  • Transactional outbox for publishing — chosen over publishing in the same DB transaction. Avoids tight coupling to the broker's transaction guarantees while still guaranteeing event emission only AFTER row commit.
  • Per-Customer idempotency scoping — two Customers may legitimately use the same opaque key string. Scoping on (customer_id, key) avoids false collisions across tenants.
  • Cancel-from-confirmed returns 409, not 403 — the cancel resource exists but is in a state that doesn't permit the transition. Error code ORDER_NOT_CANCELLABLE lets the UI translate to "contact support."
