02Slices
1Customer can place an Order (happy path)
AFKunblockedstories 1, 8, 10, 12
A Customer with a valid Cart and an Idempotency-Key header can POST to the order placement endpoint and receive a 201 with the new Order ID. The Order persists with pending status; OrderPlaced is emitted AFTER the row commits.
Acceptance criteria
  • Returns 201 with { order_id, status: "pending" } for a valid request
  • Persists Order row with pending status before the response returns
  • Persists OrderLine rows with frozen prices snapshotted from Catalog
  • Emits OrderPlaced AFTER the Order row commits — never before
  • OrderPlaced payload: event_id (ULID), order_id, customer_id, total, occurred_at
  • Returns 400 for an empty Cart
  • Returns 400 for a missing Idempotency-Key header
2Idempotency-Key dedupes retries
AFKblocked by 1stories 2, 3, 13
A retry with the same Idempotency-Key returns the original Order ID — no duplicate row, no duplicate event. Redis-backed, 24h TTL, per-Customer scoping. Redis outage degrades to "duplicates possible" rather than blocking checkout.
Acceptance criteria
  • Same (customer_id, idempotency_key) → same order_id as the first request
  • Second request does NOT persist a duplicate Order row
  • Second request does NOT emit a second OrderPlaced
  • After 24 hours, same key creates a new Order (TTL works)
  • Different Customers using the same key get distinct Orders (per-Customer scoping)
  • Redis unreachable → endpoint still returns 201; warning logged; metric incremented
  • Idempotency hit rate exposed as a Prometheus counter
3Customer can see their Order history
AFKblocked by 1stories 4, 7
GET endpoint returns the requesting Customer's Orders sorted by created_at descending, cursor-paginated. A Customer cannot read another Customer's Orders.
Acceptance criteria
  • Returns 200 with the Customer's Orders for an authenticated request
  • Orders sorted by created_at descending
  • Each entry includes order_id, status, total, created_at, order_lines[]
  • Cursor pagination: ?cursor=<opaque>&limit=<n>
  • Returns 200 with empty array for a Customer with no Orders (NOT 404)
  • Returns 403 when a Customer tries to read another Customer's Orders by ID
  • N+1 queries on OrderLines avoided (single join or batched fetch)
4Customer can cancel a pending Order
AFKblocked by 1stories 5, 6, 9
POST to cancel transitions pending → canceled and emits OrderCanceled. Cancel on confirmed returns 409 with code ORDER_NOT_CANCELLABLE (per ADR-0002, refunds live in Billing).
Acceptance criteria
  • Returns 200 with { status: "canceled" } from pending
  • Persists status change before response
  • Emits OrderCanceled with same payload shape as OrderPlaced
  • Returns 409 with code ORDER_NOT_CANCELLABLE on confirmed Order
  • Returns 409 on an already-canceled Order (idempotency on the resource)
  • Returns 403 when one Customer tries to cancel another's Order
  • No confirmed → canceled transition possible (linear state machine, ADR-0002)
5Downstream consumer contract sign-off
HITLblocked by 1, 4stories 8, 9, 10, 11
Design-review session with Fulfillment and Billing teams to ratify event payload contracts, confirm at-least-once delivery expectations (ADR-0003), and align on event_id dedup in each consumer. Publish agreed contracts in docs/events/commerce.md.
Acceptance criteria
  • Meeting held with Fulfillment lead and Billing lead
  • Event payload schemas published in docs/events/commerce.md
  • Both consumers confirm they will dedupe on event_id
  • Both consumers confirm retry-forever on transient processing failures (no DLQ for transient errors)
  • Edge case documented: what does Fulfillment do if OrderCanceled arrives before OrderPlaced was processed?
6Telemetry and observability
AFKblocked by 1-4story 13
Structured logs and Prometheus metrics on every Commerce endpoint. Grafana dashboard updated. Runbook entry for the idempotency-hit-rate alarm (which catches a Redis outage).
Acceptance criteria
  • Every Commerce endpoint emits a structured log on success and failure
  • PII (Customer email, address) redacted per the security rule
  • Idempotency hit rate counter increments on a hit, not on a miss
  • Event-publish failure metric increments on broker outage (verified via fault injection)
  • Grafana panel for idempotency hit rate, alarming below 50% for 10 minutes
  • Runbook entry: "Commerce idempotency hit rate dropped" → check Redis health
