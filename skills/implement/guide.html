Vertical-slice TDD execution of an approved tasks.md. One test, one implementation, repeat. Coach mode lets the user write the code; AI writes one test at a time. Inputs: spec.md + tasks.md.

02Good Tests vs Bad Tests

Good tests

Specifications written through the public interface.

  • Describe what, not how
  • Use vocabulary from CONTEXT.md
  • Survive an internal refactor with zero changes
  • Exercise real code paths end-to-end
  • Pin behavior, not data structures

Bad tests

Coupled to implementation details. Warning sign: they break when you rename an internal function despite identical behavior.

  • Mock internal collaborators
  • Test private methods
  • Verify through side channels (DB queries instead of the API)
  • Check signatures and shapes instead of behavior
  • Pass when behavior breaks, fail when it doesn't
03Vertical, Never Horizontal

WRONG — horizontal:

RED: test1, test2, test3, test4, test5 GREEN: impl1, impl2, impl3, impl4, impl5

Tests written in batches test imagined behavior. They check the shape of things — signatures, data structures — instead of user-facing behavior. They become insensitive to real changes.

RIGHT — vertical:

RED→GREEN: test1 → impl1 RED→GREEN: test2 → impl2 RED→GREEN: test3 → impl3 (refactor between cycles when GREEN)

Each test responds to what you learned from the previous cycle. Because you just wrote the code, you know exactly what behavior matters and how to verify it.

Never refactor while RED. Get to GREEN first. Refactoring with failing tests means you can't tell whether you're changing behavior accidentally.
Never queue tests in coach mode. Only the test you're currently solving exists. Don't preview the next one — the user should implement against the current test without anticipating.

06Never Commits
Neither mode runs git commit. No git add, no git commit, no git push. The user reviews the final state and commits when ready.
07Per-Slice Checklist

Before claiming a slice done

  • Every test describes behavior, not implementation
  • Every test uses the public interface only
  • Every test would survive an internal refactor
  • Code is minimal for the tests it satisfies
  • No speculative features beyond the slice's acceptance criteria
  • Test names use CONTEXT.md vocabulary

Handling deviations

  • Minor issue: fix and continue; note the deviation in the slice body
  • Can't implement as written: STOP and tell the user; wait for guidance
  • Test failure during refactor: revert the refactor step; refactoring must not change behavior
  • User reverts work: start fresh with the narrowed scope; don't patch a bad approach
