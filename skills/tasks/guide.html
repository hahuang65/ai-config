/tasks

Break an approved PRD into vertical-slice tracer bullets. Each slice cuts through every layer end-to-end and is demoable on its own. Reviewed and refined locally. Based on Matt Pocock's to-issues.

01Place in the Pipeline

Phase 3 of /build. Inputs: prd.md, CONTEXT.md, ADRs. Outputs: tasks.md + tasks.html.

/build "feature" ├── Phase 1: /grill ├── Phase 2: /prd ├── Phase 3: /tasks ← YOU ARE HERE └── Phase 4: /implement (or /implement-coach)
02Vertical, Never Horizontal

Vertical slice (right)

"Customer can place an Order via the API and see it in their order history."

  • Touches schema, API, business logic, UI, tests
  • Demoable end-to-end on its own
  • Tracer bullet — proves the path through every layer

Horizontal slice (rejected)

"Set up the Order database schema and migrations."

  • Touches only one layer
  • Not demoable in isolation
  • System is in a broken/invisible state until later slices land
  • If a slice looks like this, split or reframe it
Many thin slices beat few thick ones. If a slice looks fat, split it. Each slice's value is in being independently grabbable and demoable.
03HITL vs AFK
TypeDefinitionBias
AFKAway-from-keyboard. Can be implemented and merged without human interaction.Prefer this — most slices should be AFK
HITLHuman-in-the-loop. Requires interaction — an architectural decision, a design review, a credential rotation.Reserved for genuine judgment calls
04Slice Anatomy
## Slice 1: Customer can place an Order **Type:** AFK **Blocked by:** None — can start immediately **User stories covered:** 1, 2, 3 (from the PRD) **Test surface:** POST /orders public API behavior ### What to build End-to-end behavior: a Customer hits POST /orders with a valid cart, the Order is persisted, OrderPlaced is emitted, and the response includes the new Order ID. ### Acceptance criteria - [ ] Returns 201 with order ID for a valid request - [ ] Returns 400 for an empty cart - [ ] Emits OrderPlaced event with the correct payload - [ ] Persists Order with status `pending`

Avoid file paths and code snippets in slice bodies — they go stale before the slice is picked up. The Test surface line names the stable public interface or observable behavior, not a spec file. Same narrow exception as the PRD: decision-rich snippets (state machines, reducers, schemas) may be inlined when prose can't carry the precision.

05Process
StepAction
1. Gather contextRead prd.md, CONTEXT.md, relevant ADRs. Explore code if not yet done.
2. Draft slicesVertical only. Each slice cuts through every layer. Carry forward the PRD's public-interface test surface. Mark HITL/AFK. Order by dependency (blockers first).
3. Write tasks.mdOne slice per section, with Type/Blocked-by/User-stories-covered/Test-surface headers and an acceptance-criteria checklist.
4. Generate tasks.htmlVia the visual-explainer skill; open it in the browser. Emphasizes the dependency graph, HITL/AFK split, and user-story coverage.
5. ReviewPresent the numbered list; ask granularity / dependencies / HITL-AFK / coverage (or accept // annotations in tasks.md). Address feedback, re-present. Work from tasks.md — the visual is not regenerated mid-review.
6. FinalizeOn confirmation, regenerate tasks.html once if it changed, report counts, advance to implementation.
06Completion

On the user's confirmation, regenerate tasks.html once if it changed, report the counts, and advance to Phase 4 (/implement or /implement-coach) — any go-ahead works; no exact phrase needed.
