/prd

Synthesize a Product Requirements Document from the current conversation (typically a /grill session). User stories + decisions, no code snippets, no file paths — durable spec. Based on Matt Pocock's to-prd.

01Place in the Pipeline

Phase 2 of /build. Inputs: CONTEXT.md, ADRs, prior conversation. Outputs: prd.md + prd.html.

/build "feature" ├── Phase 1: /grill ├── Phase 2: /prd ← YOU ARE HERE ├── Phase 3: /tasks └── Phase 4: /implement (or /implement-coach)
02Synthesize, Don't Re-Interview
Critical: grilling was the design phase. /prd transcribes its outcome — it does NOT re-interview the user. If essential information is genuinely missing, ask one targeted question. But don't re-run the grill session.

The one micro-checkpoint that is in this phase: after sketching the major modules, confirm them with the user and ask which to test. That informs the Testing Decisions section.

03PRD Structure
SectionContent
Problem StatementThe problem from the user's perspective
SolutionThe solution from the user's perspective
User StoriesExtensive numbered list of As a <actor>, I want <feature>, so that <benefit>
Implementation DecisionsModules built/modified, interfaces, schema, contracts, references to ADRs
Testing DecisionsWhat makes a good test here, which modules will be tested, prior art
Out of ScopeThings deliberately excluded
Further NotesAnything else worth recording
04Forbidden in the PRD

No code snippets

Code rots fast — what's correct today won't be by the time the task is picked up. Code lives in tasks.md (and even there, only sparingly).

No file paths

Same reason. Files get renamed, moved, split. The PRD is durable; specific paths aren't. Reference modules by name (from CONTEXT.md), not by location.

Narrow exception: if grilling produced a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape), inline it within the relevant decision and note where it came from. Trim to the decision-rich parts — not a working demo, just the important bits.
05Deep Modules

When sketching modules, actively look for deep modules over shallow ones.

Deep

Small interface, deep implementation. Encapsulates significant functionality behind a simple, testable API that rarely changes.

Shallow

Interface nearly as wide as the implementation. Provides little encapsulation. A pass-through. Refactor target.

Deep modules are testable in isolation, their tests survive refactors, and they hide complexity from callers. The PRD's module sketch should bias toward these.

06Annotation Cycle

After writing prd.md and generating prd.html, STOP and wait. User adds // comments anywhere in the markdown:

## User Stories // also need: "as an admin, I want to revoke sessions" 1. As a customer, I want to see my balance... // remove this — it's out of scope per the grill session 7. As a customer, I want to export to CSV... // this should reference ADR-0003, not 0002

For each annotation, the agent addresses it, updates prd.md, and removes the // comment — working from the markdown. The cycle repeats until the user is satisfied; prd.html is regenerated once at the end if the markdown changed, not per annotation.

07Visual Sync Guarantee
Build once, then leave it: prd.html is generated and opened when prd.md is first written. It is NOT regenerated during the review — the markdown is the source of truth, so the open visual may lag — then regenerated once before moving to /tasks if the markdown changed.

Visual generation uses /generate-visual-plan. The HTML's <title> and <h1> must say "PRD", not "Plan".

08Completion

On the user's confirmation, regenerate prd.html once if the markdown changed, tell the user, and advance to /tasks — any go-ahead works; no exact phrase needed.
