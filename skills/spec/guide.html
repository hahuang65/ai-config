/spec

Synthesize a feature spec from the current conversation (typically a /grill session). User stories + decisions, no code snippets, no file paths — durable. Based on Matt Pocock's to-prd.

01Place in the Pipeline

Phase 2 of /build. Inputs: root or mapped context files, ADRs, and prior conversation. Output: canonical specs.html.

/build "feature" ├── Phase 1: /grill ├── Phase 2: /spec ← YOU ARE HERE ├── Phase 3: /todo └── Phase 4: /code (or /coach)
02Synthesize, Don't Re-Interview
Critical: grilling was the design phase. /spec transcribes its outcome — it does NOT re-interview the user. If essential information is genuinely missing, ask one targeted question. But don't re-run the grill session.

The one micro-checkpoint that is in this phase: after sketching the major modules, propose their test surfaces yourself and ask the user only to correct module boundaries or public-interface seams. Don't ask which modules need tests — deep modules answer that.

Domain consultants: when the feature touches REST endpoints, the module sketch consults the api-designer agent for the endpoint contract; when it adds or restructures UI, the frontend-architect agent for component boundaries and state ownership. Skipped silently for features that touch neither.

04Forbidden in the spec

No code snippets

Code rots fast — what's correct today may not be when a task is picked up. Keep implementation code out of canonical review artifacts.

No file paths

Same reason. Files get renamed, moved, split. The spec is durable; specific paths aren't. Reference modules by name from the applicable context files, not by location.

Narrow exception: if grilling produced a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape), inline it within the relevant decision and note where it came from. Trim to the decision-rich parts — not a working demo, just the important bits.
05Deep Modules

When sketching modules, actively look for deep modules over shallow ones.

Deep

Small interface, deep implementation. Encapsulates significant functionality behind a simple, testable API that rarely changes.

Shallow

Interface nearly as wide as the implementation. Provides little encapsulation. A pass-through. Refactor target.

Deep modules are testable through their stable public interface, their tests survive refactors, and they hide complexity from callers. The spec's module sketch should bias toward these and record the test seam for each module.

06Browser Review Loop

Write canonical specs.html in the project's ubiquitous language from the applicable context files, define any unavoidable unfamiliar term, then open it through review-artifact. The user can annotate exact elements or selected text and send a coherent feedback batch.

open specs.html → annotate → foreground poll ↑ ↓ └──── edit same HTML ← feedback

Address every note in the visible semantic HTML, save it, and let the existing browser session live-reload before polling again with an agent reply.

07Live Sync Guarantee
One reviewed source: specs.html is both the durable spec and the review surface. There is no Markdown companion and no intentionally stale visual.

Use semantic headings and stable IDs. The HTML's <title> and <h1> must say "Spec", not "Plan".

08Completion

An explicit approval event advances to /todo. Ending or closing review is not approval; browser failure uses the chat fallback.
