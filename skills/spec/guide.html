01 · Inputs

Transcribe decisions; do not rediscover them

  • Read selected context documentation, recent decision records, the conversation, and the affected code.
  • Read approved mockups.html when present as Authoritative intent.
  • For standalone use, run mockup first when relevant UI has no approved artifact.
  • Ask one targeted question only when essential information is missing.

Sketch major modules and propose each public-interface test surface. Ask the user only to correct boundaries or seams.

Consult api-designer for changed REST contracts and frontend-architect for added or restructured UI. Skip them when their domain is not involved.

03 · Durability rules

Prefer stable concepts over implementation detail

No file paths

Name modules and interfaces. Paths move and become stale.

No routine code snippets

Describe decisions in prose. Include only a small decision-rich shape when prose is materially less precise.

Prefer deep modules. A small stable interface should hide meaningful implementation complexity and provide a durable test seam.

04 · Review

Edit one live source

Write semantic specs.html with the title <feature title> - Spec. Open it through review-artifact, apply every feedback batch to the same file, and continue until explicit approval.

  1. Material UI feedback return path: Pause the Spec approval review.
  2. Update the changed mockups.html, then run mockup through review-artifact until explicit approval.
  3. Synchronize specs.html with the approved mockup and resume the Spec approval review.
  4. Continue to Tasks only after explicit Spec approval; renew any prior Spec approval invalidated by the UI change.

The HTML is both the durable spec and the review surface. There is no Markdown companion.

05 · Completion

Approval advances immediately

Explicit browser approval or chat-fallback confirmation clears Spec→Tasks and starts todo. Closing or ending review is not approval.
