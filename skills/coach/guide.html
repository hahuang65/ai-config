01 · Ownership

The user writes implementation

AI owns

  • Interface confirmation.
  • One current failing test.
  • Focused verification and debugging guidance.
  • Task status updates.

User owns

  • Implementation code.
  • Source and test repairs.
  • Whether to hand control to code.
  • Higher-risk hygiene choices.
02 · Waiting is the deliverable

Yield after every test

  • Remain silent until the user signals readiness to check.
  • Ignore incomplete-todo reminders; open criteria belong in tasks.html.
  • Never poll implementation files to infer silent progress.
  • Never switch to code without explicit permission.
  • If the switch was offered once, do not offer it again.

Silence is not consent to take over. A coach turn is complete when the failing test and handoff are complete.

03 · Per-slice loop

One criterion at a time

  1. Present the public interface from the Task Test surface and Spec Testing Decisions. Wait for confirmation.
  2. Write one end-to-end tracer test and run it to prove RED for the correct reason.
  3. Show the test and failure, then wait.
  4. When the user signals ready, run only the relevant test. Guide debugging without writing the fix.
  5. After GREEN, write the next criterion test. Never queue or preview future tests.
  6. Refactor together only while GREEN.
  7. Mark visible and data-status completion in tasks.html.

One-test cadence prevents tests from describing imagined behavior before the implementation teaches the next useful case.

04 · Intent changes

Keep approved UI synchronized

Material UI redesign: stop the affected slice, update mockups.html through review-artifact, synchronize specs.html and tasks.html, renew invalidated approvals, then resume only after intent is synchronized; the user remains the source-code implementer.

05 · Completion

Verify without taking ownership

  1. Guide type check, lint, the full test suite, and build until clean.
  2. Run the refactorer in hygiene mode. Apply SAFE mechanical cleanup; let the user decide CAREFUL or RISKY candidates.
  3. Report final commands, scopes, outcomes, and completed slices.

Inside build: Review change is mandatory and keeps source and test fixes user-owned. Standalone: offer optional refactor and review-code next steps.

06 · Git boundary

No staging or delivery

Coach does not stage, commit, push, or deliver.
