/todo

Break an approved spec into vertical-slice tracer bullets. Each slice cuts through every layer end-to-end and is demoable on its own. Reviewed and refined locally. Based on Matt Pocock's to-issues.

01Place in the Pipeline

Phase 3 of /build. Inputs: canonical specs.html, CONTEXT.md, ADRs. Output: canonical tasks.html.

/build "feature" ├── Phase 1: /grill ├── Phase 2: /spec ├── Phase 3: /todo ← YOU ARE HERE └── Phase 4: /code (or /coach)
02Vertical, Never Horizontal

Vertical slice (right)

"Customer can place an Order via the API and see it in their order history."

  • Touches schema, API, business logic, UI, tests
  • Demoable end-to-end on its own
  • Tracer bullet — proves the path through every layer

Horizontal slice (rejected)

"Set up the Order database schema and migrations."

  • Touches only one layer
  • Not demoable in isolation
  • System is in a broken/invisible state until later slices land
  • If a slice looks like this, split or reframe it
Many thin slices beat few thick ones. If a slice looks fat, split it. Each slice's value is in being independently grabbable and demoable.
03HITL vs AFK
TypeDefinitionBias
AFKAway-from-keyboard. Can be implemented and merged without human interaction.Prefer this — most slices should be AFK
HITLHuman-in-the-loop. Requires interaction — an architectural decision, a design review, a credential rotation.Reserved for genuine judgment calls
04Slice Anatomy
<article data-slice-id="1" data-status="pending" data-mode="AFK" data-dependencies="" data-stories="1,2,3"> Customer can place an Order Blocked by: None Test surface: POST /orders public behavior What to build: complete Order placement path Acceptance criteria: data-criterion-id="1.1" data-status="pending" data-criterion-id="1.2" data-status="pending" </article>

Avoid file paths and code snippets in slice bodies — they go stale before the slice is picked up. The Test surface line names the stable public interface or observable behavior, not a spec file. Same narrow exception as the spec: decision-rich snippets (state machines, reducers, schemas) may be inlined when prose can't carry the precision.

05Process
StepAction
1. Gather contextRead canonical specs.html, CONTEXT.md, relevant ADRs. Explore code if not yet done.
2. Draft slicesVertical only. Each slice cuts through every layer. Carry forward the spec's public-interface test surface. Mark HITL/AFK. Order by dependency.
3. Write tasks.htmlUse plain project language for visible content and semantic slice containers with stable identity, status, dependency, mode, story, test-surface, and acceptance-criterion metadata. Show “can run unattended” / “needs you present” as the main labels and AFK/HITL as secondary metadata.
4. ReviewOpen through review-artifact. Ask about granularity, dependencies, HITL/AFK, and coverage.
5. IterateAddress every browser annotation or message in the same HTML and let the open review live-reload.
6. FinalizeExplicit approval finalizes the artifact; report counts and advance to implementation.
06Completion

An explicit browser approval or chat-fallback confirmation finalizes tasks.html. Ending review is not approval. Report the counts and advance to Phase 4 (/code or /coach).
