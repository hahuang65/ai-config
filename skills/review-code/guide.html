/review-code

Surface architectural friction and propose deepening opportunities — refactors that turn shallow modules into deep ones. The aim is testability and AI-navigability.

01Shallow vs Deep

Shallow

Interface
Impl

Interface nearly as complex as the implementation. Low leverage; the module isn't hiding anything from its callers. The deletion test: removing it doesn't concentrate complexity — it just moves it.

Deep

Interface
Impl

A lot of behaviour behind a small interface. High leverage; tests hit one surface to exercise many call paths. The deletion test: removing it scatters complexity across N callers.

The interface is the test surface. Callers and tests cross the same seam. If you need to test past the interface to feel confident, the module is probably the wrong shape — and a candidate for this skill.
02Glossary (Use Exactly)

Don't substitute "component," "service," "API," or "boundary." Consistent language is the whole point. Full definitions in language.md.

Module

Anything with an interface and an implementation. Scale-agnostic: function, class, package, slice.

Interface

Everything a caller must know: types, invariants, error modes, ordering, config — not just the signature.

Implementation

The code inside the module. Distinct from adapter.

Depth

Leverage at the interface. Behaviour per unit of interface a caller has to learn.

Seam (Michael Feathers)

Where behaviour can be altered without editing in place. Where an interface lives. Use this, not "boundary."

Adapter

A concrete thing that satisfies an interface at a seam. Describes role, not substance.

Leverage

What callers get from depth: more capability per unit of interface learned.

Locality

What maintainers get from depth: change, bugs, knowledge concentrate in one place.

03Key Principles

The deletion test

Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep.

Depth is a property of the interface

Not the implementation. A deep module can be internally composed of small, swappable parts — they just aren't part of its interface.

One adapter = hypothetical seam

Two adapters = real seam. Don't introduce a port unless something actually varies across it (typically production + test).

Replace, don't layer

Old unit tests on shallow modules become waste once tests at the deepened interface exist. Delete them.

06Place in the Pipeline
/review-code is the final phase of the /build pipeline (diff-scoped, where the user decides commit-or-iterate) and a standalone tool invoked when you feel architectural friction — a new module turned out shallower than expected, a sub-system grew hard to navigate, or a grilling session keeps tripping over the same friction. For surface-level cleanup right after implementation (dead code, unused imports, simple reuse), the refactorer hygiene sweep already runs inside /code. Discovery runs in the architecture-reviewer agent; this skill wraps it — scope detection (pipeline: ONLY the feature's changes · standalone: entire codebase, or the area named by arguments), HTML rendering, and the grilling loop.
