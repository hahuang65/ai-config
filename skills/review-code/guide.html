Standalone architecture exploration

/review-code

Find architectural friction, show deepening opportunities, and grill one selected candidate. Discovery and source-code handling are read-only.

01 · Scope

Use it for structural questions

No arguments

Review the entire codebase as an architectural health check.

Named area

Review only the supplied module, subsystem, files, or directory.

review-code is optional and never part of build. Review change owns final change validation; the refactorer hygiene sweep owns surface cleanup.

02 · Workflow

Discover, report, grill, hand off

StepAction
1 · DiscoverRead context files and ADRs, then run the read-only architecture-reviewer agent over the resolved scope.
2 · ReportWrite a disposable HTML report with architectural candidates, before/after diagrams, recommendation strength, and a top recommendation.
3 · DecideOpen it through review-artifact in Explore mode. Annotations or messages select a candidate; approval means no candidate will be explored now.
4 · GrillResolve constraints, dependencies, interface shape, and surviving tests. Invoke model-domain when language or durable decisions change; it may update context files or qualifying ADRs.
5 · Hand offRoute behavior-preserving work to refactor and interface-changing work to build. This skill never edits code.
03 · Core visual

Shallow versus deep

Shallow module

The interface is nearly as complex as the implementation. Deleting it mostly moves complexity to callers.

interface ████████
impl      █████████

Deep module

A small interface hides meaningful complexity. Deleting it scatters that complexity across callers.

interface ██
impl      █████████

The interface is the test surface. If tests must reach past it for confidence, the module may have the wrong shape.

04 · Analysis vocabulary

Reason precisely; report plainly

During analysis, use module, interface, implementation, depth, seam, adapter, leverage, and locality consistently.

In the reviewer-facing report, translate those terms into the project's ubiquitous language and familiar technical terms unless the project already uses them.

  • Deletion test: if removing a module scatters complexity across callers, it earns its interface.
  • Real seam: variation exists, usually through two or more adapters.
  • Locality: related change, bugs, and knowledge stay together.
05 · Recommendations

Show confidence without pretending certainty

Strong

Clear friction, clear seam, high expected leverage.

Worth exploring

Plausible benefit with trade-offs for grilling.

Speculative

Useful context, but not enough present friction to act.

When interface alternatives are needed, use parallel subagents to produce at least three meaningfully different designs before comparison.
