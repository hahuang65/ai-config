Conditional design workflow

/mockup

Review material end-user UI before the Spec fixes its intent. One canonical artifact carries the selected direction into later phases.

01 · Relevance

Use visual judgment where it adds value

Run

New or materially changed layouts, flows, information hierarchy, responsive behavior, or visual states in browser or terminal UI.

Skip

Internal work, exact copy replacement, mechanical styling repair, or small defects with no design decision.

When no relevant UI exists, post-grill chat confirmation clears the same Design→Spec gate. Mockup does not add another gate.

02 · Output

One durable mockups.html

Reuse a supplied path under docs/features/. Otherwise derive docs/features/<YYYYMMDD-HHMM>-<slug>/ from the feature description and create it before writing.

  • Use realistic content and identify affected surfaces.
  • Show important loading, empty, error, success, disabled, and permission states.
  • Demonstrate responsive and accessibility intent.
  • Update the same live artifact after every feedback batch.
03 · Design count

One recommended design by default

Show two or three alternatives only when grilling leaves a real structural fork. Alternatives must differ in layout, information hierarchy, or primary action—not only color or copy.

Authoritative

Information hierarchy, interaction behavior, important states, responsive intent, and accessibility behavior.

Directional by default

Exact dimensions and decorative styling, unless explicitly marked as required.

04 · Approval

Settle selection first

  1. Use a review-artifact feedback or decision interaction to settle the selection. Do not request approval while alternatives remain unresolved.
  2. After the selection settles, record the selected design, rationale, and rejected alternatives in the same mockups.html.
  3. Only then start or resume the approval review and apply its feedback to the same live artifact.

Explicit approval is the Design→Spec signal. Ending or closing review is not approval.
