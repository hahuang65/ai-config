Conditional design workflow

/mockup

Show a material end-user interface before the Spec fixes its intent. Review one canonical HTML artifact, settle the visual direction, and carry that decision into implementation.

01 · Place in Build

One Design→Spec gate, two paths

GrillResolve product and domain decisions.
Mockup when relevantApproval clears Design→Spec for material UI.
SpecSummarize and link the selected design.
Tasks onwardRead the mockup as Authoritative intent.

When no relevant UI exists, post-grill chat confirmation clears the same Design→Spec gate. The conditional mockup does not add a fifth approval boundary.

02 · Relevance

Use visual judgment only where it adds value

Run

New or materially changed browser or terminal layouts, interaction flows, information hierarchy, responsive behavior, or visual states.

Skip

Internal work, exact copy replacement, mechanical styling repair, or a small defect fix with no design decision.

03 · Canonical output

One durable mockups.html

  • Use realistic content and identify every affected surface.
  • Show important loading, empty, error, success, disabled, and permission states when relevant.
  • Demonstrate responsive intent and accessibility behavior.
  • Keep the artifact semantic, self-contained, and safe to review locally.
  • Update the same live artifact after every feedback batch.
04 · Design count

Recommend first; branch only for a real fork

Present one recommended design by default. Before approval, visibly mark one recommended design as selected and state its rationale.

Add two or three structurally different alternatives only when grilling leaves an unresolved visual decision. Differences must change layout, information hierarchy, or the primary action rather than only color or copy.

05 · Authority

Bind behavior, not every pixel

Authoritative

Information hierarchy, interaction behavior, important states, responsive intent, and accessibility behavior.

Directional by default

Exact dimensions and decorative styling unless the artifact explicitly marks them as required.

06 · Review completion

Settle the design before approval

  1. When alternatives remain unresolved, use a review-artifact feedback or decision interaction to settle the selection. Do not request approval yet.
  2. After the selection settles, update the same mockups.html with the selected design, its rationale, and rejected alternatives. Show “None” when no alternative was rejected.
  3. Only then start or resume the approval review and apply its feedback to the same live artifact.

Explicit approval is the Design→Spec signal. Ending or closing review is not approval.
