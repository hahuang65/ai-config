/prototype

Throwaway code that answers one question. The question decides the shape: a TUI for logic/state, or a runnable UI grounded in the host application. A canonical mockup can settle end-user design before or after the experiment.

Logic — TUI UI — Host app
01Pick a Branch

Logic Prototype

Tiny interactive terminal app. The user presses keys; state changes.

"Does this state machine handle X then Y?"

"Can this data model represent the case where…?"

"What should the API surface look like?"

  • Isolate logic in a portable module — pure reducer, state machine, or pure functions
  • TUI is throwaway; validated portable logic needs production tests before it is absorbed
  • Re-render the full frame on every action (no scrollback)
  • Keyboard shortcuts shown at bottom

UI Prototype

Runnable throwaway UI inside the host application when standalone HTML cannot answer the question.

"Does the selected design work with real dashboard density?"

"Can this interaction use the application's actual state flow?"

"Does integration with this host page expose a design problem?"

  • Default to the existing host page — preserve real data, navigation, and density
  • Use a throwaway route only when no existing page makes sense
  • Use variants only when the integration question itself requires comparison
  • Hide all prototype controls in production builds; never ship them
Picking wrong wastes the whole prototype. A visual-design question that standalone HTML can answer belongs to /mockup. Use a UI prototype only when the host application, integration, real data density, or state behavior is part of the question.
First / Last / Skip: run /mockup first when end-user design is the subject or an imperative prerequisite; leave it until last when UI only presents logic, data exploration, manual processing, or state; skip it when no UI design question exists.
02Rules Both Branches Share
RuleWhat it means
Throwaway from day oneCode is named and located so a casual reader can tell it's not production
One command to runWhatever the project's task runner supports — pnpm, python, bun, etc.
No persistence by defaultState lives in memory unless the question is specifically about persistence
Skip the polishNo tests, no abstractions, no error handling beyond keeping it runnable
Surface the stateAfter every action, and after every variant switch when variants exist, the user can see what changed
Delete or absorb when doneThe shell goes away; validated portable logic is rewritten or absorbed under production constraints and tests
03Place in the Pipeline
Prototyping lives outside the /build pipeline. It usually surfaces when integration, real data density, or state behavior cannot be judged in mockups.html or conversation. Pair with /handoff when the prototype needs its own focused session, and let the prototype consume an approved mockup without promoting either artifact's throwaway code.
04The Answer Is What You Keep

A prototype produces two things: a runnable artifact (throwaway) and an answer (durable). The answer goes into a commit message, an ADR, an issue, or a NOTES.md next to the prototype — along with the question it was answering. Then the prototype shell is deleted.

If the answer changes the ubiquitous language or crystallises a durable decision, invoke /model-domain to update context files or record a qualifying ADR.

05Anti-Patterns
Adding testsA prototype that needs tests is no longer a prototype.
Wiring to the real DBUse in-memory unless the question is about persistence.
GeneralisingNo "what if we wanted X later." One question, one prototype.
Blurring logic and TUIIf the reducer references console.log, it's not portable anymore.
Shipping the shellThe TUI / variant switcher is for the question. Rewrite when folding in.
Variants differing only in colourThat's a tweak. Real variants disagree about structure.
