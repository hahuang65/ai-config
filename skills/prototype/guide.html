01 · Choose the artifact

The question decides the branch

Logic prototype

Use a small interactive terminal shell for state machines, reducers, data models, or API behavior.

  • Keep logic portable and separate from the shell.
  • Render complete state after each action.
  • Show keyboard controls.

UI prototype

Use the real host application when integration, real data density, or actual state behavior is part of the question.

  • Prefer an existing page and real application context.
  • Use a throwaway route only when necessary.
  • Never ship prototype controls.

Visual-only design belongs to mockup. A runnable UI is justified only when standalone HTML cannot answer the question.

02 · Mockup order

First, Last, or Skip

First / Last / Skip: run mockup first when end-user design is the subject or prerequisite; leave it until last when UI only presents logic, data, or state; skip it when no UI design question exists.

03 · Constraints

Make disposal obvious

  • Name and locate the code so readers know it is not production.
  • Provide one command to run.
  • Keep state in memory unless persistence is the question.
  • Skip tests, abstractions, and polish beyond what keeps it runnable.
  • Show relevant state after every action or variant switch.
  • Delete the shell or rewrite validated portable logic under production constraints and tests.

Use variants only when the question requires different behavior or integration strategies. Decorative-only variants do not test a meaningful hypothesis.

04 · Pipeline boundary

Experiment outside build

Prototype runs outside the main pipeline. Use handoff when the experiment needs its own focused session, then return the answer to the owning workflow.

05 · Keep the answer

Discard the shell

Record the question and result in an issue, commit message, ADR, or short note. Then remove the prototype.

If the answer changes the ubiquitous language or creates a qualifying durable decision, invoke model-domain to update the correct context files or ADR.
