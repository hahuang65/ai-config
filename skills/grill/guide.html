/grill

Interactive domain-modeling session. Interview the user one question at a time, sharpen terminology, capture decisions inline — updating CONTEXT.md and docs/adr/ as the conversation progresses. Based on Matt Pocock's grill-with-docs.

01Place in the Pipeline

Phase 1 of /build. The grilling session is the design phase. Phase 2 (/specs) just transcribes its outcome — it does NOT re-interview.

/build "feature" ├── Phase 1: /grill ← YOU ARE HERE ├── Phase 2: /specs ├── Phase 3: /tasks └── Phase 4: /implement (or /implement-coach)
02What It Produces

CONTEXT.md (repo root)

Shared domain glossary. Long-lived; accretes across every /build run. Definitions are tight (1-2 sentences), opinionated (aliases listed under Avoid), and devoid of implementation detail.

  • Updated inline as terms resolve — never batched
  • If absent, created lazily when the first term is resolved
  • For multi-context repos, lives under each bounded context, with a root CONTEXT-MAP.md

docs/adr/*.md (repo root)

Architectural Decision Records. Numbered sequentially. Each captures what was decided and why in 1-3 sentences.

  • Offered sparingly: only when hard-to-reverse AND surprising AND result of a real trade-off
  • If any of the three is missing, skip — don't document the obvious
  • docs/adr/ is created lazily on first ADR
Why repo root? These artifacts outlive any single feature. They're the durable spine that successive /build runs sharpen — not feature-scoped.
03Conversation Tactics

Challenge the glossary

When a user term conflicts with existing language in CONTEXT.md, call it out.

"Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"

Sharpen fuzzy language

When the user uses overloaded terms, propose a precise canonical term.

"You're saying 'account' — do you mean the Customer or the User? Those are different things."

Stress-test with scenarios

Invent concrete scenarios that probe edge cases and force precision about boundaries between concepts.

"If a Customer has two pending Orders and one ships, does the OrderPlaced event for the other still fire?"

Cross-reference with code

When the user describes how something works, check whether the code agrees. Surface contradictions.

"Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"
04Interaction Pattern
RuleWhy
One question at a timeBatched questions are overwhelming and the user's later answers usually depend on earlier ones
Recommend an answer for each question"What do you think?" wastes turns; users push back faster against a concrete proposal
Walk down branches sequentiallyResolve dependencies between decisions one-by-one — don't ask questions whose answer is blocked on another decision
Explore code instead of asking when possibleIf the codebase already answers a question, don't bother the user
Update inline, never batchCapture decisions as they happen — batched updates lose nuance and risk drift
05ADR Bar (all three required)

1. Hard to reverse

The cost of changing your mind later is meaningful. If you can swap it out next sprint, skip.

2. Surprising without context

A future reader will look at the code and wonder "why on earth did they do it this way?" If it's the obvious choice, no one will ask.

3. Real trade-off

There were genuine alternatives and you picked one for specific reasons. If there was no real alternative, there's nothing to document beyond "we did the obvious thing."

If any of the three is missing, skip the ADR. The point of an ADR isn't to document everything — it's to stop the next engineer from "fixing" something that was deliberate.

07Completion

The grill phase ends when all three are true:

  • → All ambiguous terms have been pinned down
  • → Cardinality and lifecycle questions are answered
  • → ADR-worthy decisions are recorded
  • → User has no questions you can't answer from the codebase
Then: tell the user what changed (terms added, ADRs created), say "say 'draft the spec' when ready", and STOP. The orchestrator does not advance autonomously.
