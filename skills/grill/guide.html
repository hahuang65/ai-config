01 · Decision frontier

Ask only what is ready

The frontier contains every decision whose prerequisites are settled.

  1. Ask all independent frontier questions in one numbered round.
  2. Recommend an answer for each question.
  3. Wait for the user's decisions.
  4. Update resolved terms and decisions inline.
  5. Recompute the frontier and repeat.

Facts are not interview questions. Inspect the codebase or delegate exploration, then ask the user only for decisions.

02 · Delegation

Two skills, one conversation

Grill owns

  • The design tree and question order.
  • Numbered rounds and recommendations.
  • Completion of every decision branch.

Model domain owns

  • The main-directory or linked-worktree documentation destination.
  • Ubiquitous-language conflicts and updates.
  • Decision records only for hard-to-reverse, surprising trade-offs.

The main project directory uses local context and decision files. A linked worktree reuses its saved local or Confluence destination and page links.

03 · Round format

Make batch replies easy

❓ Q1 — <question title>: <body or choices>
➡️ <recommended answer>

❓ Q2 — <independent question>: <body or choices>
➡️ <recommended answer>

Defer a question when it depends on another answer still open in the same round.

04 · Plain-language recap

Explain decisions before continuing

An interim recap must make sense without the earlier conversation.

  1. What we decided: State one decision per bullet and explain what it means.
  2. What remains open: Separate unresolved questions from completed decisions.
  3. What happens next: Name the next question or action.

Use complete sentences. Explain every project-specific term in the recap, even when it appeared earlier. Do not use shorthand such as “control in” or “handoff out.”

05 · Completion

Finish with no silent assumptions

  • The frontier is empty.
  • Ambiguous terms, cardinality, and lifecycle are resolved.
  • Qualifying decision records are created at the selected destination.
  • The user is satisfied with the shared understanding.

Inside build: return to the orchestrator. Relevant UI proceeds to mockup; otherwise post-grill chat confirmation clears Design→Spec. Standalone: report changed context documentation and decision records, then wait before drafting the Spec.
