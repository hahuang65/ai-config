/grill

Interactive feature interview in dependency-aware rounds. /grill owns the decision frontier and invokes /model-domain to maintain the ubiquitous language and qualifying decisions.

01Place in the Pipeline

Phase 1 of /build. The grilling session is the design phase. Phase 2 (/spec) just transcribes its outcome — it does NOT re-interview.

/build "feature" ├── Phase 1: /grill ← YOU ARE HERE ├── Phase 2: /spec ├── Phase 3: /todo └── Phase 4: /code (or /coach)
02What It Produces

model-domain → context files

CONTEXT.md and CONTEXT-MAP.md are collectively the context files. They are the durable record and navigation structure for the ubiquitous language, not the language itself. They are long-lived and accrue across every /build run.

  • Updated inline as terms resolve — never batched
  • If absent, created lazily when the first term is resolved
  • For multi-context repos, lives under each bounded context, with a root CONTEXT-MAP.md

model-domain → docs/adr/*.md

Architectural Decision Records. Numbered sequentially. Each captures what was decided and why in 1-3 sentences.

  • Offered sparingly: only when hard-to-reverse AND surprising AND result of a real trade-off
  • If any of the three is missing, skip — don't document the obvious
  • docs/adr/ is created lazily on first ADR
Why repo root? These artifacts outlive any single feature. They're the durable spine that successive /build runs sharpen — not feature-scoped.
03Two Skills, One Session

grill owns the interview

Map decisions as a tree. In each round, ask every question whose prerequisites are settled, then recompute the frontier from the user's answers.

Batch independent decisions; defer any question that depends on another answer still open in the round.

model-domain owns the model

It challenges glossary conflicts, sharpens fuzzy terms, tests scenarios, checks the code, updates the applicable context file inline, and applies the ADR bar.

Invoking it from /grill embeds its discipline in the same interview; it does not start a second session.
04Interaction Pattern
RuleWhy
Ask the whole frontier in each roundBatch every independent decision that is ready now, then wait for the user's answers before the next round
Number and recommend for each questionConsistent labels make batch replies easy to map; concrete recommendations let users push back quickly
Defer dependent questionsA question blocked on another open answer belongs to a later round, even when both were initially visible
Recompute after every roundAnswers reshape the design tree and expose a new frontier rather than a predetermined questionnaire
Explore facts instead of askingUse tools or independent subagent exploration, deferring only downstream questions while the rest of the frontier proceeds
Update documentation inline, never batchQuestion delivery is batched; durable glossary and ADR updates still happen as decisions resolve
Question format: ❓ Q1 - <question title>: <body or choices>, followed by ➡️ <recommended answer>.
05Domain-Modeling Delegation

/grill loads ../model-domain/SKILL.md at the start and follows it throughout the interview.

Do not duplicate the discipline here. /model-domain is the source of truth for context topology, ubiquitous-language updates, audit and condensation, and the ADR qualification bar.

07Completion

The grill phase ends when all are true:

  • → The decision frontier is empty: every branch was visited and nothing remains silently assumed
  • → All ambiguous terms have been pinned down
  • → Cardinality and lifecycle questions are answered
  • → ADR-worthy decisions are recorded
  • → The user is satisfied with the shared understanding
Then: tell the user what changed (terms added, ADRs created), say "say 'draft the spec' when ready", and STOP. The orchestrator does not advance autonomously.
