Feature workflow

/build

Five phases turn an idea into an approved, verified change through domain modeling, optional UI mockups, canonical HTML, vertical-slice TDD, and Review change.

1 · grillmockup when relevant2 · spec3 · tasks4 · implement5 · review
01 · Before Phase 1

Isolate the work

Already in a linked worktree

Continue there without Orchard adoption or relocation.

Main project directory

Preflight Orchard, then let it acquire and enter a task worktree.

Degraded mode is explicit. If Orchard is missing or incompatible, continue on a local task branch only after warning the user and receiving approval.

02 · The five phases

One owning skill per phase

1 · Grill

grill interviews in dependency-aware rounds and invokes model-domain to resolve the worktree destination, update context documentation, and record qualifying decisions.

Relevant UI then runs through mockup; explicit approval clears Design→Spec.

2 · Spec

spec synthesizes settled intent instead of re-interviewing.

Output: specs.html.

3 · Tasks

todo creates thin, dependency-ordered vertical slices marked AFK or HITL.

Output: tasks.html.

4 · Implement

code lets the AI implement; coach keeps implementation with the user.

Both use one RED→GREEN cycle at a time, verify the project, and run the refactorer hygiene sweep.

5 · Review change

A fresh adversarial review checks intent, targeted evidence, documentation, lint, and canonical artifact accuracy.

Output: a disposable decision report.

03 · Artifacts

Canonical HTML only

local: CONTEXT*.md + docs/adr/*.md   project-wide domain documentation
or: Confluence context + decisions  linked-worktree collaboration
docs/features/<YYYYMMDD-HHMM>-<slug>/
  mockups.html                       conditional approved UI intent
  specs.html                         approved spec
  tasks.html                         approved slices and completion state

mockups.html, specs.html, and tasks.html are durable sources, not companions to Markdown. Each feedback batch updates the same live file.

04 · Approval gates

Four decisions, not per-tool prompts

GateSignal
Design→SpecExplicit mockups.html approval for relevant UI; otherwise post-grill chat confirmation.
Spec→TasksExplicit approval of canonical specs.html.
Tasks→ImplementExplicit approval of canonical tasks.html and selection of code or coach.
Review→DoneEvery ask-user Finding has a disposition and the final report is approved.

Routine reads, edits, tests, and environment setup proceed within a phase. Verified implementation advances directly to Review change.

05 · UI intent changes

Return to the owning artifact

A deliberate material UI redesign pauses final review, returns through mockup and review-artifact, synchronizes specs.html and tasks.html, renews invalidated approvals, and restarts Review change with refreshed Authoritative intent without adding a fifth gate.

Ending a browser review, closing the browser, or losing the connection is not approval.
