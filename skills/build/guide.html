/build pipeline

Five-phase workflow combining ubiquitous-language domain modeling, canonical HTML artifacts, vertical-slice TDD, and intent-aware Review change.

1 grill → 2 specs → 3 tasks → 4 implement → 5 review change
01The Five Phases

grill opus · interactive

Dependency-aware interview that invokes model-domain to sharpen the ubiquitous language, resolve cardinality, and capture qualifying decisions.

  • Reads CONTEXT.md + docs/adr/ through model-domain
  • Asks the whole ready decision frontier in each round and recommends answers
  • Challenges fuzzy language; cross-references with code
  • Updates CONTEXT.md inline as terms resolve
  • Offers ADRs sparingly (hard-to-reverse + surprising + real trade-off)
Output: ./CONTEXT.md (ubiquitous-language record)
Output: ./docs/adr/*.md (qualifying decisions)

spec synthesis

Synthesizes a feature spec from the grilling outcome. Does NOT re-interview.

  • Reads root or mapped context files, recent ADRs, conversation
  • Sketches major modules (deep-modules philosophy)
  • Proposes module test surfaces; user corrects boundaries/seams only
  • Writes spec: problem, solution, user stories, decisions, testing
  • NO code snippets, NO file paths (they go stale)
  • Browser annotations and messages through review-artifact
  • Explicit approval advances the gate
Canonical output: docs/features/<slug>/specs.html

todo vertical slices

Breaks the approved spec into vertical-slice tracer bullets. Each slice cuts through every layer end-to-end.

  • Reads canonical specs.html, applicable context files, ADRs
  • Each slice = thin path through schema, API, UI, tests
  • Marked HITL (human-in-loop) or AFK (away-from-keyboard)
  • Dependency order: blockers first
  • Review through review-artifact until explicit approval
Canonical output: docs/features/<slug>/tasks.html

implement sonnet · TDD

Executes the approved slices via vertical-slice TDD — one test, one implementation, repeat. No batching.

  • For each slice: confirm interface → RED→GREEN per criterion → refactor
  • Tests describe behavior through the spec/task public interface, not implementation
  • Verification loop: type check, lint, test, build
  • Agents: tdd-guide and refactorer (hygiene mode)
  • Coach variant: AI writes ONE test, user implements, AI verifies
Output: verified code ready for final validation

review change opus · final gate

Validates the complete feature change against canonical approved intent rather than searching for optional redesign.

  • Fresh adversarial reviewer evaluates the full feature diff
  • Runs targeted evidence, documentation checks, and lint in fixed order
  • Fact-checks canonical specs.html and tasks.html in place
  • Presents Findings with independent severity and action
  • Opens the final report through review-artifact
  • review-code remains optional standalone architecture exploration
Output: disposable decision report + Review-to-done approval

04Review Artifact Loop

Whenever an HTML artifact asks for feedback or approval, review-artifact opens it in a local browser surface.

generate canonical HTML → annotate exact element or text ↑ ↓ └──── live reload ← agent applies feedback

Artifacts use the ubiquitous language recorded in the applicable root or mapped context files. The foreground poll returns durable feedback batches, severe layout warnings, and an explicit approval event. In the final report, each issue card contains its own decision controls and one bottom button submits all decisions without copy and paste. Ending or closing review is not approval.

05Canonical HTML Sync

specs.html and tasks.html are durable sources, not visual companions. Every feedback batch updates the same semantic HTML so the browser never intentionally lags.

Phase 5 cold-fact-checks those same files against final code, confirms idempotence, and opens its disposable decision report through review-artifact. Browser failure falls back to chat without weakening explicit approval.

07Key Principles

Vertical, never horizontal

Each task slice cuts through every layer end-to-end (schema, API, UI, tests) and is demoable on its own. Horizontal slices ("set up the schema first") are explicitly rejected.

One test, one impl, repeat

TDD is strictly vertical: write one test, write minimal code to pass, refactor when GREEN, move on. Batched tests describe imagined behavior, not actual behavior.

Ubiquitous language everywhere

The shared canonical terms recorded in the applicable context files appear unchanged in conversation, specs, tasks, test names, and code identifiers. Inconsistency triggers rework.

Semantic HTML is the deliverable

specs.html and tasks.html are durable reviewed sources. There are no Markdown companions or hidden duplicate models.

User judgment via gates

Browser annotations, messages, and explicit approvals let the user inject domain knowledge, constraints, and trade-offs. The orchestrator never infers approval from ending review.

Never commits

Neither /code nor /coach runs git commit. The user reviews and commits when ready.
