Executive summary

The "configure once, install everywhere" promise, made literal.

What changed and why

The repo's tagline — "a single configuration that can power any arbitrary AI harness" — was aspirational. It served Claude Code and OpenCode and that was it. omp users started from zero.

This change wires omp (oh-my-pi) as a first-class third harness: every skill, command, agent, and rule mirrors into ~/.omp/agent/, omp gets a hand-authored config.yml, and the rule library reshapes into two halves — a tight 3-file rulebook for advisory loading and an 8-file TTSR set for regex-triggered mid-stream enforcement. TTSR is the per-pattern enforcement layer Claude has via shell hooks but omp has no equivalent for. By the end, an omp user runs the same ./install.sh and gets the same skills, agents, and safety net Claude users get — modulo each harness's runtime model.

Zero changes to claude/settings.json, claude/hooks.json, the existing curl hook, scripts/sync-permissions.py, or any OpenCode config. Claude users see no behavior change. The integration is additive.

Code review · post-implementation triage

Good · Bad · Ugly · Questions

The code-reviewer and refactor-cleaner agents ran post-implementation. Findings below are categorized; all CRITICAL / HIGH / MEDIUM items were addressed in the verification chain before this diff-review was generated.

Good

  • TDD discipline held on slices 4 + 5. Both followed RED → GREEN cleanly with self-tests proving each new pipeline check fires on a planted fixture.
  • Zero regressions on Claude/OpenCode. git diff shows zero changes to claude/, opencode/, config/, or scripts/sync-permissions.py. The integration is additive.
  • Cross-harness wording fix found 4 sites, not 1. Originally scoped for skills/implement/SKILL.md; the grep audit found implement-coach, prd, tasks all had the same Claude-centric phrasing. Permanent guard now in place.
  • 5 ADRs capture the why. Future readers won't need to spelunk commit messages to understand why we picked full-mirror over discovery or why development-workflow.md was deleted.
  • Self-test cleanup trap extended safely. The omp/config.yml rename pattern includes a restore-if-crashed branch — even an interrupted self-test won't leave the repo broken.
  • YAML validity check generalized to omp/*.yml. Will automatically cover future omp/models.yml etc. without needing a code change.

Bad · all addressed pre-review

  • HIGH — fixed. test_omp_yaml_valid originally interpolated $yml directly into a Python single-quoted string, which would break on any filename with a quote. Rewritten to pass via argv (python3 -c "import yaml, sys; yaml.safe_load(open(sys.argv[1]))" "$yml").
  • HIGH — fixed. The original git-workflow.md condition required --force to appear immediately after git push, missing the common git push origin main -f trailing-flag form. Added a second condition allowing the flag anywhere on the line.
  • MEDIUM — fixed. no-shell-write.md missed printf > file and the tee | next-cmd mid-pipeline form. Both added/broadened.
  • MEDIUM — fixed. no-curl-pipe-interpreter.md missed the curl | tee | bash interposer bypass and python3. Pattern rebuilt as curl\b[^|;&\n]*\|[^|;&\n]*\|?\s*(bash|...|python3)\b.
  • MEDIUM — fixed. no-credentials-read.md missed uppercase SSH keys (id_RSA). Character class broadened to [A-Za-z0-9]+.
  • MEDIUM — fixed. no-deploy.md's make push* pattern over-fired on innocuous make push (commonly aliased to git push). Narrowed to push-(to-prod|staging|live|release).

Ugly · accepted trade-offs

  • omp users see more bash prompts than Claude users. Claude's ~90-entry per-pattern allow list (covering rspec *, mise x -- rspec *, etc.) doesn't translate to omp. omp users get prompted on every routine test/lint/build command. Accepted in ADR-0004 — safety > friction for v1.
  • OpenCode still doesn't load rules. Pre-existing asymmetry preserved as-is. Rules continue to be Claude-and-omp only. Worth flagging if OpenCode adds a rule loader later — the descriptions already in place would be usable immediately.
  • Live TTSR firing not verified. Conditions are verified-by-design (regex spot-checks pass against representative target strings) but no live omp session reproduced the abort + inject + retry flow. Recommend a 3–4 pattern spot-check before relying on TTSR as a security guarantee.
  • TTSR rule body for security.md uses checklist style for multi-condition coverage. When TTSR fires on string-concat SQL the reminder body covers ALL of the security topics, not just the one that triggered. The model has to self-identify which trigger fired and apply the right fix. Less precise than one-rule-per-pattern but accepted to avoid file proliferation.
  • Pre-existing ~/.omp/agent/rules directory-level symlink from a prior manual setup conflicted with install.sh's file-level symlinks. Required a one-time unlink before re-running install. Documented in tasks.md slice 1; not a general install.sh defect.

Questions for review

  • Should TTSR pattern tuning be tracked as a follow-up backlog item? Regex over-fires are easier to fix than under-fires, and the post-review pass already caught 5 misses. After a week of live use, expect more.
  • Per-project TTSR rules — omp's discovery walks ancestor .omp/rules/ dirs, so individual projects could ship narrower rules (e.g. no-touch-prod-config.md). Worth mentioning in the README or saving for a future feature?
  • The no-shell-write.md rule is the philosophically interesting one — should it apply to Claude too? Claude currently allows echo > file through the bash allowlist. Tightening on the Claude side would close a small consistency gap.
Decision log · 5 ADRs

Why we did what we did

All five ADRs were written during the grilling phase and updated post-implementation to reflect final counts. Confidence is HIGH on all — each was discussed explicitly with the user before being recorded.

ADR-0001

Full mirror per harness

install.sh symlinks every primitive into every harness root rather than relying on omp's built-in .claude discovery fallback. Native priority, no source-toggle dependency, no rules-only carve-out, copy-paste-ready for a 4th harness.

HIGH · discussed
ADR-0002

Rulebook over always-apply

Rules with only description: sit in omp's rulebook bucket — model loads them via rule://<name> on demand. Cheaper context-per-turn than alwaysApply: true, and load-trigger descriptions guide the model's decision.

HIGH · discussed
ADR-0003

TTSR is omp's enforcement layer

8 TTSR rules replace what Claude's per-pattern denylist + curl hook do on the Claude side. Drop development-workflow.md as orphaned. Bucket split: 3 advisory rulebook + 8 enforcement TTSR.

HIGH · discussed
ADR-0004

Permissions and hooks decoupled

Hand-author omp/config.yml. Don't extend the sync script (~115 per-pattern entries on the Claude side have no omp equivalent). Don't port the curl shell hook (TTSR covers it). Sync stays a Claude ↔ OpenCode bridge.

HIGH · discussed
ADR-0005

Flat shared config layout

No rules/omp/ or rules/claude/ subdirectories. Per-harness scoping only for the runtime config files themselves (claude/, opencode/, omp/). Symlink-as-source is the load-bearing property that keeps "configure once, install everywhere" simple.

HIGH · discussed
Re-entry context · note from present-you to future-you

What to remember in two weeks

Key invariants

  • The user-level omp root is ~/.omp/agent/ — with the literal agent subfolder. Easy to miss when extending install.sh.
  • TTSR rules must have both description: and a non-empty condition: list. The pipeline enforces this via test_ttsr_rule_frontmatter; rule files without either are silently dropped by omp at runtime.
  • Rulebook rules must have description: and must NOT have alwaysApply: (per ADR-0002). Enforced by test_rulebook_rule_frontmatter.
  • The install.sh omp block marker (# ── omp (third harness) is grepped by test_omp_install_targets_exist — don't rename it without updating the test.

Non-obvious coupling

  • Forbidden phrase check covers all 4 AI-readable dirs. test_no_forbidden_claude_centric_phrasing greps skills/ + commands/ + agents/ + rules/. Adding new files to any of those dirs that contain "already loaded in context" (or variants) will fail the pipeline.
  • install.sh's omp config.yml symlink is the ONLY explicit source path in the omp install block — everything else is glob-derived from skills//commands//agents//rules/. test_omp_install_targets_exist only checks the explicit path. If you add another explicit path, extend the check.
  • YAML frontmatter in rule files is parsed by all three harnesses — Claude strips it on injection (rule body still applies), omp uses the fields (description, condition, scope), OpenCode ignores rules entirely today. Adding new frontmatter keys is safe but may need pipeline validation.

Gotchas

  • Single-quoted YAML strings (used for TTSR conditions) treat backslashes as literal. Single quotes inside such strings must be escaped by doubling (''). The current TTSR rules use this pattern extensively.
  • If a user has manually pre-populated ~/.omp/agent/ with directory-level symlinks (e.g. ~/.omp/agent/rules → /Users/foo/some-dir/rules), install.sh's file-level symlinks will fail with "are the same file" — unlink the manual dir-level symlink first.
  • The sync-permissions.py script is DELIBERATELY a Claude ↔ OpenCode bridge only. Adding an omp branch would silently drop ~90 per-pattern Bash entries (omp has no per-pattern format). The current design treats this as expected and routes omp safety through TTSR instead.
  • opencode/opencode.jsonc is auto-generated by the sync script — never edit by hand. omp/config.yml is the opposite — always edit by hand, never generated.

Don't forget

  • This is uncommitted. Run git status before further edits. The git workflow rule (per rules/git-workflow.md) calls for a single logical commit covering this integration.
  • Live spot-check TTSR firing in an omp session for at least 3 patterns (one bash, one file write, one credential read) before treating TTSR as a hardened safety mechanism.
  • Adding a 4th harness later: copy the omp install.sh block; add a <harness>/config.yml file; add a row in the README Triple-Harness table; update test_omp_install_targets_exist to also check the new harness's explicit paths.
  • TTSR rule tuning is a follow-up backlog item. Regex over-fires (false positives) interrupt unnecessarily; under-fires (bypasses) leave safety holes. Expect a follow-up /build cycle after a week of live use.
