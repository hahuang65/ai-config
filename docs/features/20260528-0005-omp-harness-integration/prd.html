Architectural shape

One source, three harness roots

Problem & solution

Aspirational, made literal

The repo's stated goal — "a single configuration that can power any arbitrary AI harness" — is aspirational today. omp users get zero of its skills, rules, agents, commands, or safety configuration. This integration makes the goal literal without compromising the existing Claude / OpenCode experience.

Before · Dual-tool
After · Triple-harness

"Centralized configuration for AI coding assistants — Claude Code and OpenCode." An omp user starting from this repo gets nothing — no skills, no commands, no agents, no rules, no safety net.

  • Skills, commands, rules, agents — Claude + OpenCode only
  • Permission sync — Claude → OpenCode only
  • Bash safety — Claude denylist + deny-curl-to-interpreter.sh hook
  • omp users — start from scratch

"Centralized configuration for AI coding assistants — Claude Code, OpenCode, and omp." Every shared primitive installs into all three harnesses with one ./install.sh.

  • Skills, commands, rules, agents — all three harnesses
  • Permission sync — unchanged, Claude ↔ OpenCode bridge stays honest
  • Bash safety — Claude keeps denylist + hook; omp uses TTSR + built-in critical-pattern detector
  • 4th harness later — copy-paste the omp install.sh block
Implementation · omp runtime config

Fifteen lines of YAML

Hand-authored. Not synced.

Per ADR-0004, omp's tier-based approval model has no equivalent for Claude's per-pattern Bash(rm -rf *) entries. sync-permissions.py stays a Claude ↔ OpenCode bridge.

approvalMode: write auto-approves read/edit/write tools; tools.approval prompts for the exec-tier tools explicitly. TTSR rules are the per-pattern enforcement layer that replaces Claude's denylist. 

# omp/config.yml — symlinked to ~/.omp/agent/config.yml
tools:
  approvalMode: write          # auto-approve read/write; prompt for exec
  approval:
    bash: prompt              # every shell command gets a prompt
    browser: prompt
    ssh: prompt
    eval: prompt

# No MCP servers (out of scope for v1)
# No provider/model entries (user-personal: ~/.omp/agent/models.yml)
# No theme / statusline / keybindings (user-personal)
User stories · 30 total

From six perspectives

Stories grouped by actor. Numbers continue the PRD numbering but are renumbered within each card for readability. Full canonical list lives in prd.md.

The repo maintainer

3 stories
  1. I want omp to be installable from this repo so its "any harness" goal becomes literal rather than aspirational.
  2. I want my omp configuration installed alongside Claude and OpenCode so a single command bootstraps every harness I use.
  3. I want install.sh to create ~/.omp/agent/ and symlink the right files into it without me having to know omp's directory convention.

The omp user

11 stories
  1. I want this repo's 13 skills surfaced in my omp system prompt so I can invoke /grill, /build, /refactor, etc.
  2. I want /build to behave identically to Claude — grill → PRD → tasks → implement, no per-harness deviation.
  3. I want this repo's seven agents available by name when I spawn a subagent via the task tool.
  4. I want TTSR rules to fire automatically on dangerous patterns — no setup, no per-rule enabling.
  5. About to write git push --force, I want the stream to abort and tell me what to do instead.
  6. About to write curl … | bash, I want TTSR to fire — same protection Claude's hook gives.
  7. About to read .aws/credentials, I want the read blocked before any secret reaches the model.
  8. About to run make deploy or terraform apply, I want an interruption — deploys must be human-initiated.
  9. Invoking bash, I want a prompt before execution — approvalMode: write friction is appropriate for exec-tier tools.
  10. Editing or writing a file, I want no prompt — file mutations are auto-approved.
  11. When TTSR fires, I want a clear message about what was blocked and the right alternative — not a generic notification.

The Claude / OpenCode user

2 stories
  1. As a Claude Code user, I want nothing about my existing experience to change — rules still load, permissions still apply, hooks still fire.
  2. As an OpenCode user, I want nothing about my existing experience to change — synced permissions still work, skills and commands still resolve.

The repo developer

8 stories
  1. Browsing rules/, I want each rule's role obvious from its frontmatter: rulebook has description: only; TTSR has description: + condition: + scope:.
  2. Writing a new rule, I want clear conventions: rulebook descriptions are load-triggers; TTSR descriptions are enforcement labels.
  3. Reading CONTEXT.md, I want canonical definitions of harness, skill, rulebook, TTSR in one place.
  4. Reading docs/adr/, I want the rationale for the five integration decisions without spelunking commit history.
  5. Running test-pipeline.sh, I want it to fail loudly on missing TTSR conditions, stray rulebook conditions, broken symlinks, or invalid omp YAML.
  6. Running the test pipeline, I want it to fail if any AI-readable file says "already loaded in context" — that phrase is false on omp.
  7. Maintaining test-pipeline-self-test.sh, I want negative cases proving each new check catches its target failure.
  8. As the author of sync-permissions.py, I want the script to stay a Claude ↔ OpenCode bridge so its promise stays honest.

The Claude hook author

1 story
  1. I want deny-curl-to-interpreter.sh to stay Claude-only — no TS port for omp's hook API. TTSR covers the same surface.

The future maintainer

5 stories
  1. Adding a 4th harness, I want the omp install block in install.sh small and self-contained so I can copy-paste it as a starting point.
  2. Reading the README, I want a single Triple-Harness Support table comparing Claude / OpenCode / omp across every capability axis.
  3. Reading the README's pipeline overview, I want to know /build's phases all work in omp the same way they do in Claude.

This is a config-repo integration, not a typical software feature. "Modules" here means discrete work areas with testable boundaries where they exist. Decision record · 5 ADRs

Where the "why" lives

The PRD is the what; the ADRs are the why. Created during the grilling phase that produced this PRD. When a reader has a "why?" question, the ADRs are the answer of record.

ADR-0001

Full mirror per harness

Symlink everything into every harness root, not via omp's .claude fallback. Priority insulation, no source-toggle dependency, no rules-only carve-out, 4th-harness-ready.
ADR-0002

Rulebook over always-apply

Rulebook with load-trigger descriptions, not alwaysApply: true. Context tax per turn matters; descriptions are how the model decides when to load.
ADR-0003

TTSR is omp's enforcement layer

3 rulebook + 8 TTSR. Drop development-workflow.md as orphaned. TTSR replaces what Claude's denylist + curl hook achieve on the Claude side.
ADR-0004

Permissions and hooks decoupled

Hand-author omp/config.yml. Sync script stays a Claude ↔ OpenCode bridge. Claude shell hook stays Claude-only — TTSR is omp's equivalent.
ADR-0005

Flat shared config layout

No rules/omp/ or rules/claude/. Per-harness scoping only for runtime config files. Symlink-as-source is the property that makes "configure once, install everywhere" work.
Scope boundary

What this PRD does and doesn't

In scopev1 of the integration

  • Install pipeline extension — install.sh grows an omp section mirroring the existing Claude / OpenCode loops
  • Rule library restructure — 3 rulebook + 8 TTSR; development-workflow.md deleted
  • omp runtime config — hand-authored omp/config.yml with tier-based approval
  • Test pipeline extensions — 5 new checks + 5 negative cases
  • Implement skill correction — one-line fix; backed by regression guard
  • README rewrite — Dual-Tool → Triple-Harness narrative
  • Zero changes to claude/settings.json, claude/hooks.json, deny-curl-to-interpreter.sh, sync-permissions.py, OpenCode config

Out of scopedeferred or never

  • MCP server config in omp/config.yml — v1 ships none; future work if needed
  • omp model / provider config (models.yml) — user-personal, not repo-managed
  • omp themes, statusline, keybindings, TUI — user-personal
  • OpenCode rule loading gap — pre-existing asymmetry, not fixed here
  • Porting Claude's curl hook to omp — TTSR covers the surface (ADR-0004)
  • Extending sync-permissions.py to omp — no per-pattern equivalent on omp (ADR-0004)
  • Installing the omp binary — assume user installed it via bun install -g @oh-my-pi/pi-coding-agent or curl … | sh
  • Per-harness rule / skill / command / agent directories — flat layout (ADR-0005)
  • Automated tests for install.sh itself — no existing tests for Claude/OpenCode either; matching the existing repo norm
  • Migration script for existing users — ln -sf is idempotent; re-running install adds omp without disturbing Claude/OpenCode
