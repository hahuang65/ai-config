Feature specification · ADR-0028

Orchard Quarantine Repair Spec

Prevent harnesses from breaking a task worktree’s branch binding, preserve quarantine as a durable safety boundary, and provide one explicit, independently verified path back to work.

fail closed explicit repair manual Git escape hatch structured evidence
01

Problem Statement

A direct branch switch inside a task worktree breaks its branch binding: Orchard still registers one assigned branch at the exact managed path while Git reports another.

Orchard correctly quarantines that uncertainty and excludes the slot from ordinary lifecycle operations. However, restoring the expected branch does not make the task usable again because quarantine is intentionally durable, entry cannot target quarantined work, and current human status output hides the path and reason needed for recovery.

The result is an avoidable dead end. Valid task work may remain dirty or untracked, yet delivery, entry, and other normal operations cannot select it. Destruction becomes the only available escape even when the branch binding has been restored and can be independently proven.

Current appearance is evidence, not authorization. Recovery must be explicit without weakening quarantine into an automatic retry.
02

Solution

Add two complementary controls. First, the shared harness guard blocks recognizable direct branch-binding changes when their effective Git target is beneath ~/.orchard/. Manual Git remains available as the deliberate escape hatch because Git has no portable pre-switch hook and Orchard must not install a fragile post-checkout reversal.

Second, Orchard records structured branch-mismatch evidence and adds orchard repair [intent]. Repair accepts only a recorded branch-binding mismatch and restores the slot only after proving the exact registered project, path, assigned branch, Git worktree metadata, uniqueness, stable Git operation state, and non-conflicting ownership.

03

User Stories

  1. As a harness user, I want direct branch changes under Orchard blocked before execution, so that an accidental unscoped command cannot break a task worktree’s branch binding.
  2. As a harness user, I want branch switching, branch-mode checkout, current-branch renaming, and direct HEAD reassignment covered consistently, so that equivalent commands cannot bypass the guard.
  3. As a developer restoring files, I want explicit path checkout and restore operations allowed, so that the guard does not confuse content restoration with branch switching.
  4. As a developer working across repositories, I want an explicit Git target outside Orchard honored even when my session is inside a task worktree, so that safe cross-repository work remains possible.
  5. As a developer outside Orchard, I want branch operations to behave normally, so that this safety policy does not become a global branch prohibition.
  6. As a terminal user, I want manual Git to remain available, so that the harness guard does not pretend to be an operating-system sandbox.
  7. As a developer after a mismatch, I want quarantine to retain expected and observed branch evidence, so that I can understand what happened before attempting repair.
  8. As a developer, I want restored current state alone to remain insufficient for automatic recovery, so that quarantine keeps its fail-closed meaning.
  9. As a developer, I want normal status output to show quarantined worktrees, their exact paths, expected and observed branches, and reasons, so that recovery is discoverable.
  10. As an automation caller, I want status and repair JSON to expose stable reason codes and timestamps, so that tooling does not parse prose.
  11. As a developer in a quarantined worktree, I want repair to infer that exact slot when no intent is supplied, so that recovery is direct.
  12. As a developer in the main project directory, I want to repair by worktree intent, so that quarantine does not make navigation to the managed path a prerequisite.
  13. As a developer, I want repair intent tab completion to list eligible quarantined worktrees, so that selection works like Orchard entry.
  14. As a safety-conscious developer, I want repair rejected from unrelated linked worktrees and unrelated repositories, so that caller location cannot ambiguously select another task.
  15. As a developer, I want repair limited to a structured branch-mismatch quarantine, so that missing metadata, duplicate registrations, path-role conflicts, and damaged state remain quarantined.
  16. As a developer with legitimate uncommitted task work, I want dirty files allowed during repair, so that recovery does not require discarding or committing unrelated work.
  17. As a developer, I want repair blocked during merge, rebase, cherry-pick, revert, or bisect state, so that Orchard does not certify an unstable Git operation.
  18. As a single active owner, I want repair to remain possible, so that the harness session that restored the branch can continue.
  19. As a shared-worktree user, I want repair blocked when multiple owners remain live, so that another session cannot concurrently invalidate the proof.
  20. As a developer, I want successful repair to change only Orchard metadata, so that the command never modifies files, HEAD, refs, or branches.
  21. As a developer, I want an accidentally created branch reported but never deleted by repair, so that potentially valuable commits remain recoverable.
  22. As a maintainer, I want repair to preserve a durable audit record, so that the original mismatch and recovery time remain explainable after quarantine clears.
  23. As an automation caller, I want noninteractive repair to apply the same checks and return structured evidence, so that machine mode is not a weaker safety path.
  24. As a developer, I want a second repair attempt to fail unchanged once the slot is no longer quarantined, so that repair never masquerades as an idempotent refresh.
04

Implementation Decisions

Harness prevention

One shared policy

The branch-binding guard is a mandatory shared guardrail projected through both harness adapters. The normalized tool call carries the command and caller working directory so the policy core, not an adapter, owns target resolution and command classification.

Resolve the effective target

An unscoped Git command targets the caller directory. An explicit git -C target or preceding literal directory change replaces that target. Relative paths and home-relative Orchard paths are normalized before deciding whether the target is managed.

Recognize binding changes

The guard blocks switch, any checkout not explicitly in path mode, branch rename flags, symbolic HEAD reassignment, and direct HEAD update. Explicit checkout path mode and restore remain allowed.

Stay intentionally bounded

The detector covers recognizable direct Git commands, including ordinary command chains. It does not evaluate arbitrary shell variables, custom aliases, scripts, or programs that later invoke Git. The refusal directs harnesses to scope cross-repository mutations with an explicit absolute Git target.

Structured quarantine

A branch mismatch records a stable reason code, human reason, expected branch, observed branch or detached state, observed commit, and detection time. Other quarantine causes receive their own stable codes but are not repairable by this feature. Existing unstructured quarantine remains durable and ineligible rather than being inferred from reason text.

Repair contract

orchard repair [intent] [--json] is an explicit immediate mutation with no preview flag. From the exact quarantined worktree, Orchard infers the slot when intent is omitted and requires any supplied intent to match. From the main project directory, intent is required. Every other caller location is rejected.

Under the project lock, repair refreshes owner liveness and requires no more than one live owner. It rejects unresolved conversion or cleanup recovery and any in-progress Git operation. It then verifies that the registered project root identifies the same Git common directory, the slot path and intent retain the task-worktree role, exactly one Git worktree metadata entry owns that canonical path, exactly one entry owns the assigned branch, both entries are the same, and no durable slot duplicates either identity.

Ordinary staged, unstaged, and untracked task changes are permitted and reported without affecting eligibility. On success Orchard restores lifecycle task, removes active quarantine, writes lastRepair audit evidence, and returns the project, worktree, prior quarantine, repair proof, dirty indicator, and non-mutated accidental branch in the existing versioned machine envelope.

Repair never invokes Git mutation. A failed check leaves lifecycle, evidence, files, HEAD, refs, branches, owners, and timestamps unchanged. Re-running repair after success fails because the selected slot is no longer quarantined.

Status, help, and completion

Human status treats task and quarantined worktrees as visible managed work. Quarantine lines are visually distinct and include intent, exact path, expected branch, observed branch or detached state, reason, and detection time. Project scoping, global status, all-project mode, refresh, color behavior, and JSON envelopes remain consistent with existing status behavior.

Top-level and command help document repair eligibility, caller-location rules, dirty-work allowance, unstable-operation and ownership failures, metadata-only mutation, and the non-deletion guarantee. Completion exposes repair as a top-level command and returns only structured branch-mismatch quarantine intents in the current project.

Production modules

Managed branch-binding guard

Extends the shared policy input with caller location, resolves the effective Git target, classifies branch-binding changes, and returns one stable refusal. Harness adapters remain transport-only and the pi bundle remains a generated projection of the shared source.

Branch-binding verifier and repair service

Owns structured mismatch evidence, shared identity inspection, repair eligibility, caller targeting, ownership checks, stable-operation checks, audit construction, and the locked metadata transition. Recovery and repair reuse one verifier so detection and clearance cannot drift.

Orchard CLI status and completion surface

Wires the repair command, help, human and machine output, quarantine visibility, and eligible-intent completion onto the service without duplicating verification rules.

05

Testing Decisions

All behavioral changes follow red-green-refactor TDD. Orchard tests use real temporary Git repositories and isolated home directories; harness tests use the adapters’ public event boundaries and shared policy interface. Tests assert user-observable state and Git facts rather than private helper calls.

Managed branch-binding guard

Test directly through the shared policy evaluator. Cover every blocked command family, absolute Git executables, command chains, managed and ordinary caller directories, explicit targets into and out of Orchard, literal directory changes, relative and home-relative paths, checkout path mode, restore, benign help and status commands, and refusal guidance.

Adapter evidence: conformance tests prove pi forwards its extension context directory and Claude forwards the hook payload directory. The committed pi projection must rebuild without drift.

Branch-binding verifier and repair service

Test directly through its public service interface with real temporary repositories. Cover exact-path and main-project callers, inferred and explicit intent, expected branch restoration, detached state, missing and duplicate metadata, duplicate durable registrations, wrong project identity, role mismatch, unstructured and non-branch quarantine, unresolved recovery, ordinary dirty work, each in-progress Git operation, dead owners, one live owner, multiple live owners, successful audit, second invocation, and atomic failure preservation.

Non-mutation proof: snapshot files, index, HEAD, refs, worktree metadata, and accidental branch tips before repair and assert they remain identical afterward.

Orchard CLI status and completion surface

Test through the spawned executable as the highest stable user interface. Cover top-level and repair help, exit behavior, human and JSON repair outcomes, project and global quarantine status, color and no-color output, refresh durability after branch restoration, eligible-intent completion, shell prefix filtering, and regression that ordinary lifecycle commands continue excluding quarantined slots.

06

Out of Scope

  • Intercepting or confirming branch changes typed manually by a human.
  • Installing Git hooks, filesystem flags, shell wrappers, or automatic post-checkout branch reversal.
  • Automatic unquarantine during refresh or any ordinary lifecycle command.
  • Repairing missing metadata, duplicate registration, path-role conflict, corrupted state, conversion recovery, or other quarantine causes.
  • Inferring repair eligibility from legacy human reason text.
  • Automatically restoring the assigned branch, resetting files, cleaning changes, or aborting Git operations.
  • Deleting, renaming, moving, or otherwise changing the accidentally observed branch.
  • Evaluating arbitrary shell variables, user-defined aliases, scripts, or nested programs as a complete shell sandbox.
  • Changing entry, delivery, recycling, pruning, destruction, landing, or capacity policy beyond quarantine visibility and selection.
  • Repairing while multiple live owners share a task worktree.
07

Further Notes

ADR-0028 is authoritative for durable quarantine, harness-only prevention, and explicit repair. ADR-0023 remains authoritative for the hybrid pooled branch-bound lifecycle and conservative recovery principle.

Repair certifies identity, not content provenance. Allowing dirty work preserves legitimate task changes, while the audit record and accidental-branch report keep the branch round trip visible to the developer.

The guard is preventive ergonomics; quarantine remains the safety authority. If prevention is bypassed or unavailable, Orchard still detects disagreement and fails closed.
