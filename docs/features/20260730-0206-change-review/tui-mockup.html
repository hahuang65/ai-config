01 · Full-screen TUI

One screen, explicit progress, inspectable work.

The pipeline stays visible on the left with sub-stage labels bounded to six words. The right pane retains complete operations and outcomes—not model chain-of-thought. The header identifies the isolated review worktree. Use the tabs to simulate the run.

02 · Stage contract

What each row promises to tell you.

Lifecycle setup and teardown surround the canonical validation kernel. Each stage owns a durable in-memory log during the run and a concise outcome in the final terminal summary.

Setup 01

Resolve target

Shows target kind, source repository lookup, chosen base, and immutable base/head objects. Logs read-only git and gh metadata calls.

Setup 02

Create isolation

Shows protected-path validation, disposable clone creation, tracked/untracked snapshot scope, disabled push URL, and report-root allocation.

Kernel 01

Adversarial review

Shows scope-and-intent setup, fresh reviewer dispatch, coverage checking, and Finding/risk normalization as distinct sub-stages with live or completed elapsed timers, while retaining each as a STEP entry.

Kernel 02

Targeted evidence

Shows why each focused check was selected, its exact command or manual check, duration, exit status, and what it proves. Broad-suite repetition stays prohibited.

Kernel 03

Documentation

Shows documentation surfaces inspected, change-caused gaps, artifact consistency, and unresolved ambiguity. Standalone mode reports gaps without editing.

Kernel 04

Lint

Shows the exact focused lint or deterministic formatting checks, scoped inputs, durations, and outcomes without claiming unexecuted checks.

Results

Build report

Shows report path, risk and Finding totals, embedded provider Markdown for pull requests, one-shot Firefox launch on macOS, and immediate progression to cleanup without an approval gate.

Teardown

Cleanup

Shows child exit, exact isolated path removal, report retention, source-state verification, and final process exit status.

Final stage

Summary

Keeps the pipeline/log layout while showing the retained report path, risk and Finding totals, stage outcomes, and assistant summary. Ctrl-D scrolls down, while Ctrl-C exits once the review is complete; q, x, and Escape are ignored.

03 · Annotation prompts

What should change?

Annotate any exact row, label, log entry, or control in the mockup. These are the choices most worth challenging before implementation.

Stage boundaries

Are Resolve and Isolate useful first-class rows, or should the visible pipeline begin at Review?

Log fidelity

Should commands show full arguments by default, or a compact summary that expands on Enter?

Navigation

Do Vim-style j/k stage navigation, Ctrl-D/Ctrl-U log scrolling, Enter to expand or collapse lines, and f to follow the active stage feel natural?

Viewer handoff

Does the report log make it clear that successful browser launch never waits for browser closure, feedback, or approval before cleanup?

Failure behavior

Should later stages read Skipped after a failure, or should Documentation and Report still run to preserve complete evidence?
