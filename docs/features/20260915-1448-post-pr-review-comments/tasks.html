S1

Confirm one signed Finding locally

Complete

What to build: Carry one immutable Finding and exact pull-request scope from an eligible report through the signed publication protocol into a safe, read-only local confirmation page. Opening the report performs no request, and Continue starts no GitHub mutation.

  • An exact pull-request report shows one selected native Finding checkbox and a selection-derived read-only general comment.
  • The signed report envelope binds immutable provider identity, actor, scope, Finding body, and inline location without a per-report registry or expiry.
  • Continue submits only the signed envelope and selected Finding ID through a bounded top-level local form request.
  • The confirmation endpoint validates the envelope and current actor and scope, then renders one heading, complete destination details, general comment, inline comment, Change selection, and no mutation control other than final Post review.
  • Invalid signatures, malformed input, unsupported protocol versions, unsafe HTML values, and excessive bounds render typed no-mutation errors.
  • Browser evidence proves keyboard operation, visible focus, no startup request, no editable comment fields, and no manual-copy panels.

S2

Publish one confirmed comment review

Complete

What to build: Take the short-lived confirmation through exact account, repository, pull-request, base, head, and inline-location revalidation, then create one GitHub COMMENT review and render its verified success page.

  • The final browser form accepts only a signed confirmation envelope and cannot replace provider, comment, or operating-system approval values.
  • The provider adapter uses bounded argument-array calls with disabled prompts and never exposes credentials or raw output.
  • The publisher requires the signed GitHub actor, open pull request, immutable repository identity, exact base and head, and valid inline location, then requires a separate bounded operating-system confirmation immediately before the provider stage that can mutate.
  • One create-review call sends event COMMENT, the reviewed head, derived general body, and one inline comment.
  • The success page shows the validated actor, destination, provider review identity, and safe GitHub review link only after provider acceptance.
  • Focused evidence proves the browser's final action only requests publication, explicit operating-system approval creates one review, and every non-approval result causes no provider call.

S3

Publish the exact Finding selection

Complete

  • All current Findings start selected and each native checkbox has a name that includes the Finding title and anchor.
  • Selection changes announce only the count and always regenerate the read-only general comment from selected Finding titles in report order.

  • Unknown, duplicate, reordered, or tampered Finding values fail or normalize through the signed protocol rather than becoming provider content.
  • Confirmation and publication contain exactly the selected signed Finding bodies and locations with no excluded title or count.
  • Change selection returns to the still-open report without a server session, registry, or browser persistence layer.
  • Browser evidence covers zero, one, and many Findings, keyboard selection, status announcement, and responsive stacking.

S4

Reject stale or invalid publication

Complete

What to build: Turn account, permission, pull-request state, exact scope, location, authentication, and input failures into distinct local outcome pages while proving that every failing selection causes zero provider mutations.

  • A changed GitHub actor, repository identity, base, head, closed pull request, or invalid selected line prevents confirmation or publication as applicable.
  • One invalid selected location prevents the complete review; no valid subset posts automatically.
  • Authentication, permission, input, rate-limit, provider, and operating-system confirmation failures use stable status and error codes without credentials or raw output.
  • Each outcome page has one heading, a focused error summary, exact safe corrective action, and no optimistic success.
  • A changed scope asks for a new Review change run and never remaps a Finding.
  • HTTP and adapter tests assert zero mutation for every rejection branch.

S5

Reconcile retries without retained report state

Complete

  • Concurrent publication attempts for one report identity serialize through transient state that is removed after bounded request work.
  • Tests prove repeated exact activation returns one provider review and persist no local report record.

S6

Activate publication only on request

Complete

What to build: Install a user-owned loopback socket and platform activation definitions so an old open report can start one bounded publisher request after days or a reboot, with no publisher process, agent poll, or per-report listener between actions.

  • The normal installer configures equivalent user-level socket activation and an installation-owned absolute operating-system confirmation executable on supported macOS and Linux hosts.
  • The dormant state has no publisher process and binds only the documented loopback socket.
  • A confirmation or publication request starts bounded work and leaves no publisher process after completion.
  • Repeat installation safely upgrades managed definitions, preserves the installation signing key used by open reports, and keeps the complete managed credential directory protected by the mandatory shared guardrails from ordinary model file and shell tools.
  • Unsafe ownership, symlinked state, conflicting ports, malformed inherited sockets, unavailable platform confirmation UI, and unsupported platforms fail with corrective errors.
  • Installation and process evidence proves on-request start, request completion, no retained report state, and no cross-harness files.
