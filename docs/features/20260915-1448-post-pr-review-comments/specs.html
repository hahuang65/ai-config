Canonical feature definition

Spec

Let a reviewer publish only the relevant Review change Findings to their validated GitHub pull-request locations, without an active agent, an expiring poll, or a retained per-report service record.

Problem statement

Manual posting separates judgment from evidence.

Review change previously prepared one general pull-request comment and one inline comment for every Finding, but the reviewer had to copy each block and place it manually.

Automatic publication of every Finding is also wrong because a human reviewer can decide that a substantiated Finding is not useful for this pull request.

An agent poll or one listener per report cannot solve delayed publication safely: the reviewer may never post, or may return to an open temporary report days later.

Solution

A Review publication is selected, derived, confirmed, and posted once.

Eligible pull-request reports replace their manual copy section with the approved publication form. All Findings begin selected. The reviewer can clear irrelevant Findings, while the general comment is regenerated from only the current selection. Neither general nor inline comment text is editable.

Continue starts a user-scoped local publisher through operating-system socket activation. The publisher validates the signed report, authenticated GitHub account, open pull request, exact base and head commits, and every selected inline location before showing a read-only confirmation page.

The final Post review action requests publication but does not authorize provider mutation. After the signed confirmation token and exact selected content pass validation, the publisher shows a bounded operating-system prompt outside model-visible channels. Only explicit approval in that prompt lets the provider stage send one GitHub COMMENT review containing the selection-derived general comment and selected inline comments. No comment is sent when validation or operating-system confirmation fails.

Select Findings→Review exact publication→Approve system prompt→Show outcome
Temporary by design. The HTML carries the bounded publication capability. There is no per-report registry, expiration timer, browser storage, or retained publication manifest. Losing the open page or temporary file may safely end the publication opportunity.
User stories

Observable outcomes

  1. As a pull-request reviewer, I want a publication form in my Review change report, so that I can send comments without manually copying them.
  2. As a reviewer, I want every current Finding selected initially, so that the common case needs no repetitive setup.
  3. As a reviewer, I want to clear irrelevant Findings, so that human judgment controls which comments reach the pull request.
  4. As a reviewer, I want the general comment derived from my current selection, so that it never counts or names an excluded Finding.
  5. As a reviewer, I want the general and inline comments to remain read-only, so that published text stays aligned with reviewed evidence.
  6. As a reviewer with no selected Findings, I want a valid general-only review, so that I can still record completion without an inline comment.
  7. As a reviewer, I want a confirmation page that shows my GitHub account, destination, exact scope, general comment, and selected inline comments, so that I can inspect the complete mutation before it occurs.
  8. As a reviewer, I want Change selection before the final action, so that correction does not require a new review run.
  9. As a reviewer, I want the final Post review action to require a separate operating-system confirmation, so that browser or model-visible input alone cannot authorize provider mutation.
  10. As a reviewer, I want every selected Finding placed on its validated changed line, so that discussion appears beside the relevant code.
  11. As a reviewer, I want one GitHub comment review rather than separate comment calls, so that publication is coherent and does not intentionally post a partial selection.
  12. As a reviewer, I want publication refused when any selected location is invalid, so that the publisher never silently moves or drops a Finding.
  13. As a reviewer, I want publication refused when the base or head commit changed, so that comments never describe a different diff.
  14. As a reviewer, I want publication refused when the active GitHub account differs from the report account, so that I do not post under the wrong identity.
  15. As a reviewer, I want authentication and provider errors shown as clear local outcome pages, so that no agent is required to explain them.
  16. As a reviewer, I want an uncertain provider result reconciled before retry, so that a timeout does not create a duplicate review.
  17. As a reviewer, I want an existing matching Review publication returned as success, so that repeated activation is safe.
  18. As a reviewer, I want the button to work while an old temporary report remains open, so that no foreground poll expires before I return.
  19. As a system owner, I want no publisher process running between requests, so that reports the reviewer never uses consume no process resources.
  20. As a keyboard or assistive-technology user, I want native selection controls, clear status announcements, visible focus, and one heading per page, so that publication is operable without a pointer.
  21. As a user of local or non-pull-request reviews, I want their reports unchanged, so that provider mutation appears only where an exact GitHub pull request was validated.
  22. As a security-conscious user, I want credentials and comment payloads kept out of URLs, logs, and browser storage, so that delayed publication does not expose them.
Implementation decisions

Five boundaries preserve the review and mutation split.

Pull-request report publication form

A shared deterministic renderer produces native Finding checkboxes, a selection count, the general comment, and Continue. The same production renderer is exercised in the bounded browser test. The form performs no startup request and submits only the signed report envelope plus selected Finding IDs. The approved mockup defines its information hierarchy, state flow, responsive stacking, and accessibility behavior.

Public interface · opened pull-request report

Publication protocol

Defines strict bounds, signed report and confirmation envelopes, Finding selection, deterministic general-comment generation, stable publication identity, and typed errors. It accepts no browser-supplied comment text.

Public interface · encode, verify, derive, and canonicalize

Socket-activated local publisher

Owns the versioned loopback HTTP boundary, provider validation, server-rendered review and outcome pages, the separate operating-system confirmation, a transient lock named by a safe digest of the validated report identity, and one-request lifecycle. Different reports can publish concurrently. It has no report registry or session store.

Public interface · local review and publication endpoints

GitHub review adapter

Owns bounded argument-array GitHub CLI calls, actor and immutable-scope reads, inline-location checks, marker reconciliation, and the single create-review mutation.

Public interface · inspect scope, reconcile, and publish

Publisher installation

Installs and upgrades user-level socket activation for macOS and Linux and records the platform's absolute confirmation executable. macOS uses osascript; Linux uses Zenity in the active user session. Installation fails clearly when the supported confirmation facility is unavailable. The operating system owns the dormant socket and starts no publisher process until a browser request arrives.

Public interface · repository installer
Decision record. ADR-0038 records why publication uses a socket-activated local publisher, signed temporary report data, selection-derived immutable comments, exact-scope checks, and no retained per-report state.

Eligibility and report behavior

  • Only a report whose resolved review target is an exact GitHub pull request can offer Review publication.
  • The standalone skill's workflow contract and the standalone CLI's guard keep review generation read-only; only the separately installed publisher can perform the confirmed action afterward.
  • Pull-request reports remove the manual general-comment and per-Finding copy panels. Other report modes retain their current presentation and behavior.
  • All Findings start selected. The browser stores only native checkbox state for the loaded page and derives the preview from visible immutable Finding records.
  • The selection-state page makes no network request. Continue uses a top-level form navigation so no foreground agent or review-artifact session is involved.

Comment derivation

  • For one or more selected Findings, the general comment states the selected count and lists the selected Finding titles in report order.
  • For zero selected Findings, the general comment states that Review change completed and no Findings were selected for publication.
  • Each inline comment body and location comes from its signed Finding. The browser cannot submit a replacement body, path, line, side, repository, event, or scope.
  • Locations support the provider's explicit diff sides: LEFT means an old or deleted line, and RIGHT means a new, added, or current line. The structured Change reviewer result carries this value for each exact pull-request inline Finding. Report assembly never guesses, defaults, or remaps it. Every selected coordinate is validated before confirmation and again before publication.

Signed publication capability

Before the model runs, a trusted invocation boundary freezes the required GitHub host, repository and pull-request identities, full base and head object IDs, signing-key identifier, and comment-template version in a signed scope. The standalone CLI parent owns this boundary for CLI runs. The pi input extension and structured review_change_publication tool own it for direct pi sessions, preserve it across steering input, and supersede it only for a new recognized Review change invocation. The Claude Code UserPromptSubmit hook owns the equivalent pre-model boundary for direct Claude Code sessions and stores the signed scope as current-session state. Its PreToolUse Write hook accepts Finding claims only and replaces them with the signed form for that invocation. Both harness paths use the same code to freeze the scope and verify its signature. Every production report-signing path requires the current invocation-frozen repository, pull request, base commit, and head commit; no generic production API signs unfrozen model-authored claims. The mandatory shared guardrails classify the signing key and its complete managed ~/.review-publication/ directory as protected credential state for ordinary Claude Code and pi model tools. The separately installed socket worker and trusted pre-model harness boundaries use the key outside model tool calls. This practical boundary protects against mistakes and ordinary model tool use, not hostile code that already executes with unrestricted user-account access. Non-pull-request prompts receive no publication capability.

The trusted signer creates the random report identity and rejects submitted scope values that differ. The report envelope contains protocol version and audience fields, that trusted identity, the expected actor identity, and an ordered bounded set of Findings with stable IDs, titles, bodies, paths, lines, and sides. The initial contract supports github.com, signing key review-publication-v1, comment template 1, and token version 1; the unreleased feature has no legacy token migration. The report envelope has no time-based expiry. The short-lived confirmation envelope fixes the exact selected review and expires after fifteen minutes; an open report can request a new confirmation.

Provider verification and publication

  • Resolve the authenticated GitHub actor at confirmation and immediately before publication. Require the signed immutable actor ID and login.
  • Resolve the named repository and pull request, compare their immutable provider identities, require the pull request to remain open, and require exact full base and head object IDs.
  • Validate inline coordinates with complete diff evidence. If the changed-files response omits or truncates a patch, use one bounded complete-diff fallback. Return invalid_inline_location only when complete evidence proves absence; otherwise return the distinct inline_location_unverifiable no-mutation outcome.
  • After the confirmation token and exact selected content pass validation, show an operating-system-owned prompt immediately before the provider stage that can mutate. State the exact actor, repository, pull request, full base and head commits, selected Finding count, and whether inline comments are included.
  • Only explicit operating-system approval continues. Cancel, dismissal, timeout, unavailable UI, malformed response, process failure, and request cancellation settle the prompt and return a specific no-mutation browser outcome.
  • Use the reviewed head object as the comment review commit. Submit event COMMENT; never infer approval or requested changes from severity.
  • Send the general body and all selected inline comments in one create-review request. Invalid selection, location, scope, or permission prevents every mutation.
  • Add a stable hidden publication marker to the general body. Before mutation and after ambiguous failure, exhaust bounded provider pagination and compare the complete publication for that report identity.
  • Treat create-review HTTP 500 through 599 as ambiguous because GitHub can accept the mutation before the failure becomes visible. Reconcile by marker without a blind retry, and return publication_outcome_unknown when reconciliation cannot prove the result. Keep explicit 4xx authentication, permission, rate-limit, and validation failures definite.
  • Return the existing review when the complete marker content matches. Refuse a different selection for an already published report identity, multiple matches, incomplete reconciliation, or an outcome that remains unknown.

Security and lifecycle

  • Bind only to the fixed loopback interface. Validate the exact local Host, method, content type, and body size before form decoding, then match the versioned request path and verify the signed protocol version.
  • Use schema validation at both HTTP boundaries and constant-time signature checks. Reject duplicate or unknown Finding IDs.
  • Invoke the trusted GitHub CLI and operating-system confirmation facility with fixed absolute executables, argument arrays, bounded time, and no shell. Give the request and service enough additional time for the confirmation process to settle.
  • Never accept, predict, or pass the operating-system approval response through an HTTP request, signed report, environment, or helper argument.
  • Never request or expose a GitHub token. Never log envelopes, request bodies, comment text, credentials, raw provider output, or provider command lines.
  • Keep dynamic provider and report content in HTML text contexts. Confirmation and outcome pages deny framing, storage, referrers, and unneeded scripts.
  • Use one transient lock per validated report identity while publication runs. Derive its filesystem-safe name with a cryptographic digest so the same report is serialized without blocking a different report. No browser storage, server session, retained manifest, report registry, long poll, server-sent event, or background refresh is allowed.
  • The activated publisher exits after its bounded request work. Repeated installation preserves the signing key used by currently open signed reports. The shared guardrails block model reads, writes, edits, searches, copies, moves, deletes, normalized path variants, and common shell access to the complete managed credential directory.

Stable interfaces carry behavior evidence.

Use the existing bounded Firefox lane to prove no startup request, all-selected defaults, keyboard selection, zero/one/many derivation, exact confirmation selection, no editable or manual-copy controls, clear focus and status behavior, an initial Continue focus target when Findings are empty, the approved two-column desktop hierarchy, and narrow-screen stacking. Exercise the production fragment styles and submit against an injected local publisher boundary rather than a real provider.

Publication protocol — test directly

Exercise canonical generation, invocation-frozen signing, verification, selection ordering, zero/one/many comments, stable marker identity, confirmation expiry, strict limits, signature tampering, actor and scope binding, duplicate IDs, invalid coordinates, rejection of changed repository, pull request, base, or head scope, and rejection of unfrozen production signing through the public interface.

Socket-activated local publisher — test through HTTP

Exercise both versioned endpoints with real bounded local requests, an injectable operating-system prompt, and a fake GitHub adapter. Cover approval, denial, dismissal, timeout, unavailable executable, malformed response, process failure, cancellation, revalidation, all typed outcome pages, no provider call after every non-approval result, transient serialization, process completion, and the absence of retained report state.

GitHub review adapter — test directly

Use an injected process runner to verify argument arrays, prompt suppression, output and time bounds, immutable identity and scope comparisons, left/right locations, omitted and truncated patch fallback, unverifiable no-mutation outcomes, exhaustive bounded pagination, exact marker matching, create-stage HTTP 500 through 504 reconciliation, conflicting and uncertain outcomes, and one comment-review mutation.

Publisher installation — test through installer behavior

Extend the existing installation lanes to verify macOS and Linux socket definitions, installation-owned absolute confirmation executables, clear failure when the supported UI is unavailable, user ownership, managed links, repeatable upgrades, fixed loopback binding, exact systemd loaded, enabled, and active state restoration after failed activation, rollback failure reporting, publisher-on-request behavior, and no cross-harness leakage.

Focused tests must also prove that untrusted PR text cannot alter HTML execution or signed provider fields, a changed base or head performs zero mutation, the wrong actor performs zero mutation, a repeated exact publication returns one provider review, and real GitHub is never mutated by the test suite.

Out of scope

Deliberate exclusions

This feature does not:
  • Post from local-range, remote-branch, non-GitHub, or build-mode reports.
  • Approve a pull request, request changes, submit a pending review, merge, label, close, or modify source branches.
  • Edit the general comment or any inline Finding comment.
  • Remap Findings to a changed pull request or publish a valid subset after another selected Finding fails validation.
  • Retain per-report state, publication manifests, selection history, or an agent session.
  • Keep the existing manual provider-comment copy panels in pull-request reports.
  • Start interactive GitHub authentication from the browser or publisher.
  • Guarantee provider-level exactly-once behavior when GitHub accepts a mutation but never makes it observable for reconciliation.
  • Provide operating-system isolation of the signing key from hostile code that already runs with unrestricted user-account access; the accepted boundary covers mistakes and ordinary model tool use.
Further notes

Authority and compatibility

The approved mockup is authoritative for the selection and confirmation hierarchy, interaction flow, important states, responsive intent, and accessibility behavior. Exact decoration remains directional.

ADR-0038 is the durable architectural decision. The current provider-mutation guard remains authoritative inside Review change itself. The browser action only requests publication; the separate bounded operating-system confirmation grants the publisher's one Review publication.

The current general comment grammar and signed envelopes use versioned formats. Repeated installation preserves the signing key, but this implementation does not include a separate compatibility layer for a future protocol change.
