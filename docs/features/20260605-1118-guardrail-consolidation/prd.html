Guardrail Consolidation — PRD

Finish what ADR-0011 started: migrate every remaining command + content guardrail into the shared guard core, so enforcement is uniform and conformance-checked across every harness. Retire TTSR; leave rules/ advisory-only.

ProblemSolutionBefore/After Policy setsecurity splitModules StoriesScopeADRs

01 Problem

The floor guardrails (read-secret, curl-pipe-shell, broad rm, sudo) live in the shared guard core and enforce everywhere. But a second tier stayed behind as oh-my-pi TTSR rules — cloud teardown, deploys, DB mutation, raw-disk dd, shell-redirect writes, broad chmod, destructive git, and security.md's hardcoded-secret check.

TTSR is oh-my-pi-only. So the same intent is enforced at three different strengths: runtime on omp, guidance-plus-a-few-static-patterns on Claude, and nothing on a future harness with no stream rules. Adding a harness means re-answering "is this one enforced here?" for every pattern. The posture is inconsistent and not provable.

02 Solution

Move all of it into the one detection layer. Each becomes a guardrail policy in the guard core, projected into every harness through its adapter and conformance-checked — no per-harness reimplementation.

05 The security.md split

One file, two fates — drawn along what's safe to hard-block.

→ guard core: no-hardcoded-secret

  • Hardcoded secret literal in write/edit content
  • Matched by known formats — sk-…, AKIA…, PEM private-key header
  • High-confidence, low false-positive → a hard, uniform block
  • Pairs with no-secret-access (don't read ↔ don't write secrets)

stays advisory in rules/security.md

  • String-concatenated SQL
  • eval() on dynamic input
  • exec with string concatenation
  • Unsanitized input → file API
  • Always-on principles (validate input, escape output, authz, strip PII)
  • Too false-positive-prone to hard-block — guidance is the right tool
One core extension: the normalized tool call gains a content field (the write/edit payload the hook already sees). Only no-hardcoded-secret reads it; adapters pass it through; detection stays in the core.

06 Module sketch

Guard core deep

+8 detectors (7 command via the existing traversal, 1 content), +content on the normalized call. no-force-push folds into no-git-destructive.

Policy registry data

+8 entries with floor flags + example/counterExample boundary cases; remove no-force-push.

Per-harness adapters thin

omp adapter + Claude shim forward write/edit content. No detection logic.

Conformance + unit tests tests

per-detector positive/negative (incl. content); matrix auto-extends to the new floor; one content probe.

Rules cleanup content

delete the 7 migrated rule files; split security.md to its advisory remainder.

Validation pipeline gate

retire the TTSR-frontmatter check; assert no rule carries condition:.

07 User stories (18)

  1. Every command guardrail defined once in the core.
  2. Cloud teardown refused on every harness.
  3. DB mutation refused uniformly.
  4. Raw-disk dd refused everywhere.
  5. Deploys refused on every harness.
  6. Broad recursive chmod refused everywhere.
  7. Destructive git refused uniformly (force-push subsumed).
  8. Shell-redirect writes refused everywhere.
  9. Never write a hardcoded secret literal, any harness.
  10. A block stays instructive (right approach in the reason).
  11. New policies on the mandatory floor.
  12. One policy deliberately off-floor (the discriminator).
  13. rules/ is unambiguously advisory-only.
  14. No enforcement hides in frontmatter one harness understands.
  15. The gate asserts the retired mechanism is gone.
  16. pi later inherits everything through one adapter.
  17. Conformance matrix shows no silent gaps.
  18. Claude's static denylist kept as defense-in-depth.

08 Scope

In scope

Migrate 7 command rules → core · split security.md → no-hardcoded-secret · add content to the core · absorb no-force-push into no-git-destructive · widen the floor · delete the 7 rule files · retire TTSR · update the gate.

Out of scope

The pi harness (deferred follow-up) · Gondolin sandbox · the four fuzzy security.md anti-patterns (stay advisory) · any content inspection beyond no-hardcoded-secret · reworking Claude's static deny patterns.
