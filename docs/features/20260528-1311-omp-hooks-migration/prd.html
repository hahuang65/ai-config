PRD — omp Hooks Migration

omp Hooks Migration — PRD

Migrate four TTSR rules with known regex bypasses to omp hooks with structured tool-input parsing, plus add one net-new post-hook for secret redaction. Hooks are omp-only; Claude and OpenCode are unchanged.

Problem statement

What regex couldn't reach

The 12-rule TTSR layer covers most dangerous bash patterns adequately. Four rules, however, have known regex bypasses that markdown-level pattern matching cannot fix — and one entire capability (output redaction) sits outside what TTSR can do at all.

Four TTSR bypasses
One TTSR-impossible capability
  • no-curl-pipe-interpreter  misses bash <(curl URL) and other process-substitution forms
  • no-rm-rf-root  misses find / -delete (different syntax, same destruction) and patterns reached via process substitution
  • no-credentials-read  over-fires on prose mentions in docstrings; under-fires on shell-quoted variants
  • no-sudo  \bsudo\b misses bash <(sudo …), find … -exec sudo …, python -c "os.system('sudo …')"

omp's TTSR mechanism fundamentally cannot mutate tool output — it can only block.

There is no TTSR-shaped solution for redacting secrets that appear in read, bash, or fetch output: env dumps, .env reads not covered by guard-credentials, web responses containing tokens, error messages with connection strings.

Solution

Selective adoption, not replacement

Adopt omp's native hook system selectively — only for patterns that benefit from structured tool-input parsing — alongside the existing TTSR layer rather than replacing it. Per ADR-0006.

Five new hooks
Pipeline + docs
  • 4 pre-hooks replace the bypass-prone TTSR rules; each reads event.input.command or event.input.path as structured value
  • 1 post-hook (redact-keys) for output mutation; placeholder skip avoids docs/fixture noise
  • Each pre-hook returns { block: true, reason } on match
  • Delete the 4 corresponding TTSR .md files — clean migration, no doubled-up enforcement
  • install.sh gains a parallel path for omp/hooks/{pre,post}/*.ts, alongside the existing extensions loop
  • test_omp_hook_shape mirrors existing per-file frontmatter validators
  • README's Triple-Harness Support table updated (omp now has hooks; rule counts 15 → 11)
  • Hooks are omp-only. Claude's hooks.json + curl shell hook byte-for-byte unchanged. OpenCode has no hook system; unchanged.

The 8 TTSR rules without known bypasses (security, git-workflow, no-cloud-destroy, no-shell-write, no-deploy, no-db-mutation, no-dd-disk, no-broad-chmod) stay as-is per ADR-0006's TTSR-stays criteria.

Decision tree · for future authors

When to use hook vs. TTSR

Codified in ADR-0006. The choice depends on whether the pattern lives on the model's output stream or on a tool's structured input, and whether the action needs to be a block or a mutation.

The five hooks · corrected descriptions

What each one does

Four pre-hooks replace bypass-prone TTSR rules; each broadens coverage via structured argv parsing rather than just porting the prior regex verbatim. One post-hook delivers a capability TTSR can't.

guard-rm.ts Pre-hook

Block broad rm

Refuses rm -rf against /, ~, $HOME, ${HOME}, * (and trailing-slash variants ~/, $HOME/), plus find … -delete / find … -exec rm … against the same set, and patterns reached via process substitution.

Deliberately excluded: . and .. are not broad targets — find . -name "*.pyc" -delete is a common safe cleanup. (Post-review fix; the PRD originally listed them.)

Replaces: no-rm-rf-root.md (deleted)

Structured-parse advantage: argv split with substitution recursion catches find / -delete and bash <(rm -rf …) shapes the regex missed.

guard-curl-pipe.ts Pre-hook

Block remote-download → interpreter

Refuses remote download → interpreter pipelines including the bash <(curl URL) process-substitution form and tee-interposer chains.

Replaces: no-curl-pipe-interpreter.md (deleted)

Structured-parse advantage: scans for <(…) process substitution and pipe chains across the parsed cmdline, not just the original regex's literal pipe form.

guard-credentials.ts Pre-hook

Block credential file reads

Refuses reads of credential files across read, edit, and bash tools with per-tool structured input checks. File tools check event.input.path; bash checks parsed argv for any subcommand reading from a credential path. Covers the same 8 path patterns the deleted TTSR covered (.aws/credentials, .kube/config, .ssh/id_*, .netrc, .pgpass, .npmrc, .secrets, generic credentials).

Replaces: no-credentials-read.md (deleted)

Structured-parse advantage: no more over-firing on prose mentions of credential paths in docstrings.

guard-sudo.ts Pre-hook

Block any sudo

Refuses any sudo invocation including bypass shapes: bash <(sudo …), find … -exec sudo …, python -c "os.system('sudo …')".

Replaces: no-sudo.md (deleted)

Structured-parse advantage: finds sudo inside -exec arguments and -c string subcommands the regex couldn't see.

redact-keys.ts Post-hook

Redact secrets in tool output

Multi-tool (read, edit, bash) with 5 regex entries covering 11+ secret shapes:

  • KEY=value alternation: API_KEY, SECRET, TOKEN, PASSWORD, BEARER, AUTH(_TOKEN)?, ACCESS_KEY, PRIVATE_KEY
  • Bearer <token> HTTP-header shape
  • AKIA[A-Z0-9]{16} AWS access key IDs
  • GitHub tokens: gh[pousr]_[A-Za-z0-9]{36,} classic + github_pat_[A-Za-z0-9_]{82,} fine-grained PATs
  • JWT three-segment shape (eyJ…)

Placeholder skip: xxx, your-, your_, placeholder, example, redacted, <…> wrappers, repeated dots, all-same-char runs.

Net new: TTSR fundamentally can't mutate tool output — this is hook-only territory

Further notes · 6 items

Context worth carrying

  • The four deleted rule bodies were the model-facing guidance ("what you tried / why blocked / alternative"). Hooks deliver equivalent guidance via the reason string returned to the model as the tool call's error. The reason will be shorter than the full TTSR body but more targeted — it includes the specific blocked command snippet.
  • Claude Code regressions are zero because the patterns the deleted TTSR rules covered are also blocked by claude/settings.json's per-pattern Bash denylist (Bash(rm *), Bash(curl * | bash*), etc.) plus the curl-to-interpreter shell hook — none of which were touched.
  • OpenCode regressions are zero because OpenCode doesn't load rule files at all; the four deleted .md files were never doing anything for OpenCode users.
  • Live spot-checks before treating any hook as a hardened guard. Each hook should be exercised in omp at least once post-merge with a representative trigger pattern. The PRD codifies the bypass coverage as an intent; only live testing confirms the implementation.
  • The omp/extensions/ install path built in the prior cycle remains relevant — it's the symmetric "extensions vs hooks" split per omp's docs. Extensions can do everything hooks do plus register commands/tools/renderers; this work uses the narrower hook surface because it's the right scope for event handlers only. Future work needing command/tool registration would use omp/extensions/.
  • Possible follow-up: a hook authoring helper. If the four pre-hooks end up sharing significant argv-parsing logic (parseCmd(cmd: string): ParsedCmd with substitution-aware behavior), extract a shared module under omp/hooks/_lib/ (underscore-prefixed so the install loop skips it) and have each hook import from it. Defer until duplication is real, not anticipated.
