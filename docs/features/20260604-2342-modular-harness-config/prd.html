01 Problem

One config source powers multiple AI coding harnesses. Adding a third (pi) and maybe dropping one (oh-my-pi) exposes three pains in today's structure.

Churn
Adding or removing a harness is surgery — each harness's install logic is a hand-written block interleaved with shared content. No clean seam to plug into or delete.
Drift
"Never read secrets", "no curl-pipe-to-shell", "no force-push" each exist as separate per-harness implementations that already disagree. Adding pi adds a third copy. No single source of the guarantee.
Pollution
Harnesses auto-discover each other's config — one reads another's skills directory by default. Changes leak across harnesses and you can't tell what each is actually running.

02 Solution — three moves

Stay a single repo (ADR-0010). Each harness becomes a self-contained module; security becomes a shared policy registry projected through each harness's native mechanism (ports-and-adapters, ADR-0011).

Pluggable harness modules

Each harness owns one directory declaring its config root, consumed shared categories, and guardrail adapter. The installer is a generic loop — add a harness = drop a module; remove = delete a directory. Skills, commands, agents, and advisory rules keep sharing flat and verbatim.

Guardrails: policy → core → adapters

Each guardrail is defined once in the policy registry (ID + intent + metadata). Detection is written once in the guard core. Each harness wires it in via an adapter sized to its enforcement tier — in-process where possible, a thin command shim where not.

Two CI-checked invariants

The isolation test proves no harness sees beyond its module + the curated shared set. The conformance test proves every harness meets the mandatory policy floor and that every other gap is explicit — emitting a coverage matrix.

05 Isolation — push-only, no scavenging

Each config root is owned by exactly one module and contains only what the installer pushed. Cross-discovery is disabled so nothing is pulled from a sibling's home dir.

~/.claude
Claude module files + curated shared set. Nothing from .omp or .pi.
~/.omp/agent
oh-my-pi module files + curated shared set. enableClaudeUser: false.
~/.pi/agent
Reserved slot — same rules apply when pi lands.
Isolation test: fails CI if any config root contains a symlink resolving into a sibling harness's source, or if a cross-discovery flag is left on. A planted leak fixture proves the test actually fires.

06 Module sketch

Confirmed targets. The guard core is the one deep module; adapters are deliberately thin; the two tests are the backbone.

Harness module structure

Self-contained per-harness dir: config root, consumed shared categories, guardrail adapter.

Generic install loop structure

Iterates modules: mirror shared set + module files, disable cross-discovery, prune dangling.

Policy registry data

Canonical guardrail entries — ID + intent + enforcement metadata. Source of truth for what.

Guard core deep module

Detection logic keyed by policy ID behind evaluate(). Absorbs today's duplicated tokenizer / matchers.

Per-harness adapters thin

oh-my-pi in-process (A); Claude shim (B) + retained static denylist. Translate event ↔ verdict only.

Isolation test invariant

Each config root = module files ∪ shared set; no sibling leakage; cross-discovery off.

Conformance test invariant

Every adapter covers every policy ID; floor enforced; no silent gaps; emits the coverage matrix.

Tested directly: guard core (unit — call → verdict), install loop (behavior against a temp HOME), and each invariant test gets a test-the-test fixture (a planted violation that must fail). Adapters stay thin enough to cover via the core + conformance test.

07 User stories

24 stories across four themes — the maintainer wants cheap churn, defined-once security, a provable secrets guarantee, and honest divergence.

    Pluggable modules & install
  1. Each harness lives in one self-contained module.
  2. Add a harness by dropping in one module.
  3. Remove a harness by deleting its directory — no residue.
  4. Installer is a generic loop over modules.
  5. Skills / commands / agents / advisory rules keep sharing verbatim.
  6. Re-running install is idempotent and prunes dangling links.
  7. A clean module-shaped slot waits for pi.
  8. The tier model accommodates harnesses I can't foresee.
    9. Isolation & no pollution
  9. Each config root owned exclusively by one module.
  10. Cross-discovery between harnesses disabled.
  11. A test fails when one root contains another's content.
  12. Shared cross-harness text lives per-root from one neutral source.
    13. Define-once security
  13. Every guardrail defined once with an ID and stated intent.
  14. Detection logic for each policy written once in the core.
  15. Each harness enforces through an adapter sized to its tier.
  16. Programmable harnesses run the core in-process.
  17. A command-hook harness invokes the same core via a shim.
  18. A harness keeps native static guards as defense-in-depth.
  19. The three duplicated guard implementations are consolidated.
    20. Provable guarantee & honest gaps
  20. No harness can ever read my secrets.
  21. A mandatory floor every harness must enforce.

08 Scope

In scope

Restructure to harness modules · generic install loop · isolation (disable cross-discovery + isolation test) · policy registry · guard core consolidating today's duplicated guards · Tier A (oh-my-pi) & Tier B (Claude) adapters · conformance test + coverage matrix + mandatory floor.

Out of scope / deferred

Building the pi module (slot only) · deciding whether to remove oh-my-pi · Gondolin / VM sandboxing (Tier D) · building Tier C/D/E adapters · changing skills/commands/agents/advisory rules · output redaction / post-call mutation.

09 Decisions of record

ADR-0010

Single modular repo with pluggable harness modules; isolation by explicit mirror + disabled cross-discovery + isolation test. Updates ADR-0001 / 0005 for shared content.

ADR-0011

Guardrail policies via ports-and-adapters: registry → guard core → per-harness adapters by tier → conformance test. Supersedes ADR-0004 pillars 1–2; folds in ADR-0006.
