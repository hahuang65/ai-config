Build intent · Advisory guidance and CLI contracts

Agent-facing CLI Ergonomics Spec

Adopt the durable lessons from AXI without importing its runtime, universal format choices, or lifecycle integrations.

Project-owned guidance Three CLI audits No runtime dependency

01 · Problem Statement

Agent-consumed command lines lack one shared contract

The repository has strong conventions for source quality, tests, security, performance, and guardrails, but no focused guidance for an Agent-facing CLI.

Useful practices are consequently distributed across individual executables and can drift: output may be too large or ambiguous, usage mistakes may be silently accepted, and agents may need avoidable discovery calls.

AXI demonstrates promising ergonomics for selected read-only tasks, but its published benchmarks do not isolate all ten principles or establish universal superiority across models and domains.

Importing AXI wholesale would also conflict with existing decisions about lazy guidance, harness ownership, purpose-specific output, and locally owned runtimes.

02 · Solution

Own an outcome-based CLI ergonomics rule

Add one lazy advisory rule for designing and reviewing Agent-facing CLIs.

The rule will require compact and bounded defaults, explicit truncation, useful cheap aggregates, definitive empty states, strict invocation validation, meaningful exit codes, deterministic automation paths, and concise corrective or next-step help.

The guidance will remain format-neutral and will preserve purpose-specific JSON, text, and human terminal interfaces.

Audit review-artifact, review-change, and Orchard against that contract.

Repair objective gaps in the two executables owned by this repository without redesigning their established behavior, and report Orchard findings for its originating repository.

03 · User Stories

Observable outcomes

  1. As a developer building an Agent-facing CLI, I want one focused rule, so that I do not have to reconstruct agent ergonomics from unrelated guidance.
  2. As a model invoking a CLI, I want the smallest useful default response, so that repeated or collection output does not waste context.
  3. As a model receiving long content, I want an explicit truncation notice, total size, and full-content escape, so that I can decide whether another call is justified.
  4. As a model inspecting a collection, I want cheap totals or derived summaries when they prevent a likely follow-up call, so that I can answer complete questions efficiently.
  5. As a model receiving no matches, I want a definitive successful empty state, so that I do not confuse absence with silent failure.
  6. As a model making an invocation mistake, I want unknown input and missing values rejected before work begins, so that plausible output cannot conceal an ignored constraint.
  7. As a model recovering from a usage error, I want a meaningful exit code and concise corrective help, so that I can self-correct in one turn.
  8. As a user of an automation path, I want deterministic non-interactive behavior, so that a command never stalls waiting for terminal input.
  9. As a human CLI user, I want rich terminal presentation to remain available, so that agent ergonomics do not flatten useful interactive experiences.
  10. As a maintainer, I want the guidance loaded only when CLI work is relevant, so that unrelated sessions retain the repository’s small always-on context.
  11. As a maintainer, I want AXI acknowledged at a pinned revision without automatic synchronization, so that upstream evolution cannot silently change local contracts.
  12. As a caller of review-artifact, I want the existing direct-path shorthand preserved, so that stricter parsing does not make the common operation more cumbersome.
  13. As a caller of review-artifact, I want command-specific help and strict flag validation, so that typos, extra arguments, misplaced flags, and missing values fail clearly.
  14. As a caller of review-change, I want its existing read-only TUI and non-interactive summaries preserved, so that an ergonomics audit does not disrupt its human-controlled workflow.
  15. As an Orchard user, I want its human and structured automation interfaces audited against the same outcome-based guidance, so that lifecycle authority remains discoverable and deterministic.
  16. As a maintainer, I want all three executable audits grounded in stable public boundaries, so that conclusions reflect caller-visible behavior rather than implementation preference.

04 · Implementation Decisions

Modules and contracts

CLI ergonomics advisory rule and routing

A project-owned advisory rule will describe observable outcomes rather than mandate AXI mechanisms.

Its metadata and the global instruction bootstrap will use the same relevance trigger so both supported harnesses load it on demand.

The rule remains guidance only; no new guardrail policy or enforcement detector is introduced.

Review artifact invocation contract

One argument boundary will own recognized commands, the direct-path shorthand, command-specific flags, required values, positional cardinality, help text, and usage errors.

Usage failures will exit with status 2 and concise correction, while runtime failures remain status 1.

Successful automation output remains JSON and operational waiting status remains diagnostic output.

Review change invocation contract

The existing argument parser, help, exit semantics, bounded logs, human TUI, and redirected summary behavior will be assessed against the new rule.

Only substantiated contract gaps will be repaired; the audit is not permission to replace its presentation or introduce a new serialization format.

Orchard invocation contract

Orchard’s human help and versioned structured protocol will be audited as public lifecycle interfaces.

The audit will assess discoverability, deterministic automation, bounded output, explicit state, input rejection, exit semantics, and corrective guidance while respecting Orchard as the sole lifecycle authority.

Because Orchard belongs to its originating repository, this branch records substantiated findings but does not duplicate or patch its implementation.

Purpose-specific formats remain valid

TOON is not mandatory.

Each CLI may use compact JSON, JSONL, tailored text, or a human TUI according to its caller contract.

Errors are not universally moved to standard output, and no-argument live data is required only where it is a safe and meaningful default.

Local ownership over upstream synchronization

The guidance is an adapted snapshot attributed to AXI at a pinned source revision.

There is no imported AXI skill, SDK, hook installer, self-update behavior, runtime executable, or automatic upstream synchronization.

Audit and repair scope

The audit covers the two standalone executables owned by this repository plus Orchard.

Objective repairs remain limited to repository-owned code.

Orchard findings stay read-only and identify the originating interface that would need a separate change.

No additional current CLI candidates

The repository’s executable inventory contains installation and test scripts plus two skill-owned entry points.

Installation and test scripts are developer tooling, while status lines, hooks, extensions, and guard adapters are harness integration surfaces rather than Agent-facing CLIs.

Review artifact, Review change, and Orchard therefore form the complete current audit set.

05 · Testing Decisions

Test stable executable and installation seams

CLI ergonomics advisory rule and routing

Test directly through the repository gates.

Content checks will establish valid advisory metadata, paired lazy-load routing, documentation inventory accuracy, and successful projection through installation behavior.

Review artifact invocation contract

Test directly through the executable process boundary.

Behavior tests will cover help, shorthand preservation, accepted command-specific flags, unknown and misplaced flags, missing values, extra positionals, usage exit status 2, runtime exit status 1, and unchanged JSON success output.

Focused runtime tests may cover parser decisions that require exhaustive combinations, but the process boundary remains authoritative.

Review change invocation contract

Test through its existing public CLI and parser seams.

The audit will reuse current behavior evidence for default invocation, strict options, help, usage status, redirected summaries, bounded output, and TUI behavior.

New tests are added only where a substantiated gap requires a repair.

Orchard invocation contract

Audit through its installed public CLI, versioned structured protocol, and originating source evidence.

Safe read-only invocations will establish help, status, protocol, invalid-input, empty-state, and exit behavior without performing lifecycle transitions.

No test or implementation artifact is added to this repository for Orchard itself.

All repository-owned implementation follows one-test, one-implementation red-green-refactor cycles, and the repository-wide gate remains the final verification authority.

06 · Out of Scope

Deliberate exclusions

  • Installing or copying the upstream AXI skill.
  • Adopting the AXI SDK or adding a TOON dependency.
  • Mandating TOON, errors on standard output, executable-path disclosure, or live no-argument data.
  • Adding session-start hooks, session-end capture, built-in self-update, or another harness configuration writer.
  • Installing gh-axi, chrome-devtools-axi, or other catalog executables.
  • Changing guardrail coverage for external wrapper commands.
  • Redesigning the Review change TUI, report, isolation lifecycle, or approval behavior.
  • Modifying Orchard or its originating repository as part of this branch.
  • Auditing external executables other than Orchard.
  • Claiming that AXI’s benchmarks prove all ten principles or generalize to every model and domain.
