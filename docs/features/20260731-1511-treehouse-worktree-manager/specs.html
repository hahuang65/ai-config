Feature specification · ADR-0019

Treehouse Worktree Manager Spec

A shared, conservative worktree manager that combines reusable environments with ordinary named branches, while letting terminal users, Claude Code, pi, and the build pipeline enter the same lifecycle safely.

macOS + Linux Node.js 22+ Fast-forward integration No automatic push No configuration files
Problem· Solution· User stories· Implementation· Testing· Out of scope

Problem Statement

Git worktrees provide isolation, but ad hoc worktrees accumulate stale directories, duplicate setup costs, detached commits, ambiguous ownership, and unsafe cleanup habits.

A purely detached reusable pool improves environment reuse but weakens branch recoverability, while ordinary branch-bound worktrees are recoverable but often treated as disposable clones.

AI harnesses add another gap: creating a worktree does not move the current interaction into it, so users are asked to start another terminal or agent and manually transfer context. Pi additionally restricts session replacement to user-submitted extension commands, so an LLM tool cannot perform that privileged transition directly.

The repository also needs one integration policy across human and automated callers: trunk must only advance from the main project directory, never through another task worktree, and a successful commit must not silently become a merge or push.

Solution

Treehouse manages a bounded pool per project beneath ~/.treehouse/. Available worktrees are clean detached slots aligned with trunk. Acquiring a slot attaches it to a named feature branch and exposes it at a readable intent-based path. Recycling reverses that transition only after the work is clean and proven landed.

Available→ acquire or convert → Task worktree→ land + clean → Available

The Git dotfiles repository owns the sole lifecycle implementation and installs the Treehouse CLI as baseline Git tooling. AI skills and harness adapters contain no duplicate Git lifecycle logic: they invoke the installed CLI through its versioned structured protocol, then perform native same-window transitions that a child process cannot perform for its parent. Terminal callers use a managed shell, Claude Code uses its native existing-worktree operation, and pi preloads one authenticated transition command for the user to submit with a single Enter keypress before replacing its session in the same visible TUI with a cwd-bound fork. The build pipeline only requires worktree isolation and delegates to Treehouse when it starts outside any linked worktree.

Integration is explicit and local. Treehouse fast-forwards trunk from the main project directory, never pushes, returns the active caller to the main directory before default cleanup, and leaves landed work intact if that return transition cannot complete.

Treehouse workflows fail closed when the executable is absent or protocol-incompatible. Build is the sole degraded-mode exception: when it starts outside a linked worktree and preflight fails before acquisition, it warns and asks whether to continue on an ordinary local task branch. That fallback is never automatic or Treehouse-managed and cannot use the Treehouse merge workflow.

User Stories

  1. As a developer, I want ordinary tasks to use a local task branch by default, so that worktrees appear only when I explicitly request isolation.
  2. As a build-pipeline user, I want a build started in the main project directory to acquire and enter a task worktree with at most one native pi confirmation, so that the required isolation creates no manual context handoff.
  3. As a build-pipeline user already inside any linked worktree, I want the build to continue there uninterrupted, so that Treehouse does not adopt or relocate work managed elsewhere.
  4. As a developer, I want each repository to have its own bounded project group, so that pools, locks, and lifecycle state cannot cross project boundaries.
  5. As a developer with repositories sharing a basename, I want only the newly discovered collision to receive a parent-qualified group name, so that established paths remain stable.
  6. As a developer, I want a new task worktree to use a normalized intent and named feature branch, so that its purpose and recovery path remain obvious.
  7. As a developer, I want Treehouse to honor my trusted global branch-creation alias when present, so that branch naming follows my established convention.
  8. As a security-conscious developer, I want repository-local shell aliases treated as untrusted, so that entering a repository never executes project-supplied shell code implicitly.
  9. As a developer, I want online acquisition to begin from clean synchronized trunk, so that new work does not silently branch from stale integration state.
  10. As an offline developer, I want an explicit offline mode that uses local trunk, so that lack of network access is intentional rather than mistaken for synchronization.
  11. As a developer with staged, unstaged, or untracked work on a local task branch, I want conversion to preserve it recoverably, so that choosing isolation cannot lose work or change branch identity.
  12. As a developer converting a branch, I want ignored files left in the original working directory, so that large or machine-local artifacts are not copied unexpectedly.
  13. As a developer, I want an acquired or converted worktree to open in my current interaction, with pi requiring only one prefilled Enter confirmation, so that I do not start another visible agent or terminal.
  14. As a developer, I want a failed harness transition to leave the created worktree intact and report its path, so that continuation failure never becomes data loss.
  15. As an automation caller, I want path and JSON output modes that do not open an interactive shell, so that scripts can compose Treehouse safely.
  16. As a developer, I want bare treehouse to show relevant status, so that the common inspection path requires no subcommand.
  17. As a developer inside a repository, I want status scoped to that project unless I request all projects, so that routine output stays focused.
  18. As a developer outside a repository, I want status to summarize every project group, so that I can audit Treehouse globally.
  19. As a developer, I want to enter an existing task worktree without mutating its lifecycle, so that reopening work is distinct from creating or converting it.
  20. As a developer, I want Treehouse to refuse concurrent entry by default and require explicit shared use, so that two callers do not unknowingly edit the same checkout.
  21. As a developer, I want capacity to default to four total active-plus-available slots per project and be overridable by a positive environment value, so that resource use is bounded without configuration files.
  22. As a developer at capacity, I want acquisition to fail clearly rather than evict active or unlanded work, so that capacity pressure never discards work.
  23. As a developer, I want merge to fast-forward trunk only when it can reach the exact feature tip directly, so that integration never creates an unexpected merge commit or rewrites history.
  24. As a developer, I want a rejected fast-forward to leave both checkouts and my location unchanged, so that conflict resolution remains an explicit follow-up.
  25. As a developer, I want merge to remain local and never push, so that remote publication is always a separate decision.
  26. As a developer, I want successful default merge to return me to the main project directory before recycling, so that my current tools never point at a removed or repurposed checkout.
  27. As a developer, I want transition failure after a valid merge to leave the landed worktree and branch intact, so that cleanup can be retried without rolling trunk backward.
  28. As a developer, I want a keep option to preserve the landed task worktree, branch, and current location, so that cleanup remains optional.
  29. As a harness user, I want /merge to be a thin alias for Treehouse merge, so that convenient integration cannot drift from the canonical safety rules.
  30. As a developer, I want /commit to stop after creating a focused commit, so that committing never merges, rebases, pushes, switches branches, or changes worktree lifecycle.
  31. As a developer, I want recycling to require clean, landed work, so that an available slot never conceals uncommitted or unintegrated changes.
  32. As a maintainer, I want pruning to preview by default, recycle landed tasks first, and delete only excess available slots, so that pool reduction is conservative.
  33. As a maintainer, I want destruction to preview by default and independently gate unlanded, in-use, unverifiable, and branch-deletion risks, so that broad cleanup requires precise authorization.
  34. As a concurrent caller, I want project mutations serialized through a filesystem lock and atomic state writes, so that parallel commands cannot corrupt pool ownership.
  35. As a developer after a crash, I want stale ownership recovered conservatively and ambiguous worktrees quarantined, so that uncertain state is never recycled automatically.
  36. As a developer using squash or rebase merges, I want read-only pull-request metadata consulted only after ancestry cannot prove landing, so that remote evidence supplements rather than overrides Git.
  37. As a new user, I want comprehensive top-level and per-command help, so that every behavior, safety gate, option, and exit outcome is discoverable without external documentation.
  38. As an installer, I want Git dotfiles to install the standalone lifecycle CLI and AI dotfiles to install only thin harness integrations, so that Treehouse remains baseline Git functionality without cross-harness leakage or implementation duplication.
  39. As a build-pipeline user without a compatible Treehouse executable, I want a clear warning and an explicit choice to use a normal local task branch, so that missing optional isolation tooling does not silently change or completely block my workflow.
  40. As a harness user, I want approved Treehouse CLI and native transition operations to run without repeated permission prompts, so that lifecycle safety comes from Treehouse invariants rather than broad shell authorization.

Implementation Decisions

Architecture and ownership

One lifecycle authority

The Treehouse service in the Git dotfiles repository owns every Git and filesystem state transition. CLI commands submit structured requests, while AI skills and harness adapters consume versioned structured outcomes rather than importing or reimplementing lifecycle behavior.

Repository ownership follows responsibility

The Git dotfiles repository owns the executable, runtime, CLI tests, and command installation. The AI dotfiles repository owns only Treehouse skills, workflow policy, and native harness-transition adapters.

Treehouse owns caller transition

Creation, conversion, and entry include continuation into the selected task worktree for interactive callers. The CLI returns a validated transition outcome to AI callers, their adapter performs the native parent-session transition, and build never contains harness-switching logic. Pi alone preloads a one-time authenticated command and waits for one Enter keypress because its session-control API is restricted to user-submitted extension commands.

Daemonless durable state

Project state lives with its pool and is changed under a filesystem lock using atomic replacement. Process ownership and session claims are validated on macOS and Linux without a long-running daemon.

Conservative recovery

Git metadata is authoritative when rebuilding state. Missing owners may be cleared after liveness validation; conflicting or unverifiable worktrees are quarantined and excluded from acquisition.

Project groups and pool layout

Each repository owns ~/.treehouse/<project>/, containing readable active directories by normalized intent, hidden available slots beneath .pool/, durable state, and a project lock. Capacity counts both task and available worktrees and defaults to four through TREEHOUSE_MAX_TREES. The value must be a positive integer.

A project group normally uses the main project directory basename. When another repository already owns that name, the established group remains unchanged and only the newly discovered repository receives a parent-qualified name. Renaming an already registered project is not supported.

Command contract

Bare treehouse is equivalent to treehouse status. The command set is new, convert, status, enter, merge, recycle, prune, and destroy. Every command provides comprehensive help, stable nonzero failures, human-readable output, and machine-readable output where automation needs it.

  • new synchronizes clean trunk, creates a normalized named branch, acquires a slot, and transitions the interactive caller. Explicit offline mode uses local trunk.
  • convert requires a local task branch and uses recoverable temporary Git state to preserve staged, unstaged, and untracked changes. Ignored files remain behind.
  • status scopes to the current project in a repository and all projects otherwise. It supports explicit all-project, refresh, and JSON modes.
  • enter opens an existing task worktree without lifecycle mutation. It refuses active sharing unless explicitly permitted.
  • merge validates, fast-forwards trunk from the main project directory, transitions the default caller back, then recycles. It never pushes.
  • recycle accepts only clean, landed, unoccupied managed task worktrees and removes the completed local branch unless kept.
  • prune is preview-only by default, recycles eligible landed work first, and removes only excess available slots.
  • destroy is preview-only by default and has independent explicit gates for unlanded work, live use, unverifiable state, and branch deletion.

Human new, convert, and enter use a managed child shell. Automation uses path or JSON modes and never receives an implicit shell. Bulk operations are always bounded to one named project group.

Git and landing policy

Treehouse resolves trunk from repository metadata and never assumes its name. Online acquisition requires a clean main project directory on trunk. If a trusted user-level git sync alias exists, Treehouse runs it and verifies the required postconditions; alias failure stops acquisition. Without the alias, Treehouse performs explicit fetch, fast-forward update, prune, and submodule synchronization. Repository-local shell aliases never execute automatically.

Branch creation prefers a trusted user-level git new alias and verifies the resulting branch and checkout. Without it, Treehouse creates an ordinary unprefixed branch. Inputs are passed as argument arrays rather than shell-concatenated commands.

Landing uses ancestry first. Read-only GitHub pull-request metadata is consulted only to recognize squash or rebase landing that cannot preserve exact-tip ancestry. Unknown forge state remains unverifiable rather than guessed.

Harness and shell transitions

Claude Code claims Treehouse ownership for its live parent process, enters the existing registered task worktree through EnterWorktree, and keeps the current conversation. On default return it calls ExitWorktree with keep behavior, which restores the original main project directory without allowing Claude Code to remove the Treehouse-owned worktree; it then releases the exact owner token before Treehouse finalizes cleanup. Pi uses a user-level extension to fork the persisted conversation into the target cwd and switch the same TUI session. Cwd-bound tools, instructions, resources, and trust are rebuilt in both harnesses. Neither path depends on changing the process cwd as an implementation accident.

The pi adapter invokes the CLI in machine mode, validates the transition, stores a one-time authenticated request, preloads its internal slash command into an otherwise empty editor, and terminates the initiating tool turn. The user presses Enter once; pi then executes the command with its privileged command context, performs the session replacement, and resumes with a generic instruction to continue the requesting workflow. No command text must be typed or copied, and no additional model turn occurs before transition.

If the editor already contains a draft, the adapter refuses to overwrite it and reports the preserved task path. Clearing or declining the prefilled command leaves the worktree and ownership intact for later entry. Invalid, replayed, or expired tokens fail closed. Native transition failure likewise reports the CLI-provided safe target and stops without launching another agent or creating a handoff artifact.

A successful default merge performs the Git integration first from the main project directory, then preloads the same one-Enter return confirmation before cleanup. Cleanup runs only after the current pi interaction has returned to the main directory. If confirmation or return fails, trunk remains advanced and the landed task worktree remains attached and occupied for later recycling. A keep option skips both return and cleanup.

Workflow boundaries

The Treehouse skill is the harness-neutral AI workflow surface and delegates lifecycle requests to the installed CLI. /merge forwards unchanged arguments to its merge flow and refuses outside a managed task worktree. Neither skill has an independent Git integration implementation.

Build continues in any existing linked worktree without adoption and without requiring the Treehouse executable. When started from the main project directory or another non-worktree checkout, it first verifies executable availability and protocol compatibility, then delegates acquisition and entry to Treehouse and resumes its existing phase after transition.

If that preflight fails before Treehouse mutates state, build warns that isolation and the Treehouse merge workflow will be unavailable and asks whether to continue on an ordinary local task branch. Declining stops with Git dotfiles installation guidance. Acceptance authorizes only the established branch workflow, not duplicated worktree management. Missing executables never trigger an automatic fallback, and acquisition or native-transition failures preserve the task worktree and stop without offering branch fallback. The four existing approval gates remain unchanged.

The commit skill is checkout-local. It may inspect state, stage an unambiguous logical change, and create one commit. It never invokes Treehouse, changes branch or worktree lifecycle, merges, rebases, pushes, or chains into the merge skill. Integration is always a separate explicit action.

Shared delivery and compatibility

The executable requires Node.js 22 or newer and initially supports macOS and Linux. The Git dotfiles installer exposes treehouse/bin/treehouse.mjs at ~/.local/bin/treehouse. The AI installer never installs or vendors the executable; it installs the shared skills and pi transition adapter, while Claude uses its native worktree capability through the shared skill.

The CLI machine interface includes a protocol version so independently installed AI adapters can reject incompatible outcomes safely. Standalone Treehouse and merge workflows stop with actionable Git dotfiles installation guidance when the executable is absent and reject incompatible protocol versions before mutation. The AI installer may be used independently and does not fail merely because the separate executable has not yet been installed.

No Treehouse configuration file is introduced. The only configuration input is optional pool capacity through the environment. Both repository installers remain independently idempotent, and AI installation preserves harness-module isolation.

Claude Code permissions allow only executable discovery, direct treehouse invocations, and the native EnterWorktree/ExitWorktree tools. Pi invokes Treehouse through its registered extension tool and authenticated command without a separate shell permission prompt. Neither harness receives a broad Git or shell bypass, and mandatory guardrail hooks remain active.

Safety invariant: uncertain state is preserved, not cleaned. No capacity, synchronization, merge, prune, destroy, transition, or recovery failure may discard staged, unstaged, untracked, unlanded, occupied, or unverifiable work.

Testing Decisions

Behavior follows red-green-refactor TDD and is tested through stable public interfaces. Real temporary Git repositories are preferred over mocks for lifecycle behavior. Process, forge, and harness boundaries use controlled fakes where deterministic failure injection is required.

Treehouse service

Test directly through its structured request interface. Cover lifecycle transitions, invariants, capacity, idempotence, safe partial success, and error classification independently of presentation.

Git workspace gateway

Test directly through its public repository interface. Use real temporary repositories for trunk discovery, aliases, synchronization, conversion state, fast-forward checks, branch cleanup, ancestry, submodules, and failure recovery. Fake only network and forge responses.

Project registry

Test directly through its registry interface. Exercise naming collisions, capacity parsing, atomic writes, lock contention, ownership liveness, stale claims, reconstruction, quarantine, and concurrent acquisition.

Treehouse CLI

Test directly in the Git dotfiles repository as the highest user-facing command interface. Spawn the executable with isolated home directories and temporary repositories. Cover every command, default status behavior, complete help, exit codes, dry runs, path output, versioned JSON schemas, offline behavior, and noninteractive refusal paths.

Harness transition layer

Test in the AI dotfiles repository through the CLI protocol boundary and each registered harness contract. Drive a fake executable outcome and extension API for pi registration, empty-editor validation, authenticated command prefill, one-time token rejection, cancellation, session replacement, continuation, incompatibility, and failure cleanup, with targeted integration against session-manager behavior. Cover Claude through the Treehouse workflow contract because its cwd switch is a native harness interface rather than duplicated product code.

Workflow skills

Cover through the authoring contract plus fake executable and transition seams. Content checks pin that Treehouse owns transitions, build delegates only when outside a linked worktree, missing or incompatible executables fail closed except for build's explicitly approved local-branch fallback, merge is a thin alias, commit cannot integrate, and no handoff-file workflow returns. Prompt files do not duplicate lifecycle tests.

Installer projection

Test each repository through its throwaway-home install interface. The Git dotfiles tests verify executable installation and idempotence. The AI dotfiles tests verify skills, the pi adapter, protocol-boundary expectations, narrowly scoped Claude permissions, dangling-link cleanup, and the absence of both executable ownership and cross-harness pollution.

Out of Scope

  • Windows support.
  • Migration of pre-existing flat worktrees into project groups.
  • Renaming or moving an established project group when the repository directory changes.
  • Treehouse configuration files or per-repository configuration.
  • Setup hooks, setup command flags, ignored-file copying, or explicit cache warming.
  • Automatic pushes, pull-request creation, remote branch deletion, merge commits, rebases, or history rewriting.
  • First Mate-style terminal backends, child-agent supervision, job scheduling, message injection, or parallel-agent orchestration.
  • Automatic adoption, relocation, merge cleanup, or lifecycle tracking for unmanaged worktrees.
  • Automatic integration from the commit skill or an implicit post-commit action.
  • Destructive cleanup based on age, capacity pressure, branch name, or uncertain remote state.

Further Notes

ADR-0019 is the authoritative rationale for the hybrid pooled, branch-bound lifecycle and the boundary between Treehouse, build, merge, and commit workflows.

Environment reuse is an optimization, not a safety argument. A worktree becomes reusable only after its task identity has been detached through verified recycling.

The native same-window transition replaces the previously considered conversion handoff file and pickup behavior. Handoff and pickup remain independent tools for intentionally transferring work between separate sessions.
