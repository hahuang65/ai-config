01

Problem statement

Reloading shows the answer, but not what changed.

An open review already live-reloads when its canonical HTML changes, but the reviewer must scan the whole document to find the revised intent.

The cost grows with the document

A small revision can be difficult to locate in a long Spec, Tasks document, or review report.

This is especially costly when feedback on one artifact forces an upstream artifact to be revised and reviewed again.

The reviewer needs a clear view of only the newest saved revision without turning the review runtime into another source of truth.

Current constraints

  • The canonical HTML must remain unchanged by review controls.
  • Scroll and annotation mode already survive live reload.
  • The sandbox keeps the shell separate from the artifact DOM.
  • Review must continue when comparison cannot complete.
02

Solution

Compare settled artifact revisions in the browser.

The review runtime captures a bounded settled rendering after each load, compares consecutive artifact revisions, and presents the resulting changed regions as temporary review UI.

Clean start

No initial highlight

The first open, a full shell refresh, and a newly opened tab establish a baseline without implying that the whole artifact is new.

Focused revision

Only the latest changes

Added, Updated, Moved, and Removed regions remain marked until another artifact revision arrives or the reviewer dismisses them.

Safe fallback

Review always continues

Bounded comparison failures produce one plain status marker and never block, mutate, or repeatedly reload the artifact.

01 Settle

Wait for a bounded stable rendered state after load.

02 Capture

Keep a bounded semantic snapshot in the current browser tab.

03 Compare

Match conservatively and find the smallest changed regions.

04 Present

Draw runtime rails and type badges without changing layout.

05 Navigate

Let the reviewer move through or dismiss the newest change set.

03

User stories

The complete reviewer experience.

  1. As a reviewer, I want the initial artifact render to have no change highlight, so that opening an existing document does not imply that all content is new.
  2. As a reviewer, I want a live reload to identify only review-visible changes from the newest saved revision, so that I can inspect revised intent quickly.
  3. As a reviewer, I want additions, updates, moves, and removals to have plain-language labels, so that I understand why each region is marked.
  4. As a reviewer, I want text, relevant attributes, visible computed styles, and semantic ordering to participate in comparison, so that meaningful visual and content revisions are not missed.
  5. As a reviewer, I want interactions made after the prior artifact load to stay outside the comparison baseline, so that expanding a section or using a form does not create false changes.
  6. As a reviewer, I want my scroll position preserved when a reload completes, so that the runtime does not interrupt the part of the artifact I am reading.
  7. As a reviewer, I want a changed-region count with wrapping Previous and Next controls, so that I can find offscreen changes when I choose.
  8. As a reviewer, I want Previous or Next to select and scroll to one region at a time, so that navigation is deliberate and the current region is clear.
  9. As a reviewer, I want to dismiss the latest-change highlight, so that I can return to an unmarked artifact until another revision arrives.
  10. As a reviewer, I want removed content represented at the nearest surviving container without restoring deleted text, so that deletion is visible without falsifying the current artifact.
  11. As a reviewer, I want annotation outlines to remain clear on highlighted regions, so that giving feedback and locating prior annotations continue to work.
  12. As a reviewer, I want rapid saves to coalesce into the newest settled revision, so that I do not see highlights for intermediate states that never became reviewable.
  13. As a reviewer, I want an unchanged reload to clear the previous highlight without creating a new one, so that the view always represents the newest artifact revision.
  14. As a reviewer, I want oversized or unstable artifacts to report that detailed comparison is limited or unavailable, so that review remains usable and does not silently mislead me.
  15. As a reviewer with the same session open in multiple tabs, I want each tab to own its own baseline, so that a tab compares only revisions it actually rendered.
  16. As an artifact author, I want all snapshot, comparison, and highlight state to remain bounded and in browser memory, so that the canonical HTML and durable review state remain unchanged.
  17. As a runtime maintainer, I want malformed or stale cross-frame messages rejected, so that rapid reloads cannot apply an old comparison result to a newer artifact.
  18. As a current keyboard or reduced-motion user, I want the existing review controls and reduced-motion behavior to keep working, so that this feature does not regress established behavior.
04

Implementation decisions

State stays local; boundaries stay narrow.

The implementation follows ADR-0018: canonical semantic HTML remains authoritative, while the review runtime owns temporary presentation and browser interaction.

Deep module

Artifact revision engine

Captures bounded settled semantic snapshots and compares two revisions to produce conservative, non-overlapping changed regions.

Public interface: capture a revision and compare two revisions under explicit limits.

Deep module

Reload lifecycle coordinator

Owns each tab’s baseline, reload generation, rapid-save coalescing, stale-result rejection, dismissal state, and fail-open recovery.

Public interface: accept lifecycle events and issue bounded frame and presentation actions.

Artifact-side view

Artifact change view

Maps current changed regions to pointer-free overlays, removal anchors, active navigation, and annotation-priority behavior inside the iframe.

Public interface: the rendered browser review surface.

Shell-side view

Shell change bar

Shows the changed-region count, comparison status, and wrapping Previous, Next, and Dismiss controls above the iframe.

Public interface: the rendered browser review surface.

Trust boundary

Cross-frame message contract

Validates bounded snapshots, generation identifiers, comparison commands, and results while preserving source-window checks.

Public interface: shell-message and frame-message validators.

Change semantics

Type What qualifies Where the marker appears
Added A new semantic element or newly visible rendered content has no conservative match in the prior revision. The smallest new semantic element.
Updated Matched content changes in direct text, relevant attributes, or the bounded visible computed-style set. The smallest matched semantic owner that explains the update.
Moved A matched element changes relative order among matched siblings without geometry-only noise. The moved element, combined with Updated when both apply.
Removed A prior semantic element has no conservative match in the current revision. The nearest matched surviving container, or a page marker when none is useful.

Matching and granularity

  • Match unique stable identifiers and task metadata first.
  • Use conservative structural and text anchors only when unique.
  • Use the closest unambiguous container instead of guessing.
  • Do not duplicate a descendant change on every ancestor.
  • Count an ancestor separately only for its own attributes, direct text, or child structure.

Snapshot boundary

  • Capture after a bounded stable period and exclude runtime review UI.
  • Keep the settled snapshot from each load rather than the interaction-mutated DOM at save time.
  • Include a bounded set of visible computed styles, including visibility, generated content, color, typography, spacing, and size.
  • Exclude document metadata, script source, hidden automation metadata, and geometry-only responsive changes.

Reload lifecycle

  • The first settled load establishes a silent baseline.
  • Rapid source saves retain the last settled baseline and replace unfinished target loads with the newest available state.
  • Generation identifiers prevent stale snapshots or results from becoming current.
  • A successful comparison promotes the newest snapshot to the next baseline even when no changed regions exist.
  • A failed comparison resets the baseline chain before later comparisons resume.

Presentation

  • The change bar appears above the iframe only when a result or status marker exists.
  • No region is active after reload, so scroll remains preserved.
  • Next initially selects the first region and Previous initially selects the last.
  • Overlays use a patterned leading rail and visible type badge without changing artifact layout.
  • Annotation hover and locate outlines take priority while the change rail and badge remain visible.

Bounds and failure

  • Cap settlement duration, scanned elements, depth, text, attributes, computed styles, snapshot bytes, and displayed changed regions.
  • Reject malformed messages and ignore stale generations.
  • Use one page-level “Detailed highlights are limited” marker when comparison exceeds limits.
  • Use one page-level “Change comparison unavailable” marker when capture, settlement, comparison, or rendering fails.
  • Clear stale highlights and keep the review fully usable in every failure case.

Ownership

  • The shell owns the prior snapshot because it survives iframe replacement but not a shell refresh.
  • The current iframe owns current element references, overlays, and navigation targets.
  • The server continues to emit reload events without storing or comparing revision content.
  • Snapshots never enter durable session state, browser storage, or cross-tab synchronization.
  • Dismissal removes presentation but preserves the current revision as the next comparison baseline.
Accessibility scope for this version. The feature uses visible text labels and native shell buttons, but it adds no announcements, focus movement, focus restoration, or new keyboard shortcuts. Existing keyboard operation and reduced-motion behavior must not regress.

Testing decisions

Pin behavior at deep interfaces and in Firefox.

Tests follow the existing runtime pattern: deterministic modules cover exhaustive comparison and lifecycle cases, while real browser evidence proves the integrated shell and sandboxed iframe behavior.

Test directly

Artifact revision engine

Use its capture-and-compare interface to cover text, relevant attributes, computed styles, additions, removals, sibling moves, combined labels, ambiguous identity, non-overlapping regions, bounds, and unstable-state failure.

Test directly

Reload lifecycle coordinator

Use its event interface with controlled time to cover silent initial baselines, rapid-save coalescing, stale generations, unchanged revisions, dismissal, baseline promotion, and recovery after failed comparison.

Test directly

Cross-frame message contract

Use the validators to prove valid message acceptance and rejection of malformed, oversized, unknown, and stale payloads.

Covered through browser

Artifact change view and shell change bar

Use a real Firefox review session because overlays, iframe scrolling, sandbox messages, annotation priority, and controls are user-visible integration behavior.

06

Out of scope

Deliberate exclusions keep the first version bounded.

Not part of comparison

  • Referenced CSS, JavaScript, image, or sibling HTML saves that do not trigger a canonical HTML reload.
  • Pixel comparison for canvas, images, video, or other rasterized output.
  • Script source, document metadata, hidden automation metadata, or runtime review UI.
  • DOM changes caused only by user interaction after the previous settled load.
  • Geometry changes caused only by viewport size, font loading, or responsive layout.

Not part of presentation

  • Persistent change history or navigation across older revisions.
  • Cross-tab synchronization or durable snapshot storage.
  • Automatic scrolling or focus movement when a reload completes.
  • Timed highlight expiry or an undo action after Dismiss.
  • New announcements, focus management, keyboard shortcuts, or accessibility navigation.
  • Any rewrite of canonical HTML to add runtime controls or markers.
07

Further notes

Durable context for implementation.

Canonical immutability is non-negotiable

The source artifact remains the only durable content model.

Snapshots, comparison results, bars, rails, badges, and removal markers are temporary browser presentation.

No new architectural decision

This feature extends the existing HTML-native review decision in ADR-0018.

The detailed UX and comparison policy are reversible runtime behavior, so they do not require a new project-wide decision record.
