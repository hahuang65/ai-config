01 · Intent

Put visual judgment before specification

Problem Statement

The build pipeline can approve a detailed Spec without first showing the user what a material browser or terminal interface will look like or how its important states will behave.

Ad hoc prototypes and one-off HTML files do not give every relevant feature the same durable review path.

Solution

Add a standalone mockup workflow that creates canonical mockups.html after grilling and before the Spec when the agreed scope contains material UI design.

Review the artifact through the existing review artifact workflow, then use explicit approval to clear the Design→Spec gate and carry the selected design through tasks, implementation, and Review change.

02 · User stories

Observable outcomes

  1. As a build user, I want material UI changes mocked up before the Spec, so that I can judge the interface before implementation intent is fixed.
  2. As a build user, I want non-UI work to skip mockups, so that the pipeline does not add unnecessary review work.
  3. As a build user, I want browser and terminal interfaces treated consistently, so that either kind of end-user surface receives design review.
  4. As a build user, I want small copy edits, mechanical styling repairs, and internal changes excluded, so that the trigger remains proportional.
  5. As a build user, I want one recommended interactive design by default, so that review begins from a clear proposal.
  6. As a build user, I want alternatives only for a real unresolved design fork, so that variants add information rather than noise.
  7. As a build user, I want alternatives to differ in structure, hierarchy, or primary action, so that each option represents a meaningful choice.
  8. As a build user, I want realistic content and important states in the mockup, so that I can assess density, errors, loading, empty states, and interaction behavior.
  9. As a build user, I want responsive and accessible behavior represented, so that the selected design does not assume one viewport or input method.
  10. As a build user, I want to annotate the mockup and request revisions, so that exact elements and text can be corrected before approval.
  11. As a build user, I want explicit mockup approval to continue directly to the Spec, so that there is one unambiguous Design→Spec signal.
  12. As a build user, I want non-UI builds to retain post-grill chat confirmation, so that both paths share one approval boundary.
  13. As a build user, I want the pipeline to retain exactly four approval gates, so that conditional mockups do not add another phase boundary.
  14. As a build user, I want the selected design and rationale preserved, so that later phases understand why it won.
  15. As a build user, I want rejected alternatives retained as decision context, so that later work does not reopen settled options without cause.
  16. As an implementer, I want the approved mockup read with the Spec and Tasks, so that UI implementation follows the same Authoritative intent.
  17. As an implementer, I want behavior and hierarchy to be binding while decorative details remain directional, so that implementation does not become a pixel-matching exercise.
  18. As a reviewer, I want material UI drift substantiated with focused evidence, so that Review change does not claim conformance without support.
  19. As a reviewer, I want insufficient visual evidence reported as an ask-user Finding, so that uncertainty remains visible.
  20. As a standalone Spec user, I want a missing relevant mockup detected before synthesis, so that standalone use keeps the same design prerequisite.
  21. As a prototype user, I want mockup timing based on the prototype question, so that presentation scaffolding does not block logic or data exploration.
  22. As a prototype user, I want mockup first when end-user UI design is the subject or an imperative prerequisite, so that the runnable experiment starts from settled visual intent.
  23. As a pipeline maintainer, I want guides, context files, and content gates updated together, so that both harnesses receive one consistent workflow.
03 · Implementation decisions

One conditional workflow, one intent thread

Standalone workflow

mockup is a reusable skill rather than behavior embedded in spec. Build conditionally orchestrates it, and standalone Spec checks the same prerequisite.

Relevance test

Run for a new or materially changed end-user layout, interaction flow, information hierarchy, responsive behavior, or visual state. Ask only when code and grilled scope leave relevance ambiguous.

Canonical artifact

mockups.html is self-contained semantic HTML in the Feature directory. It shows affected surfaces, realistic states, responsive intent, accessibility behavior, and any true alternatives.

Review and gate

Open the mockup as an approval review. For relevant UI, approval clears the Design→Spec gate; otherwise post-grill chat confirmation clears that same first boundary.

Selection record

After feedback settles, the artifact visibly identifies the selected direction and rationale while preserving rejected alternatives as decision context.

Authority boundary

Hierarchy, interaction, important states, responsive intent, and accessibility behavior are authoritative. Dimensions and decorative styling are directional unless explicitly marked as required.

Synchronization

Spec, Tasks, implementation, and Review change read the mockup when present. A material UI change returns to the mockup; an already-approved Spec then needs renewed approval before tasks continue.

Validation evidence

Review change uses the smallest available behavior tests, browser checks, rendered screenshots, or documented manual checks. Missing evidence becomes an ask-user Finding.

Prototype ordering

Run mockup first only when end-user interface design is the prototype subject or an imperative prerequisite. If UI only presents logic, data exploration, or manual processing, answer the primary question first and leave optional mockup work until last.

Existing runtime

Reuse the review artifact workflow unchanged. Skill installation remains directory-driven, so the new workflow projects into both harnesses without a same-named Command.

Decision source: ADR-0030 records why mockup is conditional, standalone, ordered before the Spec, and folded into the existing first approval boundary.

05 · Testing decisions

Verify the installed workflow contract

  • Extend the repository content gate so it fails when the mockup skill omits relevance, canonical artifact, meaningful-variant, approval, or authority rules.
  • Assert that Build loads the mockup skill directly, preserves exactly four approval gates, and defines both branches of the Design→Spec gate.
  • Assert that Spec, Tasks, code, coach, and build-mode Review change read approved mockups when present and apply the synchronization rule.
  • Assert that Prototype distinguishes end-user interface design from UI used only as a presentation layer and orders mockup work accordingly.
  • Use the existing authoring gate for frontmatter, reference resolution, guide consistency, duplicate Command rejection, ADR numbering, installation, and harness isolation.
  • Run the complete repository gate because shared skills and installation behavior affect both harnesses.
06 · Boundaries

Out of Scope

  • Changing the review artifact runtime or adding a second browser-review implementation.
  • Requiring mockups for internal work, minor copy edits, mechanical visual repairs, or every prototype.
  • Replacing runnable prototypes with static HTML.
  • Promoting mockup or prototype code directly into production.
  • Pixel-level automated comparison or treating every decorative choice as binding.
  • Adding a fifth pipeline approval gate or a same-named Command.
  • Creating a mockup for this workflow-only feature, which does not add an end-user browser or terminal surface.
07 · Further notes

Durable operating notes

The new workflow must follow progressive disclosure: keep its entry point concise and move detailed artifact guidance into its own references.

Human guides must remain consistent with their skills, and all reviewer-facing text must use the ubiquitous language recorded in the applicable context files.
