02 · Tracer bullet

Make UI mockups a standalone reviewed workflow

Deliver a discoverable mockup skill that can classify relevance, render credible interface states, iterate on feedback, and preserve an approved visual decision.

Can run unattended · AFKStatus · CompleteBlocked by · None

What to build

Define the concise workflow entry point, progressively disclosed artifact contract, and consistent human guide. The workflow produces one recommended interactive design by default, adds meaningful alternatives only for a true design fork, and reviews the canonical result for explicit approval.

Acceptance criteria

  1. The skill recognizes material browser and terminal UI while excluding internal work, exact copy replacements, mechanical styling repairs, and small defect fixes without a design decision.
  2. The canonical artifact uses semantic, self-contained HTML and visibly identifies affected surfaces, realistic content, important states, responsive intent, and accessibility behavior.
  3. The artifact presents one recommended design unless an unresolved fork justifies two or three structurally different alternatives.
  4. Feedback updates the same live artifact, and the settled artifact visibly preserves the selected design, rationale, and rejected alternatives before explicit approval.
  5. The workflow defines authoritative interaction, hierarchy, state, responsive, and accessibility decisions while marking decorative styling and dimensions as directional by default.
  6. Content-contract tests fail when relevance, variant discipline, canonical output, authority, or approval behavior disappears.
  7. The existing directory-driven installer projects the new skill into both harnesses without a same-named Command.

03 · Tracer bullet

Route relevant builds through the Design→Spec gate

Integrate the approved standalone workflow without adding a fifth pipeline boundary or mixing design exploration into specification synthesis.

Can run unattended · AFKStatus · CompleteBlocked by · S1

What to build

Make Build determine relevance from grilled scope and inspected code, create the Feature directory when a mockup is needed, and load the mockup workflow before Spec. Keep post-grill chat confirmation for non-UI work and use mockup approval for relevant UI.

Acceptance criteria

  1. Build loads the mockup skill directly and asks the user about relevance only when scope and code leave the classification ambiguous.
  2. Relevant UI proceeds from grilling into mockup review, and explicit mockup approval clears the Design→Spec gate and starts Spec without another confirmation.
  3. Work without relevant UI retains post-grill chat confirmation as the same first approval boundary.
  4. The pipeline still declares and enforces exactly four approval gates.
  5. Standalone Spec detects a missing relevant mockup, invokes the prerequisite workflow, then summarizes and links the approved design without duplicating it.
  6. Material UI feedback returns to the mockup, synchronizes the Spec, and requires renewed Spec approval when prior approval is invalidated.
  7. Shared pipeline guidance, Build and Spec guides, ubiquitous language, and content-contract checks describe both gate branches consistently.

04 · Tracer bullet

Carry approved visual intent through delivery

Make every downstream phase consume the mockup when present and distinguish material design drift from harmless decorative differences.

Can run unattended · AFKStatus · CompleteBlocked by · S1, S2

What to build

Thread the approved mockup into task design, both implementation modes, and build-mode Review change. Preserve approved design intent, require focused evidence for conformance, and fail visibly when the available environment cannot substantiate a material UI claim.

Acceptance criteria

  1. Tasks read the mockup when present and carry its authoritative behavior, hierarchy, states, responsive intent, and accessibility decisions into UI acceptance criteria and test surfaces.
  2. Task feedback that materially redesigns UI returns upstream to synchronized mockup and Spec review instead of inventing a new interface.
  3. Code and coach read the approved mockup with the Spec and Tasks while retaining their existing implementation ownership and TDD discipline.
  4. Build passes the mockup to Review change as Authoritative intent when present.
  5. Review change uses the smallest available behavior tests, browser checks, rendered screenshots, or documented manual checks and reports material drift rather than pixel differences.
  6. Insufficient UI evidence produces an ask-user Finding instead of an unsupported conformance claim.
  7. Cross-skill content tests fail if any downstream consumer drops the approved mockup or its synchronization rule.

05 · Tracer bullet

Keep prototypes focused while composing mockups

Clarify the boundary between a canonical UI mockup and throwaway runnable code, then order them from the question the prototype must answer.

Can run unattended · AFKStatus · CompleteBlocked by · S1

What to build

Update Prototype so it can consume an approved mockup when interface design is central, defer optional visual work when UI only presents another experiment, and skip mockup entirely when no design question exists.

Acceptance criteria

  1. A prototype invokes mockup first when end-user interface design is the subject or an imperative prerequisite.
  2. A prototype that uses UI only to explore data, iterate through manual processing, or expose state answers its primary question first and leaves optional mockup work until last.
  3. A prototype without a UI design question skips mockup.
  4. Runnable UI prototypes remain grounded in the host application when integration, real data density, or state behavior cannot be judged in standalone HTML.
  5. Prototype and mockup code remain non-production, and neither workflow silently promotes throwaway code.
  6. The Prototype guide, public description, context files, and routing tests use the same boundary and ordering rules.
