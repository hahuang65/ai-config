Standalone physical-design workflow

3D Skill · Spec

Add an original, harness-neutral skill that helps a user turn a physical-part idea into parameterized source, printable exports, reviewed renders, and repository-consistent documentation without copying the upstream skill wholesale.

Skill name: 3dDefault engine: CadQueryTwo review checkpointsMIT-compatible synthesis

01 · Problem statement

A printable part needs more than generated geometry

The user wants a reusable 3D design workflow in the shared skill library, but does not want a wholesale copy of the Flowful.ai skill. A useful workflow must collect physical constraints, preserve adjustable source, catch geometry problems before printing, request feedback before detail work is wasted, document each 3D print project, and distinguish software evidence from facts that only a real print can prove.

02 · Solution

Guide one model from measurements to documented delivery

The standalone 3d skill will create or continue one 3D print project. It will use CadQuery for new projects, preserve OpenSCAD for existing OpenSCAD projects, produce STL and optional STEP exports, and present temporary model review sheets through the existing browser review workflow. It will finish with a final render, a mandatory per-project README, and a root catalog update when the repository has one.

The approved model review sheet mockup defines the checkpoint information hierarchy: the render first, then dimensions and parameters, then separate computed and physical validation, print guidance, and final project files.

03 · User stories

Complete behavior

  1. As a maker, I want the skill to ask first about the part's purpose and must-fit dimensions, so that geometry starts from the constraints that determine success.
  2. As a maker, I want mounting, material, printer, load, access, and aesthetic questions asked only when relevant, so that the interview is thorough without becoming a form dump.
  3. As a maker, I want my direct measurements to override published dimensions, so that the model fits the physical item I actually own.
  4. As a maker, I want externally researched dimensions cited and conflicts surfaced, so that I can assess their reliability instead of accepting hidden guesses.
  5. As a maker, I want explicit printer assumptions when geometry does not require more information, so that work can continue without unnecessary questions.
  6. As a maker, I want new designs written as parameterized CadQuery source, so that important dimensions remain easy to adjust.
  7. As a maintainer of an existing OpenSCAD design, I want the skill to keep using OpenSCAD, so that a continuation does not rewrite or mix the established source without my request.
  8. As a maker, I want source, STL, optional STEP, render configuration, final render, and documentation kept in one 3D print project directory, so that the product remains understandable and portable.
  9. As a repository maintainer, I want directory and file names to follow existing repository conventions, so that new products look native to the library.
  10. As a reviewer, I want to approve the functional shape before finish work, so that fit, attachment, proportions, and orientation errors are corrected early.
  11. As a reviewer, I want a final-model approval after finishing and validation, so that I can assess the complete printable result.
  12. As a reviewer, I want complex models to add a feature checkpoint and simple models to combine checkpoints when justified, so that review effort matches risk.
  13. As a reviewer, I want each checkpoint to show useful model angles, dimensions, adjustable parameters, evidence, print assumptions, and unresolved physical risks, so that approval is informed.
  14. As a reviewer, I want checkpoint feedback collected through the browser when available and through chat otherwise, so that missing browser support does not remove explicit approval.
  15. As a maker, I want the workflow to stop and explain missing CAD or preview capabilities before installation, so that it does not modify my environment without consent.
  16. As a maker, I want failed geometry, missing renders, or invalid meshes reported honestly, so that an unvalidated model is never presented as ready.
  17. As a maker, I want computed checks separated from physical proof, so that watertight geometry is not mistaken for verified fit, strength, or durability.
  18. As a maker, I want a fit coupon or other small test print recommended for tight interfaces and a load prototype recommended for structural parts, so that physical risk is tested efficiently.
  19. As a future maintainer, I want every product to have a README with dimensions, source and export links, material, print settings, hardware, assembly, design notes, and validation limits as applicable, so that the design can be reproduced later.
  20. As a repository reader, I want the root product catalog updated when one exists, so that the new 3D print project is discoverable.
  21. As a maker, I want ambiguous existing project directories protected from overwrite, so that unrelated work is not silently replaced.
  22. As a skill-library maintainer, I want visible credit to Nicolas Chourrout, Flowful.ai, the upstream repository, and the article, so that the source of inspiration is clear.
  23. As a skill-library maintainer, I want the new content written originally under this repository's MIT license, so that upstream PolyForm Noncommercial code and substantial text do not enter the library.

04 · Implementation decisions

Workflow and boundaries

Standalone capability

The capability is a skill named 3d, available to both supported harnesses. It has no same-named command and does not join the software Build workflow.

Progressive disclosure

The entry point stays thin. Separate references own the end-to-end workflow, FDM design guidance, and the model review sheet contract.

Project location and naming

The default project location is a title-cased product directory directly beneath the current directory. In an established repository, directory names, source basenames, part suffixes, render names, render configuration, and README conventions follow local prior art. An existing directory is reused only for a clear continuation; otherwise the user chooses whether to update it or use another name.

CAD engine

New projects default to CadQuery. Existing OpenSCAD projects stay OpenSCAD. The skill does not silently convert between engines or fall back to another engine after a failure.

Dimension authority

User measurements are authoritative. Reliable product or standards dimensions are researched when needed and cited in source comments and the model review sheet. Conflicts are reported. Unspecified ordinary work assumes a 0.4 mm nozzle, 0.20 mm layers, and PLA only when those assumptions do not conceal a geometry-changing decision.

Checkpoint lifecycle

Ordinary work has functional-shape and final-model approvals. Simple low-risk parts can combine them with a stated reason. Complex, enclosed, multipart, or tight-tolerance parts can add a feature checkpoint. Ending or closing a review does not approve it.

Temporary review surface

Each checkpoint uses a temporary semantic HTML model review sheet that embeds locally confined renders. The sheet updates during feedback and is deleted after approval by default. The delivered project keeps its parameterized source, printable exports, final render, render configuration, and documentation; checkpoint sheets and intermediate renders remain temporary unless the user asks for design history.

Validation claims

Computed evidence can establish successful model generation, expected bounds, solid or mesh integrity, and measurable geometry constraints. It cannot prove fit, strength, creep resistance, environmental durability, slicer behavior, or assembly. Delivery names those limits and recommends proportionate physical tests.

Environment ownership

The skill uses available local tooling. When required capabilities are missing, it reports the gap, proposes a setup compatible with the user's mise-managed toolchains, and waits before installation.

Documentation and attribution

Every 3D print project receives its own README, and a root product catalog is updated when present. The skill-library README acknowledges the upstream repository and article as inspiration while stating that this implementation is an original selective adaptation.

06 · Testing decisions

Test the installed skill contract

Content evidence

  • The skill has valid name and description metadata.
  • Every linked reference exists and uses the repository's progressive-disclosure structure.
  • The workflow requires a per-project README and local naming conventions.
  • The workflow defaults new projects to CadQuery and preserves existing OpenSCAD projects.
  • The workflow requires explicit checkpoint approval and browser-review fallback behavior.
  • The workflow separates computed evidence from physical proof.
  • The workflow refuses silent dependency installation, engine fallback, and ambiguous overwrite.

Installation and review evidence

  • The existing installation suite proves that the new shared skill reaches both harnesses.
  • The existing cross-reference gate proves that every linked reference resolves, while installation symlinks each complete skill directory.
  • The existing review-artifact suite remains the evidence for HTML review mechanics and asset confinement.
  • The repository-wide gate verifies content, installation isolation, guardrails, and self-tests before commit.

07 · Out of scope

Deliberate exclusions

  • Gridfinity-specific generators, dimensions, and APIs.
  • 3D scan processing or scan-to-pocket outline extraction.
  • Copied upstream Python utilities, preview renderers, model generators, tests, examples, images, or substantial prose.
  • A bundled CAD runtime, dependency installer, renderer, or mesh converter.
  • Editing an existing STL without parameterized source.
  • Digital-only modeling for games, animation, sculpting, or photogrammetry.
  • Structural certification, simulation claims, or a promise that computed checks replace a test print.
  • Changes to the software Build workflow or a new explicit command.
  • Permanent checkpoint HTML or intermediate renders unless the user asks to keep design history.

08 · Further notes

Source context

The upstream repository is licensed under PolyForm Noncommercial 1.0.0, while this library is MIT-licensed. The implementation must remain an original synthesis of useful ideas. Public acknowledgement will credit Nicolas Chourrout and Flowful.ai and link both flowful-ai/cad-skill and I Taught Claude to Design 3D-Printable Parts. Here's How.

The article reinforces the selected design: interactive checkpoints catch mistakes early; researched dimensions matter for mating products; a real CAD kernel supports functional geometry; preview-based self-review is more reliable than batch delivery; and physical slicer or print feedback remains essential.
