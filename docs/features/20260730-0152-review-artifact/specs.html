Build pipeline · Phase 2

Review Artifact — Spec

Replace passive browser opens and Markdown annotation cycles with a locally owned, durable feedback surface built around canonical semantic HTML.

Core decisionThe HTML under review is the deliverable. The browser chrome is temporary; annotations and approval travel back to the agent without rewriting the artifact behind the user’s back.

01 · Intent

Problem and solution

Problem statement

The build pipeline already produces rich HTML, but feedback falls back to chat or edits in a separate Markdown file. The browser can show the artifact but cannot identify the exact element or text at issue, carry a review conversation, or emit an unambiguous approval event. The open visual also becomes stale while the source changes elsewhere.

Solution

Introduce the review-artifact skill and its local review runtime. It serves any local HTML artifact inside a sandboxed review shell, lets the user annotate elements and text, batches messages for the agent, live-reloads edits, reports severe layout failures, and distinguishes explicit approval from merely ending review. Specs and tasks become canonical HTML consumed directly by later phases.

02 · Loop

One durable review session

01 · OPENAgent opens a canonical HTML path.
02 · ANNOTATEUser targets an element, text range, or message.
03 · POLLAgent receives a durable feedback batch.
04 · RELOADAgent edits the same HTML; browser refreshes in place.
05 · DECIDEUser explicitly approves or ends without approval.
03 · Outcomes

User stories

  1. As a build-pipeline user, I want every HTML artifact that requests feedback to open in one consistent review surface, so that I do not switch feedback conventions between phases.
  2. As a reviewer, I want to click an exact rendered element and attach a note, so that the agent knows what my feedback refers to.
  3. As a reviewer, I want to select a precise text range and annotate it, so that wording feedback is not reduced to a whole-section selector.
  4. As a reviewer, I want to queue several annotations and a freeform message before sending, so that the agent receives one coherent batch.
  5. As a reviewer, I want an Explore mode for native links and controls, so that annotation does not make the artifact unusable.
  6. As a reviewer, I want keyboard shortcuts and visible focus states, so that the full review loop works without a pointer.
  7. As a reviewer, I want the browser to show whether the agent is listening or working, so that I know whether feedback was delivered.
  8. As a reviewer, I want agent replies to appear in the review conversation, so that I can continue without moving back to chat.
  9. As a reviewer, I want the artifact to refresh after the agent edits it while preserving my place, so that each feedback cycle reviews the current version.
  10. As a reviewer, I want an explicit Approve action, so that approval cannot be confused with closing a tab or ending a session.
  11. As a reviewer, I want End review to remain distinct from Approve, so that I can stop without accidentally clearing a build gate.
  12. As an agent, I want a foreground long-poll command, so that browser feedback reliably resumes the active harness turn.
  13. As an agent, I want interrupted polling to be safe to retry, so that queued feedback is never lost.
  14. As an agent, I want feedback to include selectors, nearby text, text-range anchors, and a compact DOM snapshot, so that I can apply every note accurately.
  15. As an agent, I want a structured approval event, so that the pipeline can advance without interpreting prose.
  16. As an agent, I want proven severe layout failures delivered before human review, so that inaccessible or unusable content is repaired first.
  17. As a user, I want sessions keyed by canonical file path and durable across process restarts, so that returning to an artifact resumes the same review.
  18. As a user, I want a user-ended or approved session to remain closed unless intentionally reopened, so that the agent does not reopen a browser I deliberately dismissed.
  19. As a security-conscious user, I want the server bound to loopback with path confinement and host validation, so that arbitrary local files are not exposed to the network.
  20. As a maintainer, I want the review runtime installed with the skill and independent of an upstream package at runtime, so that pipeline behavior remains under repository control.
  21. As a maintainer, I want appropriate MIT attribution for adapted Lavish code, so that provenance stays explicit.
  22. As a pipeline author, I want specs and tasks to be canonical semantic HTML without Markdown companions, so that the reviewed representation and durable representation cannot drift.
  23. As a later pipeline phase, I want stable semantic metadata for task identity, status, dependencies, and interaction mode, so that I can consume and update tasks without a duplicate hidden model.
  24. As a user in a restricted environment, I want chat review to remain available when the browser runtime cannot start, so that the build does not deadlock.
04 · Shape

Deep modules and test seams

Public seam

Review command

Validates commands and paths, starts or contacts the local runtime, opens or resumes a session, long-polls for events, sends agent replies, and ends sessions.

Test surface
Directly through the command’s exit status and structured output.

Public seam

Review server

Owns the loopback HTTP boundary, host validation, sandboxed artifact delivery, event routes, live-reload stream, and lifecycle shutdown.

Test surface
Directly through HTTP requests against an ephemeral server.

Deep core

Session store

Persists one session per canonical file path, atomically queues feedback and decisions, tracks delivery, and preserves user-ended semantics across restarts.

Test surface
Directly through a small durable session API with exhaustive lifecycle cases.

Browser seam

Review shell

Owns conversation, queued annotations, presence, approval and end controls, responsive composition, focus management, and communication with the artifact frame.

Test surface
Covered through browser-level interaction tests and HTTP integration.

Browser seam

Artifact bridge

Is injected only into the served response. It identifies targets and text ranges, captures compact snapshots, audits severe layout failures, and communicates through a constrained message protocol.

Test surface
Directly test pure classification and target helpers; cover complete behavior in browser tests.

Workflow seam

Pipeline integration

Defines when review-artifact is mandatory, makes specs and tasks HTML-native, keeps live visuals synchronized, and routes structured approval into existing gates with chat fallback.

Test surface
Through repository content and installation contracts rather than runtime unit tests.

05 · Commitments

Implementation decisions

01

HTML is canonical

Per ADR-0018, specs and tasks are semantic HTML deliverables. Later phases read and update the visible document directly. Narrow metadata supports task identity, status, dependencies, interaction mode, and covered stories; there is no Markdown companion or duplicated hidden JSON model.

02

Review and generation stay separate

The visualization workflow generates or regenerates an artifact. The review-artifact skill owns only presentation, feedback, approval, and session lifecycle, so any HTML producer can use the same review surface.

03

Adapt the narrow Lavish core

The implementation adapts relevant MIT-licensed Lavish behavior for annotation, text ranges, session delivery, and severe layout evidence. Attribution is retained. Whiteboards, export, sharing, hooks, design playbooks, telemetry, and upstream runtime dependencies are deliberately removed.

04

Self-contained runtime distribution

The installed skill invokes small committed runtime modules directly with Node.js. The runtime has no third-party package dependency or generated bundle, so harness installation remains symlink-based and reproducible without dependency installation.

05

Path identity and durable lifecycle

A canonical real path determines session identity. State is stored locally outside the project, written atomically, and survives server restarts. Pending events remain available until a poll successfully consumes them.

06

Approval is a first-class decision

The browser exposes Approve separately from Send feedback and End review. Approval returns a structured decision and ends the review. Ending or closing without approval never clears a pipeline gate.

07

Foreground polling is the wake path

The agent keeps the long poll attached to the active tool call. Interrupted polls are retried; no detached shell, fire-and-forget process, or unverified callback is used.

08

Live reload replaces stale review

After each feedback batch the agent edits the canonical HTML. The browser reloads the file in place and preserves useful review context before polling resumes with an agent reply.

09

Local HTTP is hostile-input territory

The server binds only to loopback, validates Host and Origin where state changes occur, accepts bounded schema-validated JSON, confines file reads to the artifact directory, escapes all chrome-rendered content, and never logs artifact or feedback bodies.

10

The artifact remains portable

The saved HTML is never rewritten to include review code. The server injects a bridge into the served response and presents it inside a sandboxed iframe, so opening the file directly still shows the original artifact.

11

Review controls are accessible

The shell uses native controls, visible focus, labelled state, WCAG AA contrast, predictable tab order, keyboard submission, an annotation/explore toggle, focus restoration, and a responsive single-column fallback.

12

Layout warnings require direct evidence

Only stable, severe failures that make meaningful content or required controls inaccessible are returned. Intentional overflow, truncation, masks, decorative overlap, tiny excursions, and uncertain motion remain silent.

13

Chat is a resilience path

If browser opening or the local runtime fails, the invoking phase explicitly falls back to chat. Chat can also approve while a session is open, but browser review remains the default whenever available.

06 · Boundary

Command and event contract

InterfaceObservable behaviorFailure behavior
review-artifact <file>Validates HTML, opens or resumes the path-keyed session, launches the browser, and returns structured session metadata.Rejects missing, non-HTML, unreadable, or unsafe paths without starting a session.
review-artifact poll <file>Waits for a feedback batch, approval, end event, or severe layout warning. Optional agent reply is delivered before waiting.Connection interruption leaves queued events intact and returns retry guidance.
review-artifact end <file>Ends the session as the agent without manufacturing approval.Missing sessions produce an idempotent, structured not-active result.
review-artifact stopStops only a runtime that proves its application identity.Never terminates an unrelated process occupying the configured port.
feedback eventContains ordered prompts, target selectors and text, range anchors where applicable, and a bounded DOM snapshot.Malformed or oversized browser payloads are rejected and remain visible as send errors.
approval eventContains an explicit approved decision, file identity, and user-ended session state.No implicit approval is inferred from disconnect, close, timeout, or generic end.
layout eventContains only proven severe findings with selector, kind, axis, overflow magnitude, viewport width, and persistence.Cosmetic or uncertain findings are discarded before delivery.

HTTP posture: routes are private implementation details behind the command interface. They use explicit methods, JSON responses, bounded request bodies, stable error codes, and no authentication only because the server is loopback-only with Host and same-origin defenses.

07 · Evidence

Testing decisions

Review command

Start with behavior tests through the command seam: opening valid and invalid files, structured outputs, retry-safe polling, replies, approval delivery, idempotent end, and protection against unrelated port occupants.

Review server

Exercise the HTTP boundary on an ephemeral port: host and origin rejection, schema and size validation, path confinement, sandbox response, injection without source mutation, event delivery, and live reload.

Session store

Directly cover the deep lifecycle module: canonical identity, atomic persistence, ordered batches, take-once delivery, interrupted poll safety, approval versus end, restart recovery, and session reopen rules.

Artifact bridge

Directly cover pure selector, text-range, snapshot, control-classification, and severe-layout classifiers. Add browser tests for exact target selection, annotation mode, keyboard paths, and real rendered overflow evidence.

Review shell

Use browser-level tests for queued annotations, freeform messages, presence, agent replies, Approve versus End, focus and keyboard behavior, narrow viewport layout, live-reload scroll preservation, and XSS-resistant rendering.

Pipeline integration

Extend the repository’s content and install gates to prove the new skill is installed into both harnesses, all feedback-producing HTML workflows invoke it, obsolete Markdown artifact language is gone, and guides remain synchronized.

TDD rule: every behavior starts with one failing test through the highest stable seam. Lower-level tests are added only for deep reusable logic or edge cases that the public seam cannot cover efficiently.

08 · Boundary

Scope

In scope

  • Local review command and durable runtime
  • Sandboxed arbitrary HTML serving
  • Element and selected-text annotations
  • Queued feedback and freeform messages
  • Agent presence, replies, and foreground polling
  • Explicit approval distinct from end
  • Live reload and severe layout warnings
  • HTML-native specs and tasks
  • Pipeline, command, guide, installer, and test updates
  • MIT attribution for adapted source

Out of scope

  • Editable Mermaid or Excalidraw whiteboards
  • Standalone export bundling
  • Third-party publishing or sharing
  • Session-start hooks or ambient context
  • Visualization design playbooks
  • Telemetry or update checks
  • Remote network binding or multi-user authentication
  • A generic hidden artifact schema or Markdown compatibility layer
09 · Notes

Further notes

The implementation should preserve the best security and delivery semantics from its Lavish inspiration while remaining materially smaller than the upstream product. The review runtime is infrastructure for both harnesses, not a browser application the user must install or manage separately. Historical feature directories remain untouched; the HTML-only convention applies to new pipeline runs.
