pi Harness — PRD

Bring the third harness from a pending slot to live: a thin tier-A guard adapter routing the shared core, and one new mechanism — advisory rules projected into pi as a gate-checked concatenation (ADR-0013).

01 Problem

The repo configures three harnesses, but only two are live. pi (@oh-my-pi/pi-coding-agent, config root ~/.pi/agent) sits as a pending harness module — a slot with harness_pending=true and a no-op install. It was parked until the guardrails it must enforce lived somewhere a thin adapter could reach — which the consolidation (ADR-0012) just delivered.

Admitting pi means three invariants must hold: every floor guardrail enforced on pi, the isolation invariant across three roots, and the advisory rules reach pi. Only the third is new — pi has neither Claude's rules-dir injection nor oh-my-pi's native rulebook.

02 Solution

Fill the slot with the established harness-module (ADR-0010) and ports-and-adapters guardrail (ADR-0011/0012) patterns, plus the one new rule-projection mechanism (ADR-0013). pi inherits all twelve guardrails through a thin adapter — zero detection logic written — and a conformance column proves it.

Already solved (inherit)

Tier-A adapter shape (twin of omp) · the 12-policy guard core · conformance + isolation test harness · the generic install loop. pi has no built-in permission system, so the extension is its entire policy layer.

New (build)

The rule concatenation: advisory rules → a committed file → symlinked as pi's always-on APPEND_SYSTEM.md, kept honest by a gate drift-check. The third rule-projection mechanism.

03 Three harnesses, two axes

How enforcement and advisory rules reach each harness. Enforcement is one shared path (the guard core); rule projection is three different mechanisms sized to each harness's context model.

04 The new part — rule concatenation (ADR-0013)

pi reads single always-on context files (SYSTEM.md / APPEND_SYSTEM.md, per-project AGENTS.md) — not a rules directory, and with no @import expansion. That's why the rules must be concatenated into one file.

Edit-regenerate-commit; install once. The symlink makes a regenerated file live without re-installing; the drift-check makes a forgotten regeneration fail the pre-commit gate. (omp's committed RULES.md is precedent for the committed-and-symlinked shape.)

✓ always-on concatenation

Reliable for 6 small, always-relevant rules — advisory guidance only helps if the model sees it. Matches Claude's treatment. Rejected: a lazy progressive-disclosure index (the model often won't pull it).

✓ committed + symlinked + gated

Live after one install; drift is catchable from the repo. Rejected: generating into $HOME at install — drifts on a forgotten re-install and can't be gate-checked.

05 Module sketch

pi guard adapter thin twin

Tier-A extension: normalizes pi's tool_call event → the shared guard core → {block,reason}. Zero detection. Installs into ~/.pi/agent/extensions/.

pi manifest / install_module wiring

Fills the slot: consumes skills/commands/agents, symlinks the extension + APPEND_SYSTEM.md, installs settings, flips harness_pending=false.

pi settings.json config

Repo-managed provider/model/thinking, mirroring oh-my-pi's Opus default. User-editable.

Rule concatenation + drift gate novel · ADR-0013

A make target generates the concatenation from rules/*.md; a test/content drift-check + a self-test fixture prove a stale copy fails the gate.

Cross-harness test extension proof

Conformance matrix → 3rd column (pi); a pi-adapter unit test (twin of omp's); isolation + install tests gain ~/.pi/agent.

06 User stories (12)

  1. Every floor guardrail enforced when running pi.
  2. pi's guardrails are the same shared matchers — no second copy.
  3. Conformance matrix shows a 3rd column for pi, no floor gaps.
  4. pi enforces through a thin adapter (filling a slot, not re-implementing).
  5. Shared advisory rules reach pi.
  6. Can't ship advisory rules stale — a forgotten regen fails the gate.
  7. A rule edit reaches pi without re-running the installer.
  8. Isolation invariant holds for three config roots.
  9. pi's runtime config is version-controlled, mirrors the omp default, stays editable.
  10. Skills as /skill:name, commands as clean /name.
  11. Whole gate green, incl. a self-test that a stale concatenation is rejected.
  12. pi added as one module, no restructuring of the others.
