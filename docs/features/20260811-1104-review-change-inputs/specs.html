Review Change Input Resolution Spec

Review the change the user named, from wherever they are, without stale branches, brittle GitHub parsing, or accidental trust.

GitHub pull requests GitHub branches Local-first matching Isolated acquisition
01

Problem Statement

Broken journey

A valid change can fail before review starts

A GitHub pull-request URL fails when it contains a tab suffix such as /changes.

The user must already be inside the correct repository, even when a complete GitHub URL identifies that repository.

Local branch resolution can also select a stale local or remote-tracking tip because it does not fetch and compare both versions first.

Cost to the user

Repository discovery becomes manual setup

The user must find a checkout, remove harmless URL suffixes, translate links into accepted syntax, and determine which branch copy is current.

These tasks are target resolution work and belong to Review change, not to the user.

Security constraint. Convenience must not materialize or execute an untrusted remote change, mutate the user's source Git metadata, or weaken A5 classification rules.
02

Solution

Review change accepts a broader, explicit GitHub target grammar and resolves the named repository itself.

It separates safe input parsing from repository acquisition, performs network and Git work only inside a disposable review workspace, and freezes the final comparison to immutable commit identifiers.

ParseValidate the complete input and normalize a GitHub target without side effects.
→
Acquire and fetchSnapshot local state or clone the named GitHub repository under the review-only root.
→
Freeze and reviewSelect the current branch tip, derive the base, and pass immutable scope to validation.
Local-first means exact. Inside a repository, an exact local branch named pull/59 or 59 wins over the corresponding shorthand. Explicit GitHub URLs and gh: identifiers are not ambiguous and always select their named repository.
03

User Stories

  1. As a reviewer, I want a GitHub pull-request URL with a trailing tab path such as /changes to resolve, so that a copied browser URL works unchanged.
  2. As a reviewer, I want harmless query strings and fragments on a GitHub pull-request URL to be ignored, so that shared and copied links remain usable.
  3. As a reviewer, I want gh:owner/repository/pull/59 to identify a pull request, so that I can use a concise provider-qualified target.
  4. As a reviewer, I want GitHub branch URLs to support branch names containing slashes, so that names such as av/upgrade-to-uv resolve correctly.
  5. As a reviewer, I want gh:owner/repository/tree/branch to identify a GitHub branch, so that branches and pull requests share one concise identifier family.
  6. As a reviewer outside any Git repository, I want an explicit GitHub target to acquire its repository automatically, so that I do not have to find or create a checkout.
  7. As a reviewer inside a different repository, I want an explicit GitHub target to use the repository named by the target, so that my current directory cannot redirect the review.
  8. As a reviewer inside a repository, I want an exact local branch to win before numeric or pull/59 shorthand, so that valid branch names are not reinterpreted.
  9. As a reviewer, I want pull/59 to select pull request 59 from the current repository's GitHub remote when no exact local branch matches, so that common shorthand works.
  10. As a reviewer, I want a bare pull-request number to follow the same local-first rule, so that an exact numeric branch remains reviewable.
  11. As a reviewer, I want GitHub origin to own pull-request shorthand, so that the usual remote requires no extra input.
  12. As a reviewer without a GitHub origin, I want the only GitHub remote to own pull-request shorthand, so that an uncommon but unambiguous setup still works.
  13. As a reviewer with multiple possible GitHub remotes, I want Review change to stop and name the ambiguity, so that it never reviews the wrong repository.
  14. As a reviewer, I want branch freshness checked after an isolated fetch, so that stale remote-tracking state cannot choose the review scope.
  15. As a reviewer, I want the descendant tip selected when local and fetched remote branch versions are related, so that the more complete branch version is reviewed.
  16. As a reviewer who writes origin/my-branch, I still want a newer local descendant selected, so that explicit remote spelling does not force stale content.
  17. As a reviewer of diverged local and remote branch tips, I want Review change to alert me and stop, so that recency is not guessed from timestamps.
  18. As a reviewer when fetch fails, I want Review change to stop with a corrective error, so that stale data is never presented as current.
  19. As a reviewer of a mutable local or GitHub branch, I want its comparison base derived from the fetched repository's current default branch, so that the review represents the branch change.
  20. As a reviewer, I want the resolved base and head frozen to immutable commit identifiers, so that a moving branch cannot change scope during validation.
  21. As a reviewer of a private GitHub repository, I want acquisition to use authenticated GitHub access, so that private targets work without embedding credentials in logs or artifacts.
  22. As a security-conscious user, I want directly acquired remote changes treated as untrusted by default, so that their files and project commands are not materialized or executed with my authority.
  23. As an A5 developer, I want a direct branch trusted only after immutable-ID provider metadata and exact clone OID equality establish reviewed-content equivalence, so that A5 review does not claim repository identity that Git transport cannot attest.
  24. As an A5 developer using an HTTPS browser link, I want post-acquisition canonical provider identity evaluated through canonical SSH form, so that URL-conditioned global or system Git configuration still recognizes A5.
  25. As a user, I want invalid hosts, embedded credentials, malformed identifiers, and unsupported targets rejected before network or filesystem side effects, so that target input remains inert data.
  26. As a user outside a repository without an explicit GitHub target, I want concise accepted-form guidance, so that targetless and local-only inputs fail clearly.
  27. As a user, I want every acquired workspace to disable push and clean up only its recorded path, so that Review change remains read-only and does not disturb unrelated work.
  28. As a user, I want the skill workflow and standalone CLI to accept the same target forms and apply the same precedence, so that invocation surface does not change review meaning.
04

Implementation Decisions

Target grammar

Parse GitHub identity before Git

  • Accept https://github.com/owner/repository/pull/number and ignore content after the numeric pull-request segment.
  • Accept https://github.com/owner/repository/tree/… and resolve the longest existing branch-name prefix when the remainder could include a repository path.
  • Accept exact gh:owner/repository/pull/number and gh:owner/repository/tree/… identifiers.
  • Reject URL suffixes, queries, and fragments on gh: identifiers.
  • Preserve branch-name case and slash structure while normalizing repository identity.
Precedence

Explicit remote, then exact local

  1. An explicit GitHub URL or gh: identifier selects its named repository.
  2. Otherwise, an exact local branch wins.
  3. Otherwise, pull/number and a bare number resolve against the selected GitHub remote.
  4. Other input continues through local branch or range resolution.
GitHub remote

Prefer the conventional owner

Pull-request shorthand uses origin when it is a GitHub remote.

If origin is not GitHub, exactly one other GitHub remote is acceptable.

No match or multiple remaining matches is an operational error.

Branch freshness

Use ancestry, never timestamps

Fetch inside the disposable review workspace, then compare the local and fetched remote tips when both exist.

  • If equal, use the shared tip.
  • If one tip contains the other, use the descendant.
  • If the tips diverge, alert the user and stop.
  • If fetch fails, alert the user and stop.
Acquisition boundary

Clone and fetch only in review isolation

A local invocation snapshots tracked and untracked state before fetching in its disposable clone.

An explicit GitHub target acquires the named repository without checkout directly under the review-only root.

The source checkout's working tree, index, local refs, remote-tracking refs, and fetch metadata remain unchanged.

Trust boundary

Remote means untrusted until proven otherwise

The standalone parent freezes the selected OID and classifies trust before any materialization.

An untrusted remote head remains unmaterialized and receives static immutable-object inspection plus provider evidence only.

Explicit user trust uses --trust-remote for one direct target, and a documented sandbox retains its existing meaning.

For a direct branch, A5 classification is available only after strict immutable-ID provider resolution and exact provider/clone selected/default OID equality establish content equivalence.

Git transport does not attest clone repository node identity; unrelated clone refs cannot affect scope or trust.

Only a Trusted head is materialized, using only its exact selected OID and one recorded cleanup path.

A5 identity

Normalize transport without granting trust locally

Review change evaluates post-acquisition canonical metadata queried by immutable provider ID through canonical SSH form when consulting effective Git configuration.

This lets URL-conditioned includes recognize an HTTPS input.

Repository-local configuration cannot set or grant A5 status.

Immutable scope

Freeze after acquisition

A pull request uses provider metadata to identify its actual head repository, base commit, head commit, and cross-repository state.

A mutable local or GitHub branch uses the fetched repository's current default branch as base.

Validation receives immutable base and head commit identifiers rather than mutable branch names.

Failure contract

Fail before guessing

Unsupported hosts, malformed target structure, embedded credentials, missing repositories, unresolved branches, ambiguous remotes, divergence, and freshness failures produce concise corrective errors and nonzero CLI status.

Target validation completes before provider calls, clone creation, or fetch.

Surface parity

One target language

The interactive skill and standalone CLI document and apply the same GitHub target grammar, local precedence, freshness rules, trust classification, and read-only boundary.

The standalone CLI retains its current terminal pipeline, report, cancellation, and cleanup behavior.

Production module sketch

Deep module

GitHub target parser

Turns validated URL and gh: forms into one normalized repository and change description without side effects.

Public interface: parse one target string and return a normalized GitHub target or a precise validation failure.

Deep module

Review target resolver

Applies local precedence, selects a GitHub remote, compares fetched branch ancestry, derives the default base, and freezes immutable scope.

Public interface: resolve one parsed target against an isolated Git context.

Security boundary

Review workspace

Creates a local snapshot or direct remote acquisition, configures credential-safe fetch and disabled push, evaluates A5 identity, and owns exact-path cleanup.

Public interface: create one disposable workspace from a validated source description.

Public orchestration

Review change CLI lifecycle

Validates invocation data and coordinates parsing, acquisition, resolution, review execution, report opening, cancellation, and cleanup.

Public interfaces: the review-change executable and its lifecycle runner.

06

Out of Scope

  • SourceHut-specific URLs, identifiers, pull-request concepts, or repository acquisition.
  • GitLab, Bitbucket, Gitea, Forgejo, Azure DevOps, and other forge-specific targets.
  • GitHub Enterprise hosts beyond github.com.
  • Choosing between diverged local and remote tips by commit or reflog timestamp.
  • Using stale remote-tracking state after a failed fetch.
  • Changing pull-request Authoritative intent rules or provider review behavior.
  • Posting comments, submitting reviews, pushing repairs, merging, or any provider mutation.
  • Changing the Review change report, final Summary controls, or build-mode approval gate.
  • Changing project-wide A5 configuration or allowing repository-local A5 classification.
  • Persisting a directly acquired repository after the existing cleanup boundary.
07

Further Notes

Compatibility: Existing explicit local ranges, targetless current-branch review, report generation, and review validation stages retain their behavior.

Private repositories: GitHub authentication is an acquisition mechanism only. Credentials must not appear in remote URLs retained by the workspace, telemetry, errors, prompts, or reports.

Cleanup: A failed acquisition or review reports any retained recorded path and never performs broad repository cleanup.
